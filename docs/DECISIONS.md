# Решения по ходу цикла

Формат записи: **контекст → решение → причина**. Решения приняты по результатам
spike (фаза 0) и проверяемого кода, а не по предположениям.

---

## Фаза 1 — библиотека знаний

### D-011. Гармония в библиотеке — только степени лада

**Контекст.** Прогрессии требовалось хранить «в степенях, а не символами».
Проверка показала, что символы аккордов в Strudel пишутся как `Am`/`Am7`,
через двоеточие не принимаются, а набор таких символов пришлось бы переводить
в парсер и обратно. Степени же всегда в ладу по построению.

**Решение.** Прогрессия хранит `mode` и `degrees` — индексы ступеней лада.
Трезвучие строится как степени `[d, d+2, d+4]`. Символов аккордов в
библиотеке нет.

**Причина.** Гарантия «всегда в ладу» без отдельной проверки + совместимость
с анализатором, который тоже считает по степеням.

---

### D-012. Переходы и автоматизация — функции над дескрипторами, а не строки

**Контекст.** Требовалось хранить рецепты переходов как функции
`(pattern, barsLen) → pattern`. Нужен общий язык между библиотекой и
компилятором: переход меняет ритм, фильтр и автоматизацию партии, и это
нельзя выразить строкой шаблона.

**Решение.** Введён дескриптор партии (`knowledge/descriptor.js`): источник
(`n`/`note`/`s`), mini-нотация, флаг `.scale()` и цепочка методов с
структурированными аргументами (число / строка / описание сигнала). Переходы
и кривые автоматизации — чистые функции над дескриптором.

**Причина.** Функцию можно проверить и скомбинировать; шаблон строки — нет.
Сигнал описан данными (`{signal, slow, range, direction}`), потому что
`range` для затухания идёт вниз, а для нарастания — вверх.

---

### D-013. Лады в библиотеке ограничены списком, который понимает Strudel

**Контекст.** `scale()` принимает только полные имена одним словом.
`c:maj`, `c:min`, `c:harmonicminor` дают **пустой результат** с ошибкой в
консоли — то есть тихо ломают музыку, а не сообщают об ошибке.

**Решение.** В библиотеке используются только `major`, `minor`, `dorian`,
`phrygian`, `lydian`, `mixolydian` (плюс `ionian`/`aeolian` как синонимы).
Имена `harmonicminor`, `majpent`, `minpent` из `MODES`
(`server/music/notes.js`) в генерируемый код не попадают.

**Причина.** Собственный `MODES` — внутренний формат анализатора; генерируемый
код живёт по правилам Strudel. Смешивать их нельзя.

---

### D-014. Мелодические роли в матрице — на синтезаторах, ударные — на сэмплах

**Контекст.** У роли `lead` в джазе стоял синтезатор `sax`, а `sax` —
это **сэмпл** из белого списка, а не синтезатор.

**Решение.** Поле `synth` содержит только зарегистрированные синтезаторы
(`sawtooth`, `square`, `triangle`, `sine`, `piano`, `supersaw`, `pulse`,
`fm`, `am`, `organ`). Поле `sounds` — только сэмплы. У ролей `fx`/`texture`
паттерны содержат хотя бы один удар: паттерн из одной тишины не даёт ни
одного события и партия молчит.

**Причина.** Проверка библиотеки гоняет каждый паттерн через настоящий
движок: ошибка такого рода ловится автоматически, а не на слух.

---

### D-015. Длина формы ограничена 96 тактами

**Контекст.** Три формы (`techno-form-long`, `house-form-long`,
`cinematic-form-long`) вышли за 96 тактов — при требовании «32–96 тактов».

**Решение.** Секции укорочены так, чтобы каждая форма укладывалась в
диапазон. Длина формы — не «сколько влезло», а осознанный выбор: трек
должен быть разомкнут по форме, а не просто длинным.

**Причина.** Ограничение из задания; проверяется тестом и `check:knowledge`.

---

## Фаза 0 — spike

### D-001. Источник истины для метрик — события Strudel, а не свой парсер

**Контекст.** Метрики v2 (энергия по тактам, гармонический ритм, новизна
секций, вариативность) требуют событий на горизонте 32–96 тактов. Свой
парсер mini-нотации `server/music/mini.js` разбирает 1–2 такта и не понимает
`arrange`, `stack`, `cat/slowcat`, `<…>/n`, `.slow/.fast`, `.mask`, `.struct`,
`.every`. Расхождение измерено на `<0 5 2 6>/2`: наш парсер — 1 событие,
Strudel — 4.

**Решение.** Новые метрики прогрессии (фаза 4) считаются по событиям
`queryArc` из headless-исполнения Strudel. Свой парсер остаётся для
«быстрых» проверок (есть ли партия, лад, темп) и не меняется.

**Причина.** Требование «ничего из синтаксиса Strudel не принимать на веру»
означает, что источник истины — сам движок. Свой парсер — это реконструкция,
и на сложных конструкциях она расходится с реальностью.

---

### D-002. Headless-исполнение — через UMD-бандл @strudel/web

**Контекст.** `import '@strudel/core'` в Node падает:
`does not provide an export named 'SalatRepl'` — `@strudel/core` импортирует
`SalatRepl` из `@kabelsalat/web`, у которого в `main` лежит UMD-бандл без
этого экспорта.

**Решение.** Загружать UMD-бандл `@strudel/web` через `new Function`
(server/music/strudel-runtime.mjs). Тот же приём, что уже применён в
`scripts/check-presets.mjs`.

**Причина.** Правка зависимостей или замена пакета — риск и лишняя работа;
рабочий путь уже проверен в репозитории. Производительности хватает: 64 такта
× 6 партий — 25 мс.

---

### D-003. Нужен `setStringParser(mini)` — без него строки не разбираются

**Контекст.** Без явной регистрации строкового парсера `n("0 5 2 6")` даёт
**одно** событие `"0 5 2 6"` вместо трёх нот. В браузере это делает
`initStrudel`; в Node вызываем явно при загрузке.

**Решение.** `loadStrudel()` всегда вызывает `api.setStringParser(api.mini)`.

**Причина.** Без этого любые метрики по высотам считались бы по мусору.
Находка зафиксирована тестом «БЕЗ setStringParser строка не разбирается».

---

### D-004. Метки `$PART:` разбираются транспилятором, а не присваиванием

**Контекст.** `$BASS: <expr>` — это помеченный оператор JavaScript
(LabeledStatement), который сам по себе ничего не присваивает. Настоящий
Strudel прогоняет код через транспилятор: `$BASS: expr` → `expr.p('$BASS')`,
а `Pattern.prototype.p` кладёт паттерн в реестр.

**Решение.** Headless-исполнение идёт по цепочке
`код → transpiler → output → eval в песочнице → реестр по меткам`.
В песочнице `Pattern.prototype.p` подменён на сборщик партий.

**Причина.** Иначе партии не собираются вовсе. Отдельная ценность: порядок
партий сохраняется, микшер и mute/solo продолжают работать.

---

### D-005. Гармония выражается степенями лада, а не символами аккордов

**Контекст.** `chord("Am").voicing()` работает, а `chord("A:min").voicing()` —
нет (`unknown chord "A,min"`). Формы `"I V vi | IV"` и `"0:ma"` для Strudel
не существуют. Степени лада всегда в ладу по построению.

**Решение.** В схеме v2 гармония — это **степени** (`degrees: [0, 5, 2, 6]`).
Символы аккордов в генерируемый код не попадают.

**Причина.** Требование задачи плюс совместимость с анализатором: степени
гарантируют попадание в лад, а символы аккордов при неверном формате дают
пустую секцию вместо ошибки — худший вид отказа.

---

### D-006. Отдельный whitelist ладов для генерируемого кода

**Контекст.** `scale()` принимает только полные имена одним словом:
`c:major`, `c:minor`, `c:dorian`, `c:phrygian`, `c:lydian`, `c:mixolydian`,
`c:ionian`, `c:aeolian`, `c:pentatonic`, `c:blues`, `c:chromatic`.
`c:maj`, `c:min`, `c:harmonicminor` дают **пустой результат** с ошибкой в
консоли — то есть тихо ломают музыку.

**Решение.** В компиляторе — свой список допустимых ладов
(`server/music/knowledge/`), не связанный с `MODES` в `server/music/notes.js`,
где использованы `harmonicminor`, `majpent`, `minpent` — эти имена в код не
попадают.

**Причина.** Наш `MODES` — внутренний формат анализатора; генерируемый код
живёт по правилам Strudel. Смешивать их нельзя.

---

### D-007. Аккорд длиной 2 такта — через `.slow(2)`, а не через `/2`

**Контекст.** `n("<0 5 2 6>/2")` даёт 8 событий с дубликатами (по два на
позицию), `n("<0 5 2 6>").slow(2)` — 4 события длиной 2 такта.

**Решение.** В рецептах баса и аккордов используется `.slow(n)` как метод.

**Причина.** `/2` внутри mini-нотации даёт задвоенные атаки — это ударит по
метрике плотности и по таймлайну секций.

---

### D-008. Метрика автоматизации считается по значениям событий

**Контекст.** `sine.slow(4).range(a, b)` сам по себе отдаёт константу (0.5) —
сигнал раскрывается только в контексте параметра паттерна. Регуляркой по
тексту статичное `.gain(0.5)` не отличить от автоматизации.

**Решение.** Доля автоматизированных параметров считается по значениям
событий: если параметр меняется от события к событию — он автоматизирован.

**Причина.** Требование задачи «считать токенайзером/AST, не regex-ом» плюс
фактическое поведение движка.

---

### D-009. Старый парсер и новые метрики живут рядом

**Контекст.** Скор v1 (10 критериев) работает на `analyzeTrack` → свой парсер.
Метрики v2 требуют событий на длинном горизонте.

**Решение.** Скор v2 добавляется к существующему как **дополнительный слой**:
критерии v1 сохраняются (масштабируются до ~60% веса), новые добавляются
(~40%). Старый парсер и `analyzeTrack` не трогаем.

**Причина.** Требование «сохрани 10 старых критериев» и «106 тестов должны
остаться зелёными». Метрики v1 остаются источником обратной связи для
существующего refine.

---

### D-010. `setCpm(bpm/4)` остаётся формой темпа

**Контекст.** В бандле нет отдельной функции `setCpm` (темп ставится через
`cpm`/`cps`), но синтаксис `setCpm(124/4)` — то, что пишет генератор, что
понимает браузер и что читает `getBpm()` в `src/core/code-model.js`.

**Решение.** Компилятор пишет `setCpm(<bpm>/4)`. В headless-песочнице `setCpm`
— заглушка: темп берётся из текста кода.

**Причина.** Транспилятор пропускает эту строку без ошибок, а менять формат
темпа значило бы ломать `getBpm()` и существующие пресеты.

---

### D-016. Рецепт партии выбирает рисунок по плотности, а не по имени

**Контекст.** В спеке у каждой партии есть поле `recipe`. Если его игнорировать,
модель отвечает за проект, а компилятор всё равно ставит один и тот же рисунок —
это ровно то «плоское», что ТЗ просит убрать.

**Решение.** Рецепт — это не идентификатор шаблона, а **плотность**:
`default` (обычная плотность роли), `busy` (плотнее), `sparse` (реже).
Компилятор меряет плотность каждого шаблона библиотеки (`patternDensity`,
атаки на такт: `hh*16` → 16, `bd ~ bd ~` → 2) и выбирает подходящий.
Перечень рецептов — enum в схеме, поэтому модель не может придумать другой.

**Причина.** Название рецепта нельзя проверить исполнением, а плотность можно.
Плюс выбор по плотности даёт разнообразие рисунков без новых данных в
библиотеке.

---

### D-017. Плотность секции определяет рецепт по умолчанию

**Контекст.** Секция спеки несёт энергию 0..1. Если энергия не влияет на
звук, трек получается ровным: интро и дроп звучат одинаково.

**Решение.** Если рецепт не задан явно (`default`), он выводится из энергии
секции: ≥ 0.75 → `busy`, ≤ 0.4 → `sparse`, иначе `default`. Явный рецепт из
спеки всегда важнее энергии.

**Причина.** ТЗ требует «прогрессию во времени». Энергия — единственное поле
спеки, которое прямо описывает плотность секции, и решение превращает её в
звук без новых полей в контракте с моделью.

---

### D-018. Зерно влияет на рисунок через хэш, а не через генератор случайных чисел

**Контекст.** Первая версия компилятора использовала xorshift-PRNG. У seed = 1
состояние обнулялось на первом же шаге (`state >>>= 17` при малом состоянии),
и разные зёрна давали одинаковый код — тест «разный seed → разный код» это
поймал.

**Решение.** Никакого PRNG: вариант рисунка считается как
`hash(seed|роль) + индекс секции`, выбор шаблона — как `phase + index` по
пулу. Хэш не зависит от порядка обхода, поэтому добавление секции не
сдвигает рисунки соседних.

**Причина.** Детерминированность важнее «настоящей» случайности: код трека
должен воспроизводиться из спеки, а результат best-of-N (фаза 6) обязан быть
воспроизводимым по зерну.

---

### D-019. Гармонические партии строятся через `.add()`, ударные — без `.scale()`

**Контекст.** Арпеджио, идущее по аккордам прогрессии, нельзя собрать из
`stack()` одновременных голосов: это даёт аккорд, а не арпеджио.

**Решение.** Арпеджио и лид строятся как
`n("0 2 4").add(n("<степени>").slow(N)).scale(key)` — сумма берётся в
степенном пространстве, если `.add()` стоит **до** `.scale(key)`. Ударные и
эффекты — только сэмплы: `.scale(key)` к ним не применяется (движок ругается
`Invalid value format for 'scale'`).

**Причина.** Проверено пробами фазы 2 на живом движке, результаты — в
`docs/SPIKE.md`. Ошибка порядка методов даёт тихой неверный результат, поэтому
порядок зафиксирован в компиляторе и в тестах.

---

### D-020. Ритм мотива переводится в mini-строку, а не задаётся через `.struct()`

**Контекст.** `.struct("x ~ x x")` при длине ритма, не совпадающей с числом
нот, ведёт себя непредсказуемо: `n("0 2 4").struct("x ~ x x")` теряет третью
ноту и даёт восемь событий вместо трёх.

**Решение.** Ритм мотива раскладывается по степеням самостоятельно: `x ~ x x`
и `[0, 2, 4]` → mini-строка `0 ~ 2 4`. Больше нажатий, чем степеней, —
степени повторяются по кругу.

**Причина.** Свой код предсказуем, а `.struct()` — нет. Разница видна на
слух и на графике событий, поэтому ритм переводится детерминированно.

## Решения фазы 4 (метрики v2)

### D-021. Окно метрик — 4 такта; мера новизны — доля уникальных окон

**Контекст.** Новизна и вариативность меряются «по окнам». Окно в один
такт слишком мелко: смена рисунка внутри такта не даёт новых окон. Окно в
16 тактов слишком крупно: весь трек схлопывается в одно окно, и метрика
перестаёт различать статичный и развивающийся трек.

**Решение.** Окно = 4 такта (`WINDOW_BARS`). Мера новизны — доля
**уникальных** окон среди всех окон трека, а не доля уникальных тактов.

**Причина.** Доля уникальных тактов математически недостижима для
разумного трека: 64 такта — это 64 окна, и чтобы набрать 100 %, каждый
такт должен отличаться от всех остальных, что невозможно при повторяющейся
прогрессии. Окно в 4 такта совпадает с масштабом самой короткой секции
формы, поэтому окно — это «один смысловой блок».

### D-022. Старые 10 критериев пересчитываются по событиям, а не по тексту

**Контекст.** Скор v1 считал плотность и разнообразие своим парсером
mini-нотации. На структурированном треке (секции, `arrange`, `stack`)
парсер находит 0 событий, и плотность выходит нулевой — то есть
v1-скор штрафовал именно то, ради чего делался новый цикл.

**Решение.** Добавлен `analyzeTrackFromEvents` — слой, который получает
готовые события Strudel и считает по ним те же 10 критериев. Старый
`scoreTrack` не тронут: он продолжает работать как раньше.

**Причина.** Обратная совместимость и честность: v1-счётчик по-прежнему
применим к одиночным циклам, а для структурированных треков используется
источник истины из D-001. Ломать старый счётчик было бы дороже, чем
добавить слой рядом.

### D-023. Транспозиция партий — строго после `.scale(key)`

**Контекст.** Гармонические партии собираются из степеней лада, поэтому
бас, пэд и арпеджио звучат в одной октаве и сливаются в один тембр.

**Решение.** В компиляторе введена таблица `ROLE_TRANSPOSE`: bass/sub
`−24` (две октавы вниз), arp/lead `+12` (октава вверх), остальные — 0.
Транспозиция ставится **после** `.scale(key)`.

**Причина.** Проверено пробой `tests/spike/transpose-probe.mjs`: до
`.scale(key)` движок бросает `transpose: not a note` и значение молча
игнорирует — такой порядок дал бы «тихо сломанную» музыку вместо ошибки.
Октавное смещение выбрано потому, что не меняет гармоническую функцию:
интервальные отношения сохраняются.

### D-024. Длина трека берётся из блоков `arrange`, а не из горизонта опроса

**Контекст.** `arrange` **зацикливает** материал: `arrange([4, A], [8, B])`
— это 12 тактов, а не «12 тактов, и дальше всё заново». Длина трека,
взявтая из горизонта опроса, не совпадает с длиной формы.

**Решение.** Длина композиции вычисляется из блоков `arrange`
(`arrangeLength`), а не из числа собранных событий.

**Причина.** Метрики «прогрессия во времени» обязаны мерить ту длину,
которую слушатель действительно слышит. Иначе трек из 12 тактов, повторённый
до 64, выглядел бы как «развивающийся», а был бы статичным.

### D-025. Ноты вне лада задаются только через `note("c#4 …")`

**Контекст.** Первая версия adversarial-фикстуры «ноты вне лада» была
сделана как `n(...).scale(key)`. Оказалось, что `.scale(key)` **гарантирует**
попадание в лад: степень переводится в ступень лада по построению. Фикстура
оказалась в ладе и не тестировала заявленный дефект.

**Решение.** Для нот вне лада используется буквенная нотация
`note("c#4 e4 …")`. Наличие такой возможности — тоже защита от обмана:
дефект, который нельзя выразить в нотации лада, нельзя и случайно
спрятать.

**Причина.** Метрика `scaleFit` должна быть достижимо низкой, иначе она
не работает. Проверка достижимости дефекта — часть дизайна фикстуры.

### D-026. Adversarial-фикстуры обязаны иметь форму

**Контекст.** Первая версия фикстуры «статичные параметры» была 4 такта без
секций. Её скор был низким, но из-за отсутствия формы, а не из-за
статичных параметров — тест измерял бы не заявленный дефект.

**Решение.** Каждая фикстура содержит полноценную форму; отличается
**только** заявленный дефект. Каждая обязана получить балл ниже
эталонного трека — иначе дефект не наказывается.

**Причина.** Тест, который ловит не то, что заявляет, хуже отсутствия
теста: он создаёт ложную уверенность. Форма у всех фикстур — условие
сопоставимости с эталоном.

### D-027. Эталон сравнения — скомпилированный трек с шестью партиями

**Контекст.** Первая версия эталона наследовала 10 партий от теста
компилятора. Фикстура «восемь партий одним ритмом» получала штраф за
**число** партий, а не за одинаковый ритм, — то есть её низкий скор
объяснялся не тем, что проверялось.

**Решение.** Эталон — скомпилированный трек из нормальной спеки ровно с
шестью партиями (профиль technо требует 4–6). Сравнение идёт только с
ним.

**Причина.** Относительно числа партий счёт v1 штрафует превышение
профиля. Эталон должен лежать внутри профиля, иначе сравнение измеряет
аранжировку, а не дефект.

## Фаза 0 — аудио-спайк мини-студии

### D-028. K-взвешивание считается по формулам ITU-R BS.1770-4, а не по RBJ

**Контекст.** Первая версия `src/audio/dsp/k-weighting.js` считала коэффициенты
шелка и RLB-фильтра по формулам RBJ. Сверка с таблицей стандарта (48 кГц)
показала расхождение до **0.055** по b0 шелла — то есть другая АЧХ, а не другой
округ.

**Решение.** Коэффициенты считаются по формулам Таблицы 2 стандарта
(`ituShelfCoefficients`, `ituHighpassCoefficients`). Проверка: пересчёт при
48 кГц совпадает с таблицей стандарта с точностью **8.9e-16**, DC-усиление
шелла = 1.000000 в любой частоте дискретизации.

**Причина.** Стандарт — источник истины; RBJ-фильтр для полосы K не эквивалентен
ему. Расхождение 0.05 в коэффициентах даёт ошибку громкости, которую нельзя
игнорировать при приёмке в ±0.3 LU.

**Чем проверено.** `tests/unit/audio-dsp.test.js` (тест «коэффициенты на 48 кГц
совпадают с таблицей стандарта»), сверка с ffmpeg — `npm run validate:loudness`.

### D-029. True peak: полифазный фильтр 97 отсчётов с нормировкой фаз

**Контекст.** Первая версия передискретизатора давала −12 дБ на выходе: фазы
интерполятора не были нормированы (каждая фаза должна давать единичную сумму).
Вторая версия (64 отсчёта) имела дробную групповую задержку и расходилась с
ffmpeg на **0.42 dBTP** на широкополосном шуме.

**Решение.** Фильтр — windowed-sinc (Кайзер β = 9) на 97 отсчётах: центр 48 →
групповая задержка 12 исходных отсчётов (целое), сумма каждой фазы
нормирована в единицу.

**Причина.** Длина подобрана по сверке с эталоном: 65 отсчёков → 0.42 dBTP
против ffmpeg, 97 → **0.03 dBTP**. Более длинные фильтры (129+) сходятся к
«идеальной» реконструкции, но расходятся с ffmpeg на 0.4 дБ — приёмка идёт
по ffmpeg, поэтому эталон важнее абсолютной точности.

**Чем проверено.** `npm run validate:loudness`: 6 фикстур, |ΔLUFS| ≤ 0.05,
|ΔdBTP| ≤ 0.03 (ffmpeg ebur128, libebur128).

### D-030. Мастер-цепочка вставляется экспортным хуком, без перехвата `connect`

**Контекст.** Гипотеза H1 рисерча утверждала, что вставить цепочку между
superdough и `destination` публичным API нельзя и нужен перехват `connect`.

**Решение.** Хвост мастер-шины superdough доступен через экспорт
`getSuperdoughAudioController()`: `controller.output.destinationGain` — это
GainNode между `channelMerger` и `ctx.destination`. Цепочка вставляется так:
`destinationGain.disconnect()` → `destinationGain.connect(masterIn)` →
`masterIn → EQ → glue → лимитер → ctx.destination`. Перед этим —
`setSuperdoughAudioController(null)`, затем `setAudioContext(ctx)`: контроллер
синглтон и привязан к контексту на момент создания.

**Причина.** Разбор бандла @strudel/web 1.3.0 показал экспорт
`getSuperdoughAudioController`; перехват `connect` не нужен и не применяется.
Измерено в браузере: отношение RMS 0.500007 при gain 0.5, остаток bypass−baseline
точно ноль.

**Риск отката.** `output.destinationGain` — внутреннее поле минифицированного
бандла, а не документированный API. Поэтому есть контрактный тест движка: смена
версии `@strudel/web` обязана его сломать (`tests/unit/engine-contract.test.js`),
а в коде студии обязателен рантайм-guard с запасным путём.

### D-031. Офлайн-рендер — в отдельном контексте, `renderPatternAudio` не вызывается в живом приложении

**Контекст.** В @strudel/web 1.3.0 есть официальный `renderPatternAudio`, но он
делает `await ctx.close()` на текущем аудиоконтексте и создаёт свой
`OfflineAudioContext`, а результат отдаёт скачиванием WAV (буфер наружу не
отдаёт).

**Решение.** В приложении офлайн-рендер делается собственным кодом в
отдельном `OfflineAudioContext` (рендер-воркер), тем же DSP-ядром. Официальная
функция — только источник схемы вызова событий.

**Причина.** Закрытие живого контекста убило бы звук в приложении. Свой
рендер даёт буфер для метрик, повторяемость (два рендера) и отмену.

### D-032. Glue-компрессор: ослабление — отрицательное, тишина не даёт NaN

**Контекст.** Первая версия возвращала из `targetReduction` положительную
величину, и `grDb` уходил в плюс — компрессор **усиливал** сигнал вместо
ослабления. На старте файла (первый отсчёт тишины) огибающая уходила в NaN
(`−Infinity − −Infinity`), и весь выход становился NaN.

**Решение.** `targetReduction` возвращает отрицательные дБ (ослабление ≤ 0);
для тишины огибающая сбрасывается в ноль. Проверка потолка лимитера и GR
компрессора — в контрактных тестах.

**Причина.** Баг найден тестом, а не прослушиванием: на слухок NaN — это тишина.

### D-033. Аудио-пакеты запинены точно; версия едет в метриках

**Контекст.** `@strudel/web` был на `^1.3.0` — минорное обновление меняло бы
звук и API без предупреждения.

**Решение.** `@strudel/web` запинен как `1.3.0`; `ffmpeg-static` и
`playwright-core` — тоже точно (от них зависит воспроизводимость замеров).
Версии вынесены в `src/audio/engine-version.js` и попадают в
`MetricsReport.engineVersion`.

**Причина.** Метрика без версии движка невоспроизводима: тот же LUFS на другой
версии — другой мир.

### D-034. Изоляция ассистента — без MicroVM/gVisor

**Контекст.** Рисерч предлагал уровни изоляции (MicroVM, gVisor) для
безопасности LLM-агента.

**Решение.** Не применяются. Ассистент не порождает исполняемый код: он
работает только tool-use поверх командной шины с Zod-валидацией; сетевых и
файловых инструментов нет; рендеры изолированы в Worker с таймаутом и
отменой.

**Причина.** MicroVM/gVisor защищают от исполнения произвольного кода, которого
здесь нет. Уровень изоляции, соответствующий реальной модели угроз, —
командная шина сallowlist и валидацией.

### D-035. `.duck(n)` — это алиас `.duckorbit(n)`, а не отдельный эффект

**Контекст.** Рисерч утверждал: «`.duck()` — сам эффект приглушения,
`.duckorbit()` — определяет, на какую орбиту влияет». В @strudel/web 1.3.0
в бандле это `duck: mm = A("duckorbit", "duck")` — оба метода пишут **одно**
поле `duckorbit`.

**Решение.** Компилятор не генерирует `.duck(...)` как отдельный эффект. Роль
дакинга описывается тройкой: `.duckorbit(N)` (жертва), `.duckonset(t)` (момент
начала), `.duckattack(s)`, `.duckdepth(d)`. Орбита-жертва должна существовать
(партия-жертва обязана иметь `.orbit(N)`), иначе движок пишет
`duck target orbit N does not exist` и дакинга не будет.

**Причина.** Ошибка в понимании API дала бы «тихо сломанный» микс: дакинг
просто не случился бы, и приёмка по метрикам это показала бы не сразу.
Зафиксировано контрактным тестом «`.duck(n)` — алиас `.duckorbit(n)`».

### D-036. Список имён сэмплов вендорен и сверяется с банками

**Контекст.** Браузерный спайк показал: из 44 имён палитры проекта в банках
есть 42. Отсутствуют `oh` и `sh` — а именно эти имена были разрешены в
`server/prompts/system.md` и `server/prompts/critic.md`. Сэмпл, которого нет в
манифесте, молчит: партия исчезает без ошибки, и это слышно только на слух.

**Решение.** Манифесты банков вендорены в
`server/music/data/sample-banks.json` (218 имён dirt-samples + piano).
`tests/unit/sample-names.test.js` сверяет имена, разрешённые в промптах, с этим
списком и падает, если появилось имя без сэмпла. Обновление списка —
`npm run sync:samples` (сеть нужна только там, в CI используется вендоренный файл).
Заодно `DRUM_NAMES` в `server/music/extract.js` приведён к реальности:
`clap/rim/tom/cowbell/oh/sh` заменены на `cp/rm/odx/cb/ho`.

**Причина.** Список имён жил в тексте промпта и молча устаревал: банк сменился
— промпт об этом не знал, а модель генерировала несуществующие сэмплы. Теперь
расхождение ломает сборку, а не трек.

## Фаза 2 — аудиограф, DSP-core, мастер

### D-037. Bypass реализован внутри мастер-worklet, а не отдельной веткой графа

**Контекст.** §5 промта предлагает сухую ветку в графе: «dry-путь задержан на
величину `latencySamples`, сообщённую worklet; переключение — equal-power
кроссфейд 20–30 мс».

**Решение.** Сухая ветка живёт внутри того же worklet: `MasterChain` держит
собственную линию задержки длиной `lookahead` и кроссфейдит обработанный и
сухой сигналы по отсчётам (равная мощность, 25 мс).

**Причина.** У `AudioWorkletNode` есть собственная задержка в один рендер-квант
(128 отсчётов), о которой движок не сообщает. Нативная ветка на `DelayNode`
отстала бы от обработанной ровно на квант — A/B разъезжался бы по времени на
2.7 мс. Внутри worklet обе ветки проходят один конвейер, поэтому выравнивание
точное по построению, а не «подобрано».

**Чем проверено.** `tests/unit/audio-master.test.js`: после выхода в bypass
остаток между выходом и входом, сдвинутым на `lookahead`, < 1e-6; сдвиг по
кросс-корреляции = `latencySamples`; скачок на переходе не больше собственных
скачков сигнала.

### D-038. Фильтр true peak — как в libebur128, а не «идеальная реконструкция»

**Контекст.** D-029 выбрал фильтр на 97 отсчётов с окном Кайзера, сверяя его с
ffmpeg. Оказалось, сверка была с неверным полем: в выводе `ebur128` true peak
брался из покадрового `FTPK`, который на самом деле пара «текущее/максимум»,
а для файла с переходным в начале показывает уровень в конце, а не пик файла.
Правильное поле — «True peak: Peak: …» из блока Summary.

**Решение.** True peak считается по алгоритму libebur128 (49 отсчётов, окно
Ханнинга, передискретизация 4×) — это эталон EBU R 128. Сверка ведётся с
буквальной транскрипцией референса (`scripts/libebur128-reference.mjs`),
расхождение ≤ 0.001 дБ.

**Причина.** ffmpeg измеряет true peak не фильтром приложения 2 стандарта, а
ресемплером libswresample (до 192 кГц, `f_ebur128.c`). У ресемплера своя АЧХ:
на широкополосных синтетических сигналах он завышает пик до +0.7 дБ. Свой
фильтр с другой АЧХ дал бы цифру, не сопоставимую ни со стандартом, ни со
стриминговыми платформами.

**Чем проверено.** `npm run validate:loudness` — |ΔLUFS| ≤ 0.05 против ffmpeg,
|ΔdBTP| = 0.00 против libebur128 на 6 фикстурах; `npm run validate:master` —
то же на 5 фикстурах мастер-цепочки.

**Риск отката.** D-029 в части выбора фильтра отменяется: сверка с ffmpeg по
true peak информационная, критерий приёмки — совпадение с libebur128.

### D-039. Распределение ролей: контекст и мастер у студии, движок — гость

**Контекст.** §5 промта: «владение графом у студии, а не у движка».

**Решение.** `src/audio/graph.js` владеет `AudioContext`, мастер-шиной и
метрами; `src/audio/engine/adapter.js` — единственное место, где студия касается
движка. Точка врезки — хук H1: `destinationGain` движка отключается от
`ctx.destination` и подключается к `masterIn` студии.

**Причина.** `initStrudel({audioContext})` сажает и планировщик, и контроллер
superdough в контекст студии, поэтому движок играет в нашей шине, а не в
своей. Если worklet не загрузился — движок подключается прямо к выходу, и в
консоль пишется «мастер-цепочка недоступна»: приложение остаётся рабочим, но
не притворяется, что мастер включён.

**Чем проверено.** `tests/spike/browser/master-live-spike.mjs` (браузер):
задержка 240 отсчётов (5 мс), сквозная 55 мс (10 base + 40 output + 5 мастер),
пик на выходе ровно −1.000 dBFS, в bypass метры продолжают идти и сигнал
становится на 9 дБ громче.

### D-040. Worklet собирается esbuild'ом из того же DSP-ядра

**Контекст.** AudioWorklet не поддерживает `import`: файл worklet'а должен быть
самодостаточным. Копия DSP в worklet'е — это две реализации, которые разойдутся.

**Решение.** `src/audio/worklet/master-processor.js` импортирует `src/audio/dsp/*`
и собирается esbuild'ом в `public/worklets/master-processor.js`
(`npm run build:worklet`, автозапуск в `prebuild`/`predev`). Сборка
детерминирована: при неизменных исходниках файл не переписывается.

**Причина.** Один DSP-core на реалтайм, офлайн-рендер и CI — иначе метрики в
реалтайме и в отчётах считаются разными числами.

**Чем проверено.** `tests/unit/audio-master.test.js` запускает **собранный**
worklet в Node (с подделкой области AudioWorklet) и сверяет его выход с ядром:
максимальное расхождение < 1e-5 (разница только от float32).

### D-041. Потолок лимитера держится по sample peak; true peak может быть выше на ~0.1 дБ

**Контекст.** Приёмка требует потолок −1 dBTP, а лимитер ограничивает
мгновенный отсчёт.

**Решение.** Пока потолок держится по sample peak: в браузере на стресс-паттерне
пик на выходе ровно −1.000 dBFS, true peak −0.93 dBTP.

**Причина.** Лимитер с предпрослушиванием по отсчётам не видит межотсчётовый
пик реконструкции. Разница ~0.1 дБ меньше коридора приёмки, но формально
«−1 dBTP» не выполнено.

**Чем проверено.** `tests/spike/browser/master-live-spike.mjs`: true peak
−0.927 dBTP при потолке −1 dBFS; в bypass тот же паттерн даёт +3.17 dBFS.

**Когда.** Фаза 4 (autoMix и приёмка): потолок по true peak — либо лимитер
считает передискретизованный пик, либо потолок опускается до −1.2 dBFS.

### D-042. Аудио-блок в скоре: 20%, переключаемый, отчёт приходит из браузера

**Контекст.** §7 промта: «аудио-блок входит в скор (вес 20%, переключаемо)».
Аудио на сервере нет — рендер живёт в `AudioContext` браузера.

**Решение.** Отчёт рендера (MetricsReport) приходит в запрос
`POST /api/music/compose` полем `audioReport`. Сервер проверяет **только форму**
(`MetricsReportSchema`), числа не проверяет: их считает браузер тем же
DSP-ядром, что звучит в реалтайме. Битый отчёт не ломает композицию — аудио-блок
не участвует, причина отклонения возвращается в событии `scored` полем
`audioRejected`. Флаг `useAudio: false` выключает блок.

**Причина.** Проверить числа на сервере нечем, а отказываться от объективной
оценки звучания — значит оценивать трек только на глаз. Происхождение чисел
явно: паспорт `engineVersion` и `renderMode` внутри отчёта.

**Чем проверено.** `tests/unit/audio-score.test.js` — отчёт попадает в скор,
битый отчёт не ломает поток, флаг выключает блок.

**Риск отката.** Клиент может прислать заведомо неверные числа. Для приёмки
это не опасно: приёмка считается по отчёту, который делает браузер, и
дублируется на клиенте (шаг 3 — человек слушает и решает).

### D-043. «Повторяемость не измерена» ≠ «повторяемость есть»

**Контекст.** §5 промта: autoMix и приёмка работают только при
`repeatability.passed`. Отчёт с одним рендером ничего не доказывает.

**Решение.** `repeatability` заполняется только после двух рендеров. При одном
рендере — `null`, и QA выдаёт предупреждение `repeatability-unknown`;
аудио-блок скора при этом **не засчитывает** балл за повторяемость (25 из 100).

**Причина.** Иначе трек с одним рендером получил бы полный балл за то, что не
измерялось. «Неизвестно» не должно выглядеть как «хорошо».

**Чем проверено.** `tests/unit/audio-render.test.js`: один прогон →
`repeatability = null` и предупреждение; два прогона детерминированного рендера
→ `passed = true`, расхождение 0; шумящий рендер → `passed = false` и ошибка QA.

**Риск отката.** Скор трека с одним рендером систематически ниже. Это осознанно:
в студии рендер всегда делается двумя прогонами (кнопка «Анализ»).

### D-044. Офлайн-рендер пересоздаёт контроллер superdough — живой трек возвращается

**Контекст.** H3: официальный `renderPatternAudio` закрывает живой
`AudioContext`, поэтому рендер делается в отдельном `OfflineAudioContext`.

**Решение.** Свой рендер: код → паттерн (`patternFromCode`, без звука) →
события → `OfflineAudioContext`. После рендера контроллер superdough
пересоздаётся, поэтому адаптер заново врезает хвост движка в мастер-шину
студии, а движок возвращает живой трек повторной оценкой кода. Рендер — это
действие по кнопке, а не фоновая задача.

**Причина.** Один контекст на всё — иначе либо рендер ломает звук, либо звук
ломает рендер. Пересоздание контроллера — цена офлайн-контекста, и она
явно описана в коде.

**Чем проверено.** `npm run spike:offline` — рендер двух тактов в браузере,
затем проверка, что живой контекст жив и код исполняется.

**Риск отката.** Если superdough изменит порядок инициализации, восстановление
не сработает — тогда рендер придётся делать в отдельном окне. Контрактный
тест движка (`tests/unit/engine-contract.test.js`) ломает сборку при смене
версии пакета.

### D-045. Соло-рендеры партий отложены до фазы 4

**Контекст.** §7 промта требует соло-рендеры партий, чтобы понимать, кто
именно громкий.

**Решение.** Модуль рендера (`src/audio/render/offline.js`) поддерживает
`parts` и `partId`, но движок пока фильтрует события по всей партии: в коде
нет разметки партий (id контроллера), по которой можно отфильтровать hap'ы.
Разметка появится вместе с палитрой и правилами микса в фазе 4.

**Причина.** Выдавать за соло-рендер партии полный микс — это ложные числа в
отчёте; честнее не выдавать их вовсе.

**Чем проверено.** `tests/unit/audio-render.test.js` — приём с `parts`
заполняет метрики партий; в браузере соло пока не проверяется.

**Риск отката.** Замечания «партия слишком громкая» до фазы 4 не появятся:
их приёмка опирается на `parts`.


### D-046. Composition IR: план вместо кода

**Контекст.** LLM-путь пишет Strudel-код. Код непрозрачен, «сделай мрачнее»
требует перегенерации, а выход модели нельзя безопасно исполнять.

**Решение.** Введён Composition IR (`src/ir/schema.js`) — Zod-схема типизированного
плана: настроение, форма, гармония римскими цифрами, мотивы, грув, палитра,
регистры ролей. Компилятор (`src/ir/compiler.js`) — чистая функция IR→код.
Правки — типизированные трансформации IR (`src/ir/transforms.js`), каждая
возвращает новый IR и объявляет ожидаемый знак изменения метрик.

**Причина.** Только план позволяет измерить правку, получить соло-стемы
бесплатно и не пускать текст модели в исполнение.

**Чем проверено.** 167 тестов (`tests/unit/ir-*.test.js`): схема, намерение,
гармония, грув, компилятор (fuzz на 300 случайных IR + исполнение в движке),
трансформации. Побайтная детерминированность компиляции.

### D-047. Символьный оракул двухслойный: быстрый из IR и точный из движка

**Контекст.** Рендер стоит секунды, перебрать сотню кандидатов нельзя. Бриф §6
требует «≤50 мс на 32 такта, ≥200 кандидатов/с».

**Решение.** Два слоя. Быстрый (`src/oracle/ir-events.js`) считает события
прямо из IR, используя те же `grooveSteps`, `buildChordPlan`, `motifToMini`,
`roleLevel`, что и компилятор. Точный (`server/music/strudel-runtime.mjs`) —
`queryArc` движка, для финалистов.

**Причина.** Измерено: `queryArc` даёт 11 кандидатов/с, быстрый слой — 45…600.
Поиск по кандидатам возможен только на быстром слое.

**Чем проверено.** `tests/spike/oracle-timing.probe.mjs` (экономика) и
`tests/unit/oracle-consistency.test.js` (расхождение слоёв ломает тест).

### D-048. Граница точности быстрого оракула: ритм точен, вокальный алгоритм — нет

**Контекст.** Движок раскладывает аккорд по голосам своим алгоритмом. Воспроизвести
его в оракуле — отдельная задача, а для метрик (движение корней, напряжение,
регистр) она не нужна.

**Решение.** Быстрый оракул воспроизводит ритмический скелет точно (все атаки,
длительности, числа событий) и высоты ударных, баса, лида и арп. Высоты
аккордов — каноническое сомкнутое расположение от якоря. Граница объявлена в
шапке `src/oracle/ir-events.js` и в `docs/ORACLE.md`.

**Причина.** Честная граница лучше незаметной неточности: сверка атак
остаётся строгой, а расхождение по голосам не маскируется под «примерно
так же».

**Чем проверено.** Тест сверяет по числу событий и таймингам атак; для аккордов
сравниваются атаки, а не высоты.

### D-049. PRNG: FNV-1a + финализатор fmix32

**Контекст.** PRNG проекта — адресный, от `(seed, секция, роль, шаг)`. Он
использовался для отсева шагов по плотности и для выбора нот мотива.

**Решение.** К FNV-1a добавлен финализатор `fmix32` (MurmurHash3) —
avalanche-шаг. Тот же финализатор применён к отсеву шагов в `groove.js`.

**Причина.** Измерено: у «голого» FNV-1a старшие биты почти не смешиваются,
распределение получалось рваным (46 % значений в одном десятом интервала,
среднее 0.68 вместо 0.5). Для отбора нот и отсева шагов это означало
систематический перекос, а не случайность.

**Чем проверено.** `tests/spike/prng-distribution.probe.mjs`: после фиксатора
гистограмма по десятым интервалам — 9.9…10.1 %.

### D-050. Свинг и микротайминг считает компилятор, а не движок; бюджет ±20 мс

**Контекст.** Карта groove-templates требует свинга и микротайминга. Штатные
средства движка не подходят: `swingBy(x, n)` в @strudel/web 1.3.0 дублирует
события (16 хэтов → 24), `swing(x)` без второго аргумента — no-op, а `.gain()`
по событию ломает привязку внутри `.beat()` со списком шагов.

**Решение.** Шаблоны грува задают сдвиг в миллисекундах; компилятор раскладывает
шаги по группам «динамика + сдвиг» и кладёт сдвиг через `.late(ms(x))`.
Суммарный сдвиг ограничен **±20 мс на любом темпе**.

**Причина.** Свой путь детерминирован, прозрачен для аудита и не зависит от
недокументированного поведения движка. Ограничение ±20 мс — из карты
грув-шаблонов; на 80 BPM свинг 8-х сам по себе даёт 45 мс и упирается в
бюджет (20 мс на медленном темпе и есть правильный лоуфай-свинг).

**Чем проверено.** `tests/unit/ir-groove.test.js`: сдвиги укладываются в
±20 мс для всех шаблонов на темпах 70…200.

### D-051. Пороги линтера зависят от жанра

**Контекст.** Единые пороги North Star (плотность ≤20/с, связка бас–кик ≥0.6)
применялись ко всем жанрам.

**Решение.** Пороги вынесены в `GENRE_THRESHOLDS` (`src/oracle/lint.js`):
плотность для D&B — 40/с, для эмбиента — 10/с; связка бас–кик не проверяется
в синтипопе (оффбитный бас там и есть жанр).

**Причина.** Измерено: D&B даёт 33.6 события/с, и это норма, а не «каша»;
в синтипопе бас оффбитный по определению, и «рассинхрон» — ложное
срабатывание. Единый порог врал бы на каждом жанре.

**Чем проверено.** `tests/unit/oracle-lint.test.js`: на пяти здоровых треках
ошибок линтера нет.

### D-052. Регистр роли honored компилятором

**Контекст.** Поле `layer.register` было описано в схеме, но компилятор его
игнорировал: бас всегда играл `rootNotes(2)`, а мотив — без сдвига октавы.
Из-за этого трансформация `shiftRegister` меняла IR, но не меняла звук.

**Решение.** Октава баса берётся из `layer.register[0]`, мотив сдвигается на
октаву оттуда же (степени лада — индексы, октава = ±7 индексов).

**Причина.** Трансформация, которая не меняет звук, — ложь в интерфейсе.
Дефект найден mutation-тестом линтера.

**Чем проверено.** `tests/unit/oracle-lint.test.js` (дефект «бас в середине»
стал находиться) и `tests/unit/oracle-consistency.test.js` (сверка с движком).

### D-053. В матрицу ролей добавлен снейр

**Контекст.** `ROLE_MATRIX` не содержал снейра, поэтому ни один трек,
собранный планировщиком, не имел акцента на 2 и 4 долю — бэкбита.

**Решение.** Снейр добавлен во все секции, где есть ударные, с весами по
матрице ролей.

**Причина.** Трек без бэкбита не имеет пульса. Это было видно и по
символьному разбору: связка бас–кик падала из-за отсутствия снейра.

**Чем проверено.** `tests/unit/ir-compiler.test.js`: партия SNARE присутствует
в скомпилированном коде и стоит на шагах 4 и 12 сетки 1/16.

### D-054. Символьный скор — гипотеза, а не цель оптимизации

**Контекст.** Скор нужен, чтобы выбирать кандидатов. Но скор, оптимизируемый
без проверки на людях, — классический Goodhart: метрику начинают обманывать.

**Решение.** Скор помечен `validated: false` и сопровождается замечанием в
отчёте. Веса составляющих видны пользователю. Канарейки (пять подлых треков)
обязаны набирать строго меньше медианы корпуса, иначе эволюция скилов и
Taste Model блокируются. Поиск по мутациям честно назван фильтром дефектов:
на зрелом треке он ничего не улучшает (измерено, E-005).

**Причина.** Проект не имеет ни одной человеческой пары. Утверждать «микс
стал лучше» на основании символьного скора — выдумка.

**Чем проверено.** `tests/unit/oracle-lint.test.js`: проверка канарейк;
`docs/EXPERIMENTS.md`, E-005 — нулевой результат зафиксирован, а не сокрыт.

### D-055. Скил-пак — источник правил для LLM-планировщика

**Контекст.** Карты скил-пака были написаны, но планировщик на тексте (`planIR`)
работал по правилам, зашитым в код. Получалось два источника правды: карты
говорили одно, код — другое, и никто их не сверял.

**Решение.** Учебник (сборка COMPACT-блоков карт под конкретный запрос) —
единственный источник правил для модели. Правила из карт попадают в системный
промт планировщика; код их не дублирует. Версия пака (`skillsVersion` =
sha256 от frontmatter + COMPACT всех карт) входит в ключ кэша планировщика и в
ответ API: без неё результат невоспроизводим — правила могут поменяться.

**Почему.** «LLM решает что, код решает как» работает только если у LLM есть
правила. Карты — это и есть правила в машиночитаемом виде; без них модель
описывает музыку словами, а мы переводим их в код сами, то есть возвращаемся
к проблеме промтов.

**Последствия.** Появился `check:skills` — гейт, который ломает сборку, если
карта разошлась с кодом или её тело изменилось без bump версии. Карты больше
нельзя править «на глаз»: правка без версии падает в CI.

**Чем проверено.** `tests/unit/skills.test.js` — матрица активации из
`skills/INDEX.md` сверяется с кодом; `tests/unit/skills-planner.test.js` —
в промт уходит учебник, а не пустая строка.

### D-056. «<...>» в n()/note() — один элемент за цикл, а не шаги внутри такта

**Контекст.** В картах жанра мелодии были записаны как `n("<4 ~ 2 ~ 5 ~ 3 ~>")`.
Измерено в headless-рантайме Strudel: `n("0 2 4")` даёт 3 события за цикл,
`n("<0 2 4>")` — **1** событие за цикл. Угловые скобки в mini-нотации — это
«один элемент за цикл», а не последовательность шагов.

**Решение.** Шаги внутри такта пишутся без угловых скобок. Прогрессии
(`chord("<Am F C G>")`), маски (`mask("<1!15 0>")`) и панорамы
(`pan("<.4 .6>")`) остаются как есть: там один элемент за цикл нужен. В
линтер примеров добавлено правило `angle-sequence-in-note`; отказ от него —
явный комментарий `one-per-cycle` в коде.

**Почему.** Ошибка тихая: код исполняется, ошибок нет, музыка играет — но
по одной ноте на такт вместо ритмической фигуры, а с `degradeBy(.3)` голос
мог замолчать целиком. Это ровно тот класс дефектов, который ловит CI, а не
слух.

**Чем проверено.** `tests/spike/skills-example-shape.probe.mjs` — сама
семантика; `tests/unit/skills.test.js` — правило линтера; правки в карках
`genre-trip-hop`, `genre-lofi`, `composer-workflow`.

### D-057. Матрица активации — исполняемое правило, а не текст

**Контекст.** `skills/INDEX.md` содержал таблицу «промт → ожидаемые карты»,
которая ни с чем не сверялась. При первой же сверке с кодом разошлись три
строки.

**Решение.** Матрица разбирается тестом и сверяется с кодом: жанр — по
`resolveGenre`, настроение — по словарю emotion-map, грув и арка — из карты
жанра. Расхождение падает в тесте, а не всплывает через полгода.

**Что пришлось решить по существу.**
* «мрачный трип-хоп про дождь» — карта и словарь дают `melancholy`
  («последнее слово доминирует»), матрица ждала `dark`. Оставлено по
  правилу карты; матрица приведена в соответствие.
* «уютный лоуфай для учёбы» — словарь не знал падежа «учёбы», поэтому
  настроение читалось как `tender` вместо `nostalgia`. Словарь дополнен
  (`учёба/учёбы/учеба/учебы`), карта поднята до 1.0.1.
* «светлый синтипоп для вечеринки» — «светл» и «вечерин» добавлены в `joy`.
* Условная арка «(или club-64 для «фестиваля»)» **никогда не срабатывала**:
  в карте точка после скобки, а слово-триггер стоит в родительном падеже
  («фестиваля» против «фестиваль» в запросе). Теперь триггер сравнивается по
  основе, и «эйфоричный фестиваль» действительно получает club-64.
* Грув трип-хопа в матрице был `laid-back`, а карта объявляет `drunken`;
  `laid-back` — грув другой карты. Матрица исправлена.

**Почему.** Документация, которую не читает код, вредна: она обещает
проверяемое и не проверяет.

### D-058. Theory-lint для примеров карт — подмножество, и это зафиксировано

**Контекст.** Спека требует «dry-parse + theory-lint v1 (0 errors)» для
каждого примера карты. Полный линтер оракула (`src/oracle/lint.js`) работает
по IR, а примеры карт — это сырой Strudel-код.

**Решение.** Для примеров применяется подмножество, которое исполняется
по-настоящему: dry-parse в headless-Strudel (синтаксис, имена контролов,
mini-нотация), запрещённые конструкции, guardrails (delayfeedback < 1,
gain ≤ 1.2, duckdepth ≤ 1, |микротайминг| ≤ 20 мс), соответствие нот ладу и
ловушка «<...>». Полный theory-lint (параллельные квинты, коллизии регистров)
включается на этапе компиляции IR, где он и живёт.

**Почему.** Лучше меньше проверок, которые действительно исполняются, чем
список правил, который никто не запускал. Подмножество названо прямо, чтобы
его не выдали за полный линт.

**Долг.** Полный линт по сырому коду — отдельная задача (нужен обратный
перевод кода в IR).

### D-059. Baseline-0 заморожен; аудио-часть — честный долг

**Контекст.** Пока не зафиксировано, с чем сравнивать, любое «стало лучше» —
мнение. Спринт S0.2 требует корпус из 60 промтов с разбивкой и заморозкой.

**Решение.** `corpus/baseline0/`: 60 промтов (4 квадранта × 5 жанров ×
3 плотности), сплит 36/12/12 детерминированно по sha256 id, для каждого
промта — план по правилам, скомпилированный код, IR-хэш, code-хэш и
символьный разбор. Манифест подписывает sha256 обоих файлов; `npm run
check:baseline` в CI ломает сборку при любой правке корпуса.

**Почему.** Заморозка — это и есть Baseline-0: не «эталонные примеры», а
слепок системы на момент заморозки, с которым можно сравнивать честно.

**Долг.** Аудио-часть Baseline-0 (WAV + MetricsReport + renderFingerprint) не
собрана: рендер требует браузера, а в CI это 60 офлайн-рендеров. Планируется
отдельным прогоном (`npm run spike:offline` уже умеет рендерить). До этого
Baseline-0 — это код и символьный разбор, а не звук.

### D-060. Дорожка H: пары строятся на правилах против мутации

**Контекст.** Метки — узкое место проекта: без них нельзя проверить
символьный скор, обучить Taste Model и честно сказать «стало лучше».

**Решение.** Очередь пар — детерминированная: A — план по правилам, B —
мутация того же плана; стороны переставлены по хэшу индекса, каждая десятая
пара — повтор с переставленными сторонами (измеряет надёжность рецензента).
Страница `/tinder.html` рендерит оба варианта в браузере тем же движком,
выравнивает громкость **только гейном** (без лимитера) и переставляет треки
по каналам случайно. Метки пишутся в JSONL без PII; экспорт — NDJSON
chosen/rejected, удаление — одной командой.

**Важная деталь.** Мутация не всегда меняет план: у эмбиента нет ударных, а
мутация плотности бьёт по ударным — получалась пара «сам с собой», то есть
фиктивное сравнение. Поэтому кандидаты перебираются, пока коды не разойдутся;
если не разошлись ни одна мутация — берётся другой план того же промта.

**Почему.** «Пара» из двух одинаковых треков даёт рецензенту ложную метку:
он вроде бы выбрал, а на самом деле сравнивал одно с тем же.

**Долг.** Активный отбор пар (где модель неуверена) отложен: очередка v0 идёт
по порядку. Публичная ссылка для друзей-рецензентов — только с разрешения
владельца (rate-limit, без PII).

### D-061. Механика ответа модели чинится кодом, а не моделью

**Контекст.** Первый же живой прогон планировщика (14.11.2026, боевой сервер,
OpenAI) показал: модель отвечает, но её план не проходит Zod — система молча
уходила в правила. Причина измерена по живому ответу, а не предположена:

```
layers.texture.plan: Invalid enum value.
  Expected 'drums' | 'bassline' | …, received 'тихий виниловый шум и тёмная атмосфера'
```

Модель трактует поле `plan` как «описание партии» и пишет туда естественный
язык. Восемь слоёв из восьми были такими.

**Решение.** Три вещи, каждая по своему основанию.

1. **Детерминированная починка** (`server/ir/normalize.js`): `plan` берётся по
   роли (`planForRole`), выдуманные роли выбрасываются, недостающий регистр
   ставится по роли, числа вне диапазона обрезаются, «IV/3» → «IV». Каждая
   правка записывается в `notes` — видно, что именно изменилось.
2. **Живой ремонтный ретрай**: в промпт повтора попадают прошлый ответ модели
   и список конкретных ошибок Zod. До этого повтор был повтором того же
   запроса — модель физически не могла узнать, что не так, и второй ответ
   был тем же.
3. **Явный контракт**: в краткой схеме enum-поля описаны словами
   («ОДНО слово из списка, а НЕ описание»).

**Почему именно так.** Это и есть принцип брифа: «LLM решает что, код решает
как». Тип партии — это механика, а не музыкальное намерение: модель сказала
«педальный слой, тихий», код решил, что это `pad`. Спорить с моделью о типе
партии — бессмысленная трата вызовов; спорить о гармонии или энергии — нужное
дело.

**Чем проверено.** `tests/unit/ir-normalize.test.js` — тесты построены на
реальном ответе модели; `tests/unit/skills-planner.test.js` — ретрай несёт
ошибку, починка закрывает класс ошибок без повторного вызова.

**Честная оговорка.** Починка чинит форму, а не вкус: если модель сказала
«три секции по одной ноте» — это останется «тремя секциями по одной ноте».
Качество плана на живых прогонах пока не измерено человеком.

### D-062. Dockerfile копирует скил-карты: /api/skills иначе даёт 500

**Контекст.** После первого деплоя этой сессии `/api/health` был зелёным, а
`/api/skills` отдавал 500 с ENOENT: `scandir '/app/skills'`. Причина:
`.dockerignore` исключает `corpus`, `docs`, `tests`, а Dockerfile копировал в
образ только `dist`, `server`, `src`, `scripts` — каталог `skills/` в образ
не попадал.

**Решение.** `COPY skills ./skills` в Dockerfile. Плюс: отсутствие каталога
карт теперь проверяется гейтом `check:skills` (он читает карты с диска), а
деплой проверяет `/api/skills`, а не только `/api/health`.

**Почему это отдельное решение.** Зелёный `/api/health` доказывает, что
процесс жив, но не что все маршруты работают: ошибка чтения файлов возникает
внутри обработчика. Смоук деплоя расширен: после деплоя проверяются и
`/api/skills`, и `/api/preference/queue`, и `/tinder.html`.

### D-063. Метрики и веса скора живут в одном реестре

**Контекст.** Символьные веса скора жили в `src/oracle/score.js`, критерии
аудио-блока — в `server/music/compose/audio-score.js`, формула смешивания
v1/v2/аудио — там же, а третий набор весов (критерии v2) — в
`server/music/score-v2.js`. Плюс в комментарии аудио-блока была написана
формула `v1·0.5 + v2·0.3 + аудио·0.2`, которой в коде не было: код считал
`v1·0.48 + v2·0.32 + аудио·0.2`. То есть и веса, и их описание расходились
между собой.

Бриф §2.8 требует, чтобы «ни одна метрика не становилась целью оптимизации,
пока она не проверена против человеческих суждений». С тремя разбросанными
наборами весов это требование невыполнимо: у веса не было места, где можно
поставить «не проверено».

**Решение.** `src/metrics/registry.js` — единственный источник:

* 43 метрики: `id`, `label`, `unit`, `range`, `target`, `source`, `version`;
* критерии символьного скора (`SCORE_CRITERIA`), критерии аудио-блока
  (`AUDIO_SCORE_CRITERIA`), веса блоков (`SCORE_COMBINE`) — с явным полем
  `validated: false`;
* `src/metrics/extract.js` — единственное место, где отчёт превращается в
  числа по id (чтобы объявление и измерение не разъезжались).

Потребители переведены на реестр: `src/oracle/score.js` и
`server/music/compose/audio-score.js`. Числа не изменились — формула
смешивания зафиксирована тестом, комментарий приведён в соответствие с
кодом.

**Почему так.** Реестр — это не «бумага ради бумаги», а цена ответа на
вопрос «какой вес чем проверяется». Без общего места любой вес выглядит
одинаково доверенным, а это прямой путь к Goodhart.

**Проверка.** `npm run check:taste` требует: id уникальны, покрытие
экстракторами 100 %, суммы весов 100/100/1. Тест
`tests/unit/taste.test.js` сверяет, что веса в отчёте совпадают с
реестром, а формула смешивания даёт прежние числа (72 / 80 / 77.6).

**Остаётся.** `validated: false` у всех весов — до допуска Taste Model.

### D-064. Пара рождается вместе со своими признаками

**Контекст.** Дорожка H работала: человек слушал пары, выбирал победителя,
метка писалась в `preferences.jsonl`. Но метка содержала только хэши двух
треков — «победил вот этот». Обучение на таких данных невозможно в принципе:
нечем сравнивать победителя с проигравшим. Taste Model из брифа §7.4 была
невозможна не из-за нехватки данных, а из-за нехватки способа их
использовать.

**Решение.** Реестр пар `server/data/pairs.jsonl`. Пара кладётся в реестр в
момент создания вместе с **IR обеих сторон**, а не только с хэшами кода.
Отсюда:

* признаки пересчитываются из IR при обучении → смена состава признаков не
  убивает старые пары;
* аудио-признаки (L0) приходят с меткой из браузера: страница «Тиндер»
  меряет обе стороны тем же DSP-ядром, что и студия (LUFS, true peak,
  crest, клиппинг), и отправляет их вместе с выбором.

Хранение: `server/preference/ledger.js`. Маршрут `server/routes/preference.js`
стал тонким слоем над хранилищем (было 320 строк логики вперемешку с HTTP).

**Почему так.** Разделение «как хранится» и «как отдаётся по HTTP» нужно
было не для красоты: обучение (`server/taste/*`) читает те же данные из
того же места. Второй формат — это второй источник правды, а значит
источник расхождений.

**Проверка.** `tests/unit/taste-http.test.js` — сквозной путь: очередь →
пара с IR → метка с аудио → обучающий вектор признаков.

**Остаётся.** Прокси-пары (best-of-N) помечены `source: 'proxy'` и весят
≤ 0.2; в вердикт о допуске они не входят.

### D-065. Выученная цель допускается в скор только после leave-prompt-out CV

**Контекст.** Обучить модель можно на чём угодно; вопрос в том, можно ли
ей доверять. Бриф §7.4: в Score допускается только при CV-accuracy ≥ 60 % и
выше базовых линий («всегда-громче», текущий символьный скор) с 95 % CI,
и не используется при < 60 парах.

**Решение.** `src/taste/cv.js`:

* проверка — **leave-prompt-out**: целый промт уходит в тест, потому что
  пары одного промта не независимы (бриф §7.2), и обычная случайная
  разбивка дала бы модели подсказку;
* базовые линии обязательны и считаются на тех же парах;
* интервал — Уилсона (не нормальный: на малых n тот даёт неправдоподобные
  границы);
* вердикт объясняется словами: `reasons[]` — почему не допущено.

Пока допуска нет, веса символьного скора продолжают работать как есть, с
пометкой «не проверено на людях». Модель при этом обучается и сохраняется —
чтобы её можно было посмотреть глазами.

**Почему так.** Хорошая модель с плохой проверкой хуже, чем её отсутствие:
она молча уводит оптимизацию в сторону, проверенную ровно ноль раз.

**Проверка.** `npm run check:taste` — 20 проверок, включая «без живых пар
модель не допускается» и «при 40 парах не допускается».

**Остаётся.** На 14.11.2026 живых пар 0 → модель не допущена, вердикт
записан в `docs/evidence/taste/gate.json` и `docs/TASTE.md`.

### D-066. Данные меток изолированы каталогом STRUDEL_DATA_DIR

**Контекст.** Тесты дорожки H писали в настоящий
`server/data/preferences.jsonl`: файл сохранялся, стирался и
восстанавливался. Пока это работало, оно означало, что прогон тестов
рискует уничтожить метки владельца (при падении теста файл остаётся
удалённым), а параллельные тестовые файлы мешают друг другу: один стирает
файл, который только что записал другой.

**Решение.** Каталог данных переопределяется переменной окружения
`STRUDEL_DATA_DIR` (`server/preference/ledger.js` → `dataDir()`). Тесты
поднимают свой временный каталог. Значение по умолчанию — прежний
`server/data`.

**Почему так.** Метки — главный дефицит проекта. Делать так, чтобы
автоматический прогон тестов мог их потерять, — недопустимо.

**Проверка.** `tests/unit/preference.test.js` и `tests/unit/taste*.test.js`
работают во временных каталогах; `npm test` не трогает `server/data`.

**Остаётся.** Файлы `server/data/*.jsonl` и модель — вне git (см.
`.gitignore`).

### D-067. Сбойная мутация не должна рушить весь best-of-N

**Контекст.** `searchBest` защищал вызов оценки, но не вызов мутации.
Мутация `boostSection` выбирает секцию из `ir.sections`: если секций нет,
`pick` бросает исключение, и весь поиск падал целиком, а не выбывал один
кандидат.

**Решение.** Мутация обёрнута в `try/catch` (кандидат выбывает, остальные
оцениваются), а сама операция `boostSection` на пустом списке секций
возвращает описание вместо исключения.

**Почему так.** Поиск — рычаг «вычисления вместо надежды на удачный промт».
Один вырожденный план не должен отключать рычаг целиком.

**Проверка.** `tests/unit/taste.test.js` — прокси-пара строится из плана без
секций и не роняет выборку.
