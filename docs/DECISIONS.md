# Решения по ходу цикла

Формат записи: **контекст → решение → причина**. Решения приняты по результатам
spike (фаза 0) и проверяемого кода, а не по предположениям.

---

## Фаза 1 — библиотека знаний

### D-011. Гармония в библиотеке — только степени лада

**Контекст.** Прогрессии требовалось хранить «в степенях, а не символами».
Проверка показала, что символы аккордов в Strudel пишутся как `Am`/`Am7`,
через двоеточие не принимаются, а набор таких символов пришлось бы переводить
в парсер и обратно. Степени же всегда в ладу по построению.

**Решение.** Прогрессия хранит `mode` и `degrees` — индексы ступеней лада.
Трезвучие строится как степени `[d, d+2, d+4]`. Символов аккордов в
библиотеке нет.

**Причина.** Гарантия «всегда в ладу» без отдельной проверки + совместимость
с анализатором, который тоже считает по степеням.

---

### D-012. Переходы и автоматизация — функции над дескрипторами, а не строки

**Контекст.** Требовалось хранить рецепты переходов как функции
`(pattern, barsLen) → pattern`. Нужен общий язык между библиотекой и
компилятором: переход меняет ритм, фильтр и автоматизацию партии, и это
нельзя выразить строкой шаблона.

**Решение.** Введён дескриптор партии (`knowledge/descriptor.js`): источник
(`n`/`note`/`s`), mini-нотация, флаг `.scale()` и цепочка методов с
структурированными аргументами (число / строка / описание сигнала). Переходы
и кривые автоматизации — чистые функции над дескриптором.

**Причина.** Функцию можно проверить и скомбинировать; шаблон строки — нет.
Сигнал описан данными (`{signal, slow, range, direction}`), потому что
`range` для затухания идёт вниз, а для нарастания — вверх.

---

### D-013. Лады в библиотеке ограничены списком, который понимает Strudel

**Контекст.** `scale()` принимает только полные имена одним словом.
`c:maj`, `c:min`, `c:harmonicminor` дают **пустой результат** с ошибкой в
консоли — то есть тихо ломают музыку, а не сообщают об ошибке.

**Решение.** В библиотеке используются только `major`, `minor`, `dorian`,
`phrygian`, `lydian`, `mixolydian` (плюс `ionian`/`aeolian` как синонимы).
Имена `harmonicminor`, `majpent`, `minpent` из `MODES`
(`server/music/notes.js`) в генерируемый код не попадают.

**Причина.** Собственный `MODES` — внутренний формат анализатора; генерируемый
код живёт по правилам Strudel. Смешивать их нельзя.

---

### D-014. Мелодические роли в матрице — на синтезаторах, ударные — на сэмплах

**Контекст.** У роли `lead` в джазе стоял синтезатор `sax`, а `sax` —
это **сэмпл** из белого списка, а не синтезатор.

**Решение.** Поле `synth` содержит только зарегистрированные синтезаторы
(`sawtooth`, `square`, `triangle`, `sine`, `piano`, `supersaw`, `pulse`,
`fm`, `am`, `organ`). Поле `sounds` — только сэмплы. У ролей `fx`/`texture`
паттерны содержат хотя бы один удар: паттерн из одной тишины не даёт ни
одного события и партия молчит.

**Причина.** Проверка библиотеки гоняет каждый паттерн через настоящий
движок: ошибка такого рода ловится автоматически, а не на слух.

---

### D-015. Длина формы ограничена 96 тактами

**Контекст.** Три формы (`techno-form-long`, `house-form-long`,
`cinematic-form-long`) вышли за 96 тактов — при требовании «32–96 тактов».

**Решение.** Секции укорочены так, чтобы каждая форма укладывалась в
диапазон. Длина формы — не «сколько влезло», а осознанный выбор: трек
должен быть разомкнут по форме, а не просто длинным.

**Причина.** Ограничение из задания; проверяется тестом и `check:knowledge`.

---

## Фаза 0 — spike

### D-001. Источник истины для метрик — события Strudel, а не свой парсер

**Контекст.** Метрики v2 (энергия по тактам, гармонический ритм, новизна
секций, вариативность) требуют событий на горизонте 32–96 тактов. Свой
парсер mini-нотации `server/music/mini.js` разбирает 1–2 такта и не понимает
`arrange`, `stack`, `cat/slowcat`, `<…>/n`, `.slow/.fast`, `.mask`, `.struct`,
`.every`. Расхождение измерено на `<0 5 2 6>/2`: наш парсер — 1 событие,
Strudel — 4.

**Решение.** Новые метрики прогрессии (фаза 4) считаются по событиям
`queryArc` из headless-исполнения Strudel. Свой парсер остаётся для
«быстрых» проверок (есть ли партия, лад, темп) и не меняется.

**Причина.** Требование «ничего из синтаксиса Strudel не принимать на веру»
означает, что источник истины — сам движок. Свой парсер — это реконструкция,
и на сложных конструкциях она расходится с реальностью.

---

### D-002. Headless-исполнение — через UMD-бандл @strudel/web

**Контекст.** `import '@strudel/core'` в Node падает:
`does not provide an export named 'SalatRepl'` — `@strudel/core` импортирует
`SalatRepl` из `@kabelsalat/web`, у которого в `main` лежит UMD-бандл без
этого экспорта.

**Решение.** Загружать UMD-бандл `@strudel/web` через `new Function`
(server/music/strudel-runtime.mjs). Тот же приём, что уже применён в
`scripts/check-presets.mjs`.

**Причина.** Правка зависимостей или замена пакета — риск и лишняя работа;
рабочий путь уже проверен в репозитории. Производительности хватает: 64 такта
× 6 партий — 25 мс.

---

### D-003. Нужен `setStringParser(mini)` — без него строки не разбираются

**Контекст.** Без явной регистрации строкового парсера `n("0 5 2 6")` даёт
**одно** событие `"0 5 2 6"` вместо трёх нот. В браузере это делает
`initStrudel`; в Node вызываем явно при загрузке.

**Решение.** `loadStrudel()` всегда вызывает `api.setStringParser(api.mini)`.

**Причина.** Без этого любые метрики по высотам считались бы по мусору.
Находка зафиксирована тестом «БЕЗ setStringParser строка не разбирается».

---

### D-004. Метки `$PART:` разбираются транспилятором, а не присваиванием

**Контекст.** `$BASS: <expr>` — это помеченный оператор JavaScript
(LabeledStatement), который сам по себе ничего не присваивает. Настоящий
Strudel прогоняет код через транспилятор: `$BASS: expr` → `expr.p('$BASS')`,
а `Pattern.prototype.p` кладёт паттерн в реестр.

**Решение.** Headless-исполнение идёт по цепочке
`код → transpiler → output → eval в песочнице → реестр по меткам`.
В песочнице `Pattern.prototype.p` подменён на сборщик партий.

**Причина.** Иначе партии не собираются вовсе. Отдельная ценность: порядок
партий сохраняется, микшер и mute/solo продолжают работать.

---

### D-005. Гармония выражается степенями лада, а не символами аккордов

**Контекст.** `chord("Am").voicing()` работает, а `chord("A:min").voicing()` —
нет (`unknown chord "A,min"`). Формы `"I V vi | IV"` и `"0:ma"` для Strudel
не существуют. Степени лада всегда в ладу по построению.

**Решение.** В схеме v2 гармония — это **степени** (`degrees: [0, 5, 2, 6]`).
Символы аккордов в генерируемый код не попадают.

**Причина.** Требование задачи плюс совместимость с анализатором: степени
гарантируют попадание в лад, а символы аккордов при неверном формате дают
пустую секцию вместо ошибки — худший вид отказа.

---

### D-006. Отдельный whitelist ладов для генерируемого кода

**Контекст.** `scale()` принимает только полные имена одним словом:
`c:major`, `c:minor`, `c:dorian`, `c:phrygian`, `c:lydian`, `c:mixolydian`,
`c:ionian`, `c:aeolian`, `c:pentatonic`, `c:blues`, `c:chromatic`.
`c:maj`, `c:min`, `c:harmonicminor` дают **пустой результат** с ошибкой в
консоли — то есть тихо ломают музыку.

**Решение.** В компиляторе — свой список допустимых ладов
(`server/music/knowledge/`), не связанный с `MODES` в `server/music/notes.js`,
где использованы `harmonicminor`, `majpent`, `minpent` — эти имена в код не
попадают.

**Причина.** Наш `MODES` — внутренний формат анализатора; генерируемый код
живёт по правилам Strudel. Смешивать их нельзя.

---

### D-007. Аккорд длиной 2 такта — через `.slow(2)`, а не через `/2`

**Контекст.** `n("<0 5 2 6>/2")` даёт 8 событий с дубликатами (по два на
позицию), `n("<0 5 2 6>").slow(2)` — 4 события длиной 2 такта.

**Решение.** В рецептах баса и аккордов используется `.slow(n)` как метод.

**Причина.** `/2` внутри mini-нотации даёт задвоенные атаки — это ударит по
метрике плотности и по таймлайну секций.

---

### D-008. Метрика автоматизации считается по значениям событий

**Контекст.** `sine.slow(4).range(a, b)` сам по себе отдаёт константу (0.5) —
сигнал раскрывается только в контексте параметра паттерна. Регуляркой по
тексту статичное `.gain(0.5)` не отличить от автоматизации.

**Решение.** Доля автоматизированных параметров считается по значениям
событий: если параметр меняется от события к событию — он автоматизирован.

**Причина.** Требование задачи «считать токенайзером/AST, не regex-ом» плюс
фактическое поведение движка.

---

### D-009. Старый парсер и новые метрики живут рядом

**Контекст.** Скор v1 (10 критериев) работает на `analyzeTrack` → свой парсер.
Метрики v2 требуют событий на длинном горизонте.

**Решение.** Скор v2 добавляется к существующему как **дополнительный слой**:
критерии v1 сохраняются (масштабируются до ~60% веса), новые добавляются
(~40%). Старый парсер и `analyzeTrack` не трогаем.

**Причина.** Требование «сохрани 10 старых критериев» и «106 тестов должны
остаться зелёными». Метрики v1 остаются источником обратной связи для
существующего refine.

---

### D-010. `setCpm(bpm/4)` остаётся формой темпа

**Контекст.** В бандле нет отдельной функции `setCpm` (темп ставится через
`cpm`/`cps`), но синтаксис `setCpm(124/4)` — то, что пишет генератор, что
понимает браузер и что читает `getBpm()` в `src/core/code-model.js`.

**Решение.** Компилятор пишет `setCpm(<bpm>/4)`. В headless-песочнице `setCpm`
— заглушка: темп берётся из текста кода.

**Причина.** Транспилятор пропускает эту строку без ошибок, а менять формат
темпа значило бы ломать `getBpm()` и существующие пресеты.

---

### D-016. Рецепт партии выбирает рисунок по плотности, а не по имени

**Контекст.** В спеке у каждой партии есть поле `recipe`. Если его игнорировать,
модель отвечает за проект, а компилятор всё равно ставит один и тот же рисунок —
это ровно то «плоское», что ТЗ просит убрать.

**Решение.** Рецепт — это не идентификатор шаблона, а **плотность**:
`default` (обычная плотность роли), `busy` (плотнее), `sparse` (реже).
Компилятор меряет плотность каждого шаблона библиотеки (`patternDensity`,
атаки на такт: `hh*16` → 16, `bd ~ bd ~` → 2) и выбирает подходящий.
Перечень рецептов — enum в схеме, поэтому модель не может придумать другой.

**Причина.** Название рецепта нельзя проверить исполнением, а плотность можно.
Плюс выбор по плотности даёт разнообразие рисунков без новых данных в
библиотеке.

---

### D-017. Плотность секции определяет рецепт по умолчанию

**Контекст.** Секция спеки несёт энергию 0..1. Если энергия не влияет на
звук, трек получается ровным: интро и дроп звучат одинаково.

**Решение.** Если рецепт не задан явно (`default`), он выводится из энергии
секции: ≥ 0.75 → `busy`, ≤ 0.4 → `sparse`, иначе `default`. Явный рецепт из
спеки всегда важнее энергии.

**Причина.** ТЗ требует «прогрессию во времени». Энергия — единственное поле
спеки, которое прямо описывает плотность секции, и решение превращает её в
звук без новых полей в контракте с моделью.

---

### D-018. Зерно влияет на рисунок через хэш, а не через генератор случайных чисел

**Контекст.** Первая версия компилятора использовала xorshift-PRNG. У seed = 1
состояние обнулялось на первом же шаге (`state >>>= 17` при малом состоянии),
и разные зёрна давали одинаковый код — тест «разный seed → разный код» это
поймал.

**Решение.** Никакого PRNG: вариант рисунка считается как
`hash(seed|роль) + индекс секции`, выбор шаблона — как `phase + index` по
пулу. Хэш не зависит от порядка обхода, поэтому добавление секции не
сдвигает рисунки соседних.

**Причина.** Детерминированность важнее «настоящей» случайности: код трека
должен воспроизводиться из спеки, а результат best-of-N (фаза 6) обязан быть
воспроизводимым по зерну.

---

### D-019. Гармонические партии строятся через `.add()`, ударные — без `.scale()`

**Контекст.** Арпеджио, идущее по аккордам прогрессии, нельзя собрать из
`stack()` одновременных голосов: это даёт аккорд, а не арпеджио.

**Решение.** Арпеджио и лид строятся как
`n("0 2 4").add(n("<степени>").slow(N)).scale(key)` — сумма берётся в
степенном пространстве, если `.add()` стоит **до** `.scale(key)`. Ударные и
эффекты — только сэмплы: `.scale(key)` к ним не применяется (движок ругается
`Invalid value format for 'scale'`).

**Причина.** Проверено пробами фазы 2 на живом движке, результаты — в
`docs/SPIKE.md`. Ошибка порядка методов даёт тихой неверный результат, поэтому
порядок зафиксирован в компиляторе и в тестах.

---

### D-020. Ритм мотива переводится в mini-строку, а не задаётся через `.struct()`

**Контекст.** `.struct("x ~ x x")` при длине ритма, не совпадающей с числом
нот, ведёт себя непредсказуемо: `n("0 2 4").struct("x ~ x x")` теряет третью
ноту и даёт восемь событий вместо трёх.

**Решение.** Ритм мотива раскладывается по степеням самостоятельно: `x ~ x x`
и `[0, 2, 4]` → mini-строка `0 ~ 2 4`. Больше нажатий, чем степеней, —
степени повторяются по кругу.

**Причина.** Свой код предсказуем, а `.struct()` — нет. Разница видна на
слух и на графике событий, поэтому ритм переводится детерминированно.

## Решения фазы 4 (метрики v2)

### D-021. Окно метрик — 4 такта; мера новизны — доля уникальных окон

**Контекст.** Новизна и вариативность меряются «по окнам». Окно в один
такт слишком мелко: смена рисунка внутри такта не даёт новых окон. Окно в
16 тактов слишком крупно: весь трек схлопывается в одно окно, и метрика
перестаёт различать статичный и развивающийся трек.

**Решение.** Окно = 4 такта (`WINDOW_BARS`). Мера новизны — доля
**уникальных** окон среди всех окон трека, а не доля уникальных тактов.

**Причина.** Доля уникальных тактов математически недостижима для
разумного трека: 64 такта — это 64 окна, и чтобы набрать 100 %, каждый
такт должен отличаться от всех остальных, что невозможно при повторяющейся
прогрессии. Окно в 4 такта совпадает с масштабом самой короткой секции
формы, поэтому окно — это «один смысловой блок».

### D-022. Старые 10 критериев пересчитываются по событиям, а не по тексту

**Контекст.** Скор v1 считал плотность и разнообразие своим парсером
mini-нотации. На структурированном треке (секции, `arrange`, `stack`)
парсер находит 0 событий, и плотность выходит нулевой — то есть
v1-скор штрафовал именно то, ради чего делался новый цикл.

**Решение.** Добавлен `analyzeTrackFromEvents` — слой, который получает
готовые события Strudel и считает по ним те же 10 критериев. Старый
`scoreTrack` не тронут: он продолжает работать как раньше.

**Причина.** Обратная совместимость и честность: v1-счётчик по-прежнему
применим к одиночным циклам, а для структурированных треков используется
источник истины из D-001. Ломать старый счётчик было бы дороже, чем
добавить слой рядом.

### D-023. Транспозиция партий — строго после `.scale(key)`

**Контекст.** Гармонические партии собираются из степеней лада, поэтому
бас, пэд и арпеджио звучат в одной октаве и сливаются в один тембр.

**Решение.** В компиляторе введена таблица `ROLE_TRANSPOSE`: bass/sub
`−24` (две октавы вниз), arp/lead `+12` (октава вверх), остальные — 0.
Транспозиция ставится **после** `.scale(key)`.

**Причина.** Проверено пробой `tests/spike/transpose-probe.mjs`: до
`.scale(key)` движок бросает `transpose: not a note` и значение молча
игнорирует — такой порядок дал бы «тихо сломанную» музыку вместо ошибки.
Октавное смещение выбрано потому, что не меняет гармоническую функцию:
интервальные отношения сохраняются.

### D-024. Длина трека берётся из блоков `arrange`, а не из горизонта опроса

**Контекст.** `arrange` **зацикливает** материал: `arrange([4, A], [8, B])`
— это 12 тактов, а не «12 тактов, и дальше всё заново». Длина трека,
взявтая из горизонта опроса, не совпадает с длиной формы.

**Решение.** Длина композиции вычисляется из блоков `arrange`
(`arrangeLength`), а не из числа собранных событий.

**Причина.** Метрики «прогрессия во времени» обязаны мерить ту длину,
которую слушатель действительно слышит. Иначе трек из 12 тактов, повторённый
до 64, выглядел бы как «развивающийся», а был бы статичным.

### D-025. Ноты вне лада задаются только через `note("c#4 …")`

**Контекст.** Первая версия adversarial-фикстуры «ноты вне лада» была
сделана как `n(...).scale(key)`. Оказалось, что `.scale(key)` **гарантирует**
попадание в лад: степень переводится в ступень лада по построению. Фикстура
оказалась в ладе и не тестировала заявленный дефект.

**Решение.** Для нот вне лада используется буквенная нотация
`note("c#4 e4 …")`. Наличие такой возможности — тоже защита от обмана:
дефект, который нельзя выразить в нотации лада, нельзя и случайно
спрятать.

**Причина.** Метрика `scaleFit` должна быть достижимо низкой, иначе она
не работает. Проверка достижимости дефекта — часть дизайна фикстуры.

### D-026. Adversarial-фикстуры обязаны иметь форму

**Контекст.** Первая версия фикстуры «статичные параметры» была 4 такта без
секций. Её скор был низким, но из-за отсутствия формы, а не из-за
статичных параметров — тест измерял бы не заявленный дефект.

**Решение.** Каждая фикстура содержит полноценную форму; отличается
**только** заявленный дефект. Каждая обязана получить балл ниже
эталонного трека — иначе дефект не наказывается.

**Причина.** Тест, который ловит не то, что заявляет, хуже отсутствия
теста: он создаёт ложную уверенность. Форма у всех фикстур — условие
сопоставимости с эталоном.

### D-027. Эталон сравнения — скомпилированный трек с шестью партиями

**Контекст.** Первая версия эталона наследовала 10 партий от теста
компилятора. Фикстура «восемь партий одним ритмом» получала штраф за
**число** партий, а не за одинаковый ритм, — то есть её низкий скор
объяснялся не тем, что проверялось.

**Решение.** Эталон — скомпилированный трек из нормальной спеки ровно с
шестью партиями (профиль technо требует 4–6). Сравнение идёт только с
ним.

**Причина.** Относительно числа партий счёт v1 штрафует превышение
профиля. Эталон должен лежать внутри профиля, иначе сравнение измеряет
аранжировку, а не дефект.

## Фаза 0 — аудио-спайк мини-студии

### D-028. K-взвешивание считается по формулам ITU-R BS.1770-4, а не по RBJ

**Контекст.** Первая версия `src/audio/dsp/k-weighting.js` считала коэффициенты
шелка и RLB-фильтра по формулам RBJ. Сверка с таблицей стандарта (48 кГц)
показала расхождение до **0.055** по b0 шелла — то есть другая АЧХ, а не другой
округ.

**Решение.** Коэффициенты считаются по формулам Таблицы 2 стандарта
(`ituShelfCoefficients`, `ituHighpassCoefficients`). Проверка: пересчёт при
48 кГц совпадает с таблицей стандарта с точностью **8.9e-16**, DC-усиление
шелла = 1.000000 в любой частоте дискретизации.

**Причина.** Стандарт — источник истины; RBJ-фильтр для полосы K не эквивалентен
ему. Расхождение 0.05 в коэффициентах даёт ошибку громкости, которую нельзя
игнорировать при приёмке в ±0.3 LU.

**Чем проверено.** `tests/unit/audio-dsp.test.js` (тест «коэффициенты на 48 кГц
совпадают с таблицей стандарта»), сверка с ffmpeg — `npm run validate:loudness`.

### D-029. True peak: полифазный фильтр 97 отсчётов с нормировкой фаз

**Контекст.** Первая версия передискретизатора давала −12 дБ на выходе: фазы
интерполятора не были нормированы (каждая фаза должна давать единичную сумму).
Вторая версия (64 отсчёта) имела дробную групповую задержку и расходилась с
ffmpeg на **0.42 dBTP** на широкополосном шуме.

**Решение.** Фильтр — windowed-sinc (Кайзер β = 9) на 97 отсчётах: центр 48 →
групповая задержка 12 исходных отсчётов (целое), сумма каждой фазы
нормирована в единицу.

**Причина.** Длина подобрана по сверке с эталоном: 65 отсчёков → 0.42 dBTP
против ffmpeg, 97 → **0.03 dBTP**. Более длинные фильтры (129+) сходятся к
«идеальной» реконструкции, но расходятся с ffmpeg на 0.4 дБ — приёмка идёт
по ffmpeg, поэтому эталон важнее абсолютной точности.

**Чем проверено.** `npm run validate:loudness`: 6 фикстур, |ΔLUFS| ≤ 0.05,
|ΔdBTP| ≤ 0.03 (ffmpeg ebur128, libebur128).

### D-030. Мастер-цепочка вставляется экспортным хуком, без перехвата `connect`

**Контекст.** Гипотеза H1 рисерча утверждала, что вставить цепочку между
superdough и `destination` публичным API нельзя и нужен перехват `connect`.

**Решение.** Хвост мастер-шины superdough доступен через экспорт
`getSuperdoughAudioController()`: `controller.output.destinationGain` — это
GainNode между `channelMerger` и `ctx.destination`. Цепочка вставляется так:
`destinationGain.disconnect()` → `destinationGain.connect(masterIn)` →
`masterIn → EQ → glue → лимитер → ctx.destination`. Перед этим —
`setSuperdoughAudioController(null)`, затем `setAudioContext(ctx)`: контроллер
синглтон и привязан к контексту на момент создания.

**Причина.** Разбор бандла @strudel/web 1.3.0 показал экспорт
`getSuperdoughAudioController`; перехват `connect` не нужен и не применяется.
Измерено в браузере: отношение RMS 0.500007 при gain 0.5, остаток bypass−baseline
точно ноль.

**Риск отката.** `output.destinationGain` — внутреннее поле минифицированного
бандла, а не документированный API. Поэтому есть контрактный тест движка: смена
версии `@strudel/web` обязана его сломать (`tests/unit/engine-contract.test.js`),
а в коде студии обязателен рантайм-guard с запасным путём.

### D-031. Офлайн-рендер — в отдельном контексте, `renderPatternAudio` не вызывается в живом приложении

**Контекст.** В @strudel/web 1.3.0 есть официальный `renderPatternAudio`, но он
делает `await ctx.close()` на текущем аудиоконтексте и создаёт свой
`OfflineAudioContext`, а результат отдаёт скачиванием WAV (буфер наружу не
отдаёт).

**Решение.** В приложении офлайн-рендер делается собственным кодом в
отдельном `OfflineAudioContext` (рендер-воркер), тем же DSP-ядром. Официальная
функция — только источник схемы вызова событий.

**Причина.** Закрытие живого контекста убило бы звук в приложении. Свой
рендер даёт буфер для метрик, повторяемость (два рендера) и отмену.

### D-032. Glue-компрессор: ослабление — отрицательное, тишина не даёт NaN

**Контекст.** Первая версия возвращала из `targetReduction` положительную
величину, и `grDb` уходил в плюс — компрессор **усиливал** сигнал вместо
ослабления. На старте файла (первый отсчёт тишины) огибающая уходила в NaN
(`−Infinity − −Infinity`), и весь выход становился NaN.

**Решение.** `targetReduction` возвращает отрицательные дБ (ослабление ≤ 0);
для тишины огибающая сбрасывается в ноль. Проверка потолка лимитера и GR
компрессора — в контрактных тестах.

**Причина.** Баг найден тестом, а не прослушиванием: на слухок NaN — это тишина.

### D-033. Аудио-пакеты запинены точно; версия едет в метриках

**Контекст.** `@strudel/web` был на `^1.3.0` — минорное обновление меняло бы
звук и API без предупреждения.

**Решение.** `@strudel/web` запинен как `1.3.0`; `ffmpeg-static` и
`playwright-core` — тоже точно (от них зависит воспроизводимость замеров).
Версии вынесены в `src/audio/engine-version.js` и попадают в
`MetricsReport.engineVersion`.

**Причина.** Метрика без версии движка невоспроизводима: тот же LUFS на другой
версии — другой мир.

### D-034. Изоляция ассистента — без MicroVM/gVisor

**Контекст.** Рисерч предлагал уровни изоляции (MicroVM, gVisor) для
безопасности LLM-агента.

**Решение.** Не применяются. Ассистент не порождает исполняемый код: он
работает только tool-use поверх командной шины с Zod-валидацией; сетевых и
файловых инструментов нет; рендеры изолированы в Worker с таймаутом и
отменой.

**Причина.** MicroVM/gVisor защищают от исполнения произвольного кода, которого
здесь нет. Уровень изоляции, соответствующий реальной модели угроз, —
командная шина сallowlist и валидацией.

### D-035. `.duck(n)` — это алиас `.duckorbit(n)`, а не отдельный эффект

**Контекст.** Рисерч утверждал: «`.duck()` — сам эффект приглушения,
`.duckorbit()` — определяет, на какую орбиту влияет». В @strudel/web 1.3.0
в бандле это `duck: mm = A("duckorbit", "duck")` — оба метода пишут **одно**
поле `duckorbit`.

**Решение.** Компилятор не генерирует `.duck(...)` как отдельный эффект. Роль
дакинга описывается тройкой: `.duckorbit(N)` (жертва), `.duckonset(t)` (момент
начала), `.duckattack(s)`, `.duckdepth(d)`. Орбита-жертва должна существовать
(партия-жертва обязана иметь `.orbit(N)`), иначе движок пишет
`duck target orbit N does not exist` и дакинга не будет.

**Причина.** Ошибка в понимании API дала бы «тихо сломанный» микс: дакинг
просто не случился бы, и приёмка по метрикам это показала бы не сразу.
Зафиксировано контрактным тестом «`.duck(n)` — алиас `.duckorbit(n)`».

### D-036. Список имён сэмплов вендорен и сверяется с банками

**Контекст.** Браузерный спайк показал: из 44 имён палитры проекта в банках
есть 42. Отсутствуют `oh` и `sh` — а именно эти имена были разрешены в
`server/prompts/system.md` и `server/prompts/critic.md`. Сэмпл, которого нет в
манифесте, молчит: партия исчезает без ошибки, и это слышно только на слух.

**Решение.** Манифесты банков вендорены в
`server/music/data/sample-banks.json` (218 имён dirt-samples + piano).
`tests/unit/sample-names.test.js` сверяет имена, разрешённые в промптах, с этим
списком и падает, если появилось имя без сэмпла. Обновление списка —
`npm run sync:samples` (сеть нужна только там, в CI используется вендоренный файл).
Заодно `DRUM_NAMES` в `server/music/extract.js` приведён к реальности:
`clap/rim/tom/cowbell/oh/sh` заменены на `cp/rm/odx/cb/ho`.

**Причина.** Список имён жил в тексте промпта и молча устаревал: банк сменился
— промпт об этом не знал, а модель генерировала несуществующие сэмплы. Теперь
расхождение ломает сборку, а не трек.

## Фаза 2 — аудиограф, DSP-core, мастер

### D-037. Bypass реализован внутри мастер-worklet, а не отдельной веткой графа

**Контекст.** §5 промта предлагает сухую ветку в графе: «dry-путь задержан на
величину `latencySamples`, сообщённую worklet; переключение — equal-power
кроссфейд 20–30 мс».

**Решение.** Сухая ветка живёт внутри того же worklet: `MasterChain` держит
собственную линию задержки длиной `lookahead` и кроссфейдит обработанный и
сухой сигналы по отсчётам (равная мощность, 25 мс).

**Причина.** У `AudioWorkletNode` есть собственная задержка в один рендер-квант
(128 отсчётов), о которой движок не сообщает. Нативная ветка на `DelayNode`
отстала бы от обработанной ровно на квант — A/B разъезжался бы по времени на
2.7 мс. Внутри worklet обе ветки проходят один конвейер, поэтому выравнивание
точное по построению, а не «подобрано».

**Чем проверено.** `tests/unit/audio-master.test.js`: после выхода в bypass
остаток между выходом и входом, сдвинутым на `lookahead`, < 1e-6; сдвиг по
кросс-корреляции = `latencySamples`; скачок на переходе не больше собственных
скачков сигнала.

### D-038. Фильтр true peak — как в libebur128, а не «идеальная реконструкция»

**Контекст.** D-029 выбрал фильтр на 97 отсчётов с окном Кайзера, сверяя его с
ffmpeg. Оказалось, сверка была с неверным полем: в выводе `ebur128` true peak
брался из покадрового `FTPK`, который на самом деле пара «текущее/максимум»,
а для файла с переходным в начале показывает уровень в конце, а не пик файла.
Правильное поле — «True peak: Peak: …» из блока Summary.

**Решение.** True peak считается по алгоритму libebur128 (49 отсчётов, окно
Ханнинга, передискретизация 4×) — это эталон EBU R 128. Сверка ведётся с
буквальной транскрипцией референса (`scripts/libebur128-reference.mjs`),
расхождение ≤ 0.001 дБ.

**Причина.** ffmpeg измеряет true peak не фильтром приложения 2 стандарта, а
ресемплером libswresample (до 192 кГц, `f_ebur128.c`). У ресемплера своя АЧХ:
на широкополосных синтетических сигналах он завышает пик до +0.7 дБ. Свой
фильтр с другой АЧХ дал бы цифру, не сопоставимую ни со стандартом, ни со
стриминговыми платформами.

**Чем проверено.** `npm run validate:loudness` — |ΔLUFS| ≤ 0.05 против ffmpeg,
|ΔdBTP| = 0.00 против libebur128 на 6 фикстурах; `npm run validate:master` —
то же на 5 фикстурах мастер-цепочки.

**Риск отката.** D-029 в части выбора фильтра отменяется: сверка с ffmpeg по
true peak информационная, критерий приёмки — совпадение с libebur128.

### D-039. Распределение ролей: контекст и мастер у студии, движок — гость

**Контекст.** §5 промта: «владение графом у студии, а не у движка».

**Решение.** `src/audio/graph.js` владеет `AudioContext`, мастер-шиной и
метрами; `src/audio/engine/adapter.js` — единственное место, где студия касается
движка. Точка врезки — хук H1: `destinationGain` движка отключается от
`ctx.destination` и подключается к `masterIn` студии.

**Причина.** `initStrudel({audioContext})` сажает и планировщик, и контроллер
superdough в контекст студии, поэтому движок играет в нашей шине, а не в
своей. Если worklet не загрузился — движок подключается прямо к выходу, и в
консоль пишется «мастер-цепочка недоступна»: приложение остаётся рабочим, но
не притворяется, что мастер включён.

**Чем проверено.** `tests/spike/browser/master-live-spike.mjs` (браузер):
задержка 240 отсчётов (5 мс), сквозная 55 мс (10 base + 40 output + 5 мастер),
пик на выходе ровно −1.000 dBFS, в bypass метры продолжают идти и сигнал
становится на 9 дБ громче.

### D-040. Worklet собирается esbuild'ом из того же DSP-ядра

**Контекст.** AudioWorklet не поддерживает `import`: файл worklet'а должен быть
самодостаточным. Копия DSP в worklet'е — это две реализации, которые разойдутся.

**Решение.** `src/audio/worklet/master-processor.js` импортирует `src/audio/dsp/*`
и собирается esbuild'ом в `public/worklets/master-processor.js`
(`npm run build:worklet`, автозапуск в `prebuild`/`predev`). Сборка
детерминирована: при неизменных исходниках файл не переписывается.

**Причина.** Один DSP-core на реалтайм, офлайн-рендер и CI — иначе метрики в
реалтайме и в отчётах считаются разными числами.

**Чем проверено.** `tests/unit/audio-master.test.js` запускает **собранный**
worklet в Node (с подделкой области AudioWorklet) и сверяет его выход с ядром:
максимальное расхождение < 1e-5 (разница только от float32).

### D-041. Потолок лимитера держится по sample peak; true peak может быть выше на ~0.1 дБ

**Контекст.** Приёмка требует потолок −1 dBTP, а лимитер ограничивает
мгновенный отсчёт.

**Решение.** Пока потолок держится по sample peak: в браузере на стресс-паттерне
пик на выходе ровно −1.000 dBFS, true peak −0.93 dBTP.

**Причина.** Лимитер с предпрослушиванием по отсчётам не видит межотсчётовый
пик реконструкции. Разница ~0.1 дБ меньше коридора приёмки, но формально
«−1 dBTP» не выполнено.

**Чем проверено.** `tests/spike/browser/master-live-spike.mjs`: true peak
−0.927 dBTP при потолке −1 dBFS; в bypass тот же паттерн даёт +3.17 dBFS.

**Когда.** Фаза 4 (autoMix и приёмка): потолок по true peak — либо лимитер
считает передискретизованный пик, либо потолок опускается до −1.2 dBFS.

### D-042. Аудио-блок в скоре: 20%, переключаемый, отчёт приходит из браузера

**Контекст.** §7 промта: «аудио-блок входит в скор (вес 20%, переключаемо)».
Аудио на сервере нет — рендер живёт в `AudioContext` браузера.

**Решение.** Отчёт рендера (MetricsReport) приходит в запрос
`POST /api/music/compose` полем `audioReport`. Сервер проверяет **только форму**
(`MetricsReportSchema`), числа не проверяет: их считает браузер тем же
DSP-ядром, что звучит в реалтайме. Битый отчёт не ломает композицию — аудио-блок
не участвует, причина отклонения возвращается в событии `scored` полем
`audioRejected`. Флаг `useAudio: false` выключает блок.

**Причина.** Проверить числа на сервере нечем, а отказываться от объективной
оценки звучания — значит оценивать трек только на глаз. Происхождение чисел
явно: паспорт `engineVersion` и `renderMode` внутри отчёта.

**Чем проверено.** `tests/unit/audio-score.test.js` — отчёт попадает в скор,
битый отчёт не ломает поток, флаг выключает блок.

**Риск отката.** Клиент может прислать заведомо неверные числа. Для приёмки
это не опасно: приёмка считается по отчёту, который делает браузер, и
дублируется на клиенте (шаг 3 — человек слушает и решает).

### D-043. «Повторяемость не измерена» ≠ «повторяемость есть»

**Контекст.** §5 промта: autoMix и приёмка работают только при
`repeatability.passed`. Отчёт с одним рендером ничего не доказывает.

**Решение.** `repeatability` заполняется только после двух рендеров. При одном
рендере — `null`, и QA выдаёт предупреждение `repeatability-unknown`;
аудио-блок скора при этом **не засчитывает** балл за повторяемость (25 из 100).

**Причина.** Иначе трек с одним рендером получил бы полный балл за то, что не
измерялось. «Неизвестно» не должно выглядеть как «хорошо».

**Чем проверено.** `tests/unit/audio-render.test.js`: один прогон →
`repeatability = null` и предупреждение; два прогона детерминированного рендера
→ `passed = true`, расхождение 0; шумящий рендер → `passed = false` и ошибка QA.

**Риск отката.** Скор трека с одним рендером систематически ниже. Это осознанно:
в студии рендер всегда делается двумя прогонами (кнопка «Анализ»).

### D-044. Офлайн-рендер пересоздаёт контроллер superdough — живой трек возвращается

**Контекст.** H3: официальный `renderPatternAudio` закрывает живой
`AudioContext`, поэтому рендер делается в отдельном `OfflineAudioContext`.

**Решение.** Свой рендер: код → паттерн (`patternFromCode`, без звука) →
события → `OfflineAudioContext`. После рендера контроллер superdough
пересоздаётся, поэтому адаптер заново врезает хвост движка в мастер-шину
студии, а движок возвращает живой трек повторной оценкой кода. Рендер — это
действие по кнопке, а не фоновая задача.

**Причина.** Один контекст на всё — иначе либо рендер ломает звук, либо звук
ломает рендер. Пересоздание контроллера — цена офлайн-контекста, и она
явно описана в коде.

**Чем проверено.** `npm run spike:offline` — рендер двух тактов в браузере,
затем проверка, что живой контекст жив и код исполняется.

**Риск отката.** Если superdough изменит порядок инициализации, восстановление
не сработает — тогда рендер придётся делать в отдельном окне. Контрактный
тест движка (`tests/unit/engine-contract.test.js`) ломает сборку при смене
версии пакета.

### D-045. Соло-рендеры партий отложены до фазы 4

**Контекст.** §7 промта требует соло-рендеры партий, чтобы понимать, кто
именно громкий.

**Решение.** Модуль рендера (`src/audio/render/offline.js`) поддерживает
`parts` и `partId`, но движок пока фильтрует события по всей партии: в коде
нет разметки партий (id контроллера), по которой можно отфильтровать hap'ы.
Разметка появится вместе с палитрой и правилами микса в фазе 4.

**Причина.** Выдавать за соло-рендер партии полный микс — это ложные числа в
отчёте; честнее не выдавать их вовсе.

**Чем проверено.** `tests/unit/audio-render.test.js` — приём с `parts`
заполняет метрики партий; в браузере соло пока не проверяется.

**Риск отката.** Замечания «партия слишком громкая» до фазы 4 не появятся:
их приёмка опирается на `parts`.


### D-046. Composition IR: план вместо кода

**Контекст.** LLM-путь пишет Strudel-код. Код непрозрачен, «сделай мрачнее»
требует перегенерации, а выход модели нельзя безопасно исполнять.

**Решение.** Введён Composition IR (`src/ir/schema.js`) — Zod-схема типизированного
плана: настроение, форма, гармония римскими цифрами, мотивы, грув, палитра,
регистры ролей. Компилятор (`src/ir/compiler.js`) — чистая функция IR→код.
Правки — типизированные трансформации IR (`src/ir/transforms.js`), каждая
возвращает новый IR и объявляет ожидаемый знак изменения метрик.

**Причина.** Только план позволяет измерить правку, получить соло-стемы
бесплатно и не пускать текст модели в исполнение.

**Чем проверено.** 167 тестов (`tests/unit/ir-*.test.js`): схема, намерение,
гармония, грув, компилятор (fuzz на 300 случайных IR + исполнение в движке),
трансформации. Побайтная детерминированность компиляции.

### D-047. Символьный оракул двухслойный: быстрый из IR и точный из движка

**Контекст.** Рендер стоит секунды, перебрать сотню кандидатов нельзя. Бриф §6
требует «≤50 мс на 32 такта, ≥200 кандидатов/с».

**Решение.** Два слоя. Быстрый (`src/oracle/ir-events.js`) считает события
прямо из IR, используя те же `grooveSteps`, `buildChordPlan`, `motifToMini`,
`roleLevel`, что и компилятор. Точный (`server/music/strudel-runtime.mjs`) —
`queryArc` движка, для финалистов.

**Причина.** Измерено: `queryArc` даёт 11 кандидатов/с, быстрый слой — 45…600.
Поиск по кандидатам возможен только на быстром слое.

**Чем проверено.** `tests/spike/oracle-timing.probe.mjs` (экономика) и
`tests/unit/oracle-consistency.test.js` (расхождение слоёв ломает тест).

### D-048. Граница точности быстрого оракула: ритм точен, вокальный алгоритм — нет

**Контекст.** Движок раскладывает аккорд по голосам своим алгоритмом. Воспроизвести
его в оракуле — отдельная задача, а для метрик (движение корней, напряжение,
регистр) она не нужна.

**Решение.** Быстрый оракул воспроизводит ритмический скелет точно (все атаки,
длительности, числа событий) и высоты ударных, баса, лида и арп. Высоты
аккордов — каноническое сомкнутое расположение от якоря. Граница объявлена в
шапке `src/oracle/ir-events.js` и в `docs/ORACLE.md`.

**Причина.** Честная граница лучше незаметной неточности: сверка атак
остаётся строгой, а расхождение по голосам не маскируется под «примерно
так же».

**Чем проверено.** Тест сверяет по числу событий и таймингам атак; для аккордов
сравниваются атаки, а не высоты.

### D-049. PRNG: FNV-1a + финализатор fmix32

**Контекст.** PRNG проекта — адресный, от `(seed, секция, роль, шаг)`. Он
использовался для отсева шагов по плотности и для выбора нот мотива.

**Решение.** К FNV-1a добавлен финализатор `fmix32` (MurmurHash3) —
avalanche-шаг. Тот же финализатор применён к отсеву шагов в `groove.js`.

**Причина.** Измерено: у «голого» FNV-1a старшие биты почти не смешиваются,
распределение получалось рваным (46 % значений в одном десятом интервала,
среднее 0.68 вместо 0.5). Для отбора нот и отсева шагов это означало
систематический перекос, а не случайность.

**Чем проверено.** `tests/spike/prng-distribution.probe.mjs`: после фиксатора
гистограмма по десятым интервалам — 9.9…10.1 %.

### D-050. Свинг и микротайминг считает компилятор, а не движок; бюджет ±20 мс

**Контекст.** Карта groove-templates требует свинга и микротайминга. Штатные
средства движка не подходят: `swingBy(x, n)` в @strudel/web 1.3.0 дублирует
события (16 хэтов → 24), `swing(x)` без второго аргумента — no-op, а `.gain()`
по событию ломает привязку внутри `.beat()` со списком шагов.

**Решение.** Шаблоны грува задают сдвиг в миллисекундах; компилятор раскладывает
шаги по группам «динамика + сдвиг» и кладёт сдвиг через `.late(ms(x))`.
Суммарный сдвиг ограничен **±20 мс на любом темпе**.

**Причина.** Свой путь детерминирован, прозрачен для аудита и не зависит от
недокументированного поведения движка. Ограничение ±20 мс — из карты
грув-шаблонов; на 80 BPM свинг 8-х сам по себе даёт 45 мс и упирается в
бюджет (20 мс на медленном темпе и есть правильный лоуфай-свинг).

**Чем проверено.** `tests/unit/ir-groove.test.js`: сдвиги укладываются в
±20 мс для всех шаблонов на темпах 70…200.

### D-051. Пороги линтера зависят от жанра

**Контекст.** Единые пороги North Star (плотность ≤20/с, связка бас–кик ≥0.6)
применялись ко всем жанрам.

**Решение.** Пороги вынесены в `GENRE_THRESHOLDS` (`src/oracle/lint.js`):
плотность для D&B — 40/с, для эмбиента — 10/с; связка бас–кик не проверяется
в синтипопе (оффбитный бас там и есть жанр).

**Причина.** Измерено: D&B даёт 33.6 события/с, и это норма, а не «каша»;
в синтипопе бас оффбитный по определению, и «рассинхрон» — ложное
срабатывание. Единый порог врал бы на каждом жанре.

**Чем проверено.** `tests/unit/oracle-lint.test.js`: на пяти здоровых треках
ошибок линтера нет.

### D-052. Регистр роли honored компилятором

**Контекст.** Поле `layer.register` было описано в схеме, но компилятор его
игнорировал: бас всегда играл `rootNotes(2)`, а мотив — без сдвига октавы.
Из-за этого трансформация `shiftRegister` меняла IR, но не меняла звук.

**Решение.** Октава баса берётся из `layer.register[0]`, мотив сдвигается на
октаву оттуда же (степени лада — индексы, октава = ±7 индексов).

**Причина.** Трансформация, которая не меняет звук, — ложь в интерфейсе.
Дефект найден mutation-тестом линтера.

**Чем проверено.** `tests/unit/oracle-lint.test.js` (дефект «бас в середине»
стал находиться) и `tests/unit/oracle-consistency.test.js` (сверка с движком).

### D-053. В матрицу ролей добавлен снейр

**Контекст.** `ROLE_MATRIX` не содержал снейра, поэтому ни один трек,
собранный планировщиком, не имел акцента на 2 и 4 долю — бэкбита.

**Решение.** Снейр добавлен во все секции, где есть ударные, с весами по
матрице ролей.

**Причина.** Трек без бэкбита не имеет пульса. Это было видно и по
символьному разбору: связка бас–кик падала из-за отсутствия снейра.

**Чем проверено.** `tests/unit/ir-compiler.test.js`: партия SNARE присутствует
в скомпилированном коде и стоит на шагах 4 и 12 сетки 1/16.

### D-054. Символьный скор — гипотеза, а не цель оптимизации

**Контекст.** Скор нужен, чтобы выбирать кандидатов. Но скор, оптимизируемый
без проверки на людях, — классический Goodhart: метрику начинают обманывать.

**Решение.** Скор помечен `validated: false` и сопровождается замечанием в
отчёте. Веса составляющих видны пользователю. Канарейки (пять подлых треков)
обязаны набирать строго меньше медианы корпуса, иначе эволюция скилов и
Taste Model блокируются. Поиск по мутациям честно назван фильтром дефектов:
на зрелом треке он ничего не улучшает (измерено, E-005).

**Причина.** Проект не имеет ни одной человеческой пары. Утверждать «микс
стал лучше» на основании символьного скора — выдумка.

**Чем проверено.** `tests/unit/oracle-lint.test.js`: проверка канарейк;
`docs/EXPERIMENTS.md`, E-005 — нулевой результат зафиксирован, а не сокрыт.

### D-055. Скил-пак — источник правил для LLM-планировщика

**Контекст.** Карты скил-пака были написаны, но планировщик на тексте (`planIR`)
работал по правилам, зашитым в код. Получалось два источника правды: карты
говорили одно, код — другое, и никто их не сверял.

**Решение.** Учебник (сборка COMPACT-блоков карт под конкретный запрос) —
единственный источник правил для модели. Правила из карт попадают в системный
промт планировщика; код их не дублирует. Версия пака (`skillsVersion` =
sha256 от frontmatter + COMPACT всех карт) входит в ключ кэша планировщика и в
ответ API: без неё результат невоспроизводим — правила могут поменяться.

**Почему.** «LLM решает что, код решает как» работает только если у LLM есть
правила. Карты — это и есть правила в машиночитаемом виде; без них модель
описывает музыку словами, а мы переводим их в код сами, то есть возвращаемся
к проблеме промтов.

**Последствия.** Появился `check:skills` — гейт, который ломает сборку, если
карта разошлась с кодом или её тело изменилось без bump версии. Карты больше
нельзя править «на глаз»: правка без версии падает в CI.

**Чем проверено.** `tests/unit/skills.test.js` — матрица активации из
`skills/INDEX.md` сверяется с кодом; `tests/unit/skills-planner.test.js` —
в промт уходит учебник, а не пустая строка.

### D-056. «<...>» в n()/note() — один элемент за цикл, а не шаги внутри такта

**Контекст.** В картах жанра мелодии были записаны как `n("<4 ~ 2 ~ 5 ~ 3 ~>")`.
Измерено в headless-рантайме Strudel: `n("0 2 4")` даёт 3 события за цикл,
`n("<0 2 4>")` — **1** событие за цикл. Угловые скобки в mini-нотации — это
«один элемент за цикл», а не последовательность шагов.

**Решение.** Шаги внутри такта пишутся без угловых скобок. Прогрессии
(`chord("<Am F C G>")`), маски (`mask("<1!15 0>")`) и панорамы
(`pan("<.4 .6>")`) остаются как есть: там один элемент за цикл нужен. В
линтер примеров добавлено правило `angle-sequence-in-note`; отказ от него —
явный комментарий `one-per-cycle` в коде.

**Почему.** Ошибка тихая: код исполняется, ошибок нет, музыка играет — но
по одной ноте на такт вместо ритмической фигуры, а с `degradeBy(.3)` голос
мог замолчать целиком. Это ровно тот класс дефектов, который ловит CI, а не
слух.

**Чем проверено.** `tests/spike/skills-example-shape.probe.mjs` — сама
семантика; `tests/unit/skills.test.js` — правило линтера; правки в карках
`genre-trip-hop`, `genre-lofi`, `composer-workflow`.

### D-057. Матрица активации — исполняемое правило, а не текст

**Контекст.** `skills/INDEX.md` содержал таблицу «промт → ожидаемые карты»,
которая ни с чем не сверялась. При первой же сверке с кодом разошлись три
строки.

**Решение.** Матрица разбирается тестом и сверяется с кодом: жанр — по
`resolveGenre`, настроение — по словарю emotion-map, грув и арка — из карты
жанра. Расхождение падает в тесте, а не всплывает через полгода.

**Что пришлось решить по существу.**
* «мрачный трип-хоп про дождь» — карта и словарь дают `melancholy`
  («последнее слово доминирует»), матрица ждала `dark`. Оставлено по
  правилу карты; матрица приведена в соответствие.
* «уютный лоуфай для учёбы» — словарь не знал падежа «учёбы», поэтому
  настроение читалось как `tender` вместо `nostalgia`. Словарь дополнен
  (`учёба/учёбы/учеба/учебы`), карта поднята до 1.0.1.
* «светлый синтипоп для вечеринки» — «светл» и «вечерин» добавлены в `joy`.
* Условная арка «(или club-64 для «фестиваля»)» **никогда не срабатывала**:
  в карте точка после скобки, а слово-триггер стоит в родительном падеже
  («фестиваля» против «фестиваль» в запросе). Теперь триггер сравнивается по
  основе, и «эйфоричный фестиваль» действительно получает club-64.
* Грув трип-хопа в матрице был `laid-back`, а карта объявляет `drunken`;
  `laid-back` — грув другой карты. Матрица исправлена.

**Почему.** Документация, которую не читает код, вредна: она обещает
проверяемое и не проверяет.

### D-058. Theory-lint для примеров карт — подмножество, и это зафиксировано

**Контекст.** Спека требует «dry-parse + theory-lint v1 (0 errors)» для
каждого примера карты. Полный линтер оракула (`src/oracle/lint.js`) работает
по IR, а примеры карт — это сырой Strudel-код.

**Решение.** Для примеров применяется подмножество, которое исполняется
по-настоящему: dry-parse в headless-Strudel (синтаксис, имена контролов,
mini-нотация), запрещённые конструкции, guardrails (delayfeedback < 1,
gain ≤ 1.2, duckdepth ≤ 1, |микротайминг| ≤ 20 мс), соответствие нот ладу и
ловушка «<...>». Полный theory-lint (параллельные квинты, коллизии регистров)
включается на этапе компиляции IR, где он и живёт.

**Почему.** Лучше меньше проверок, которые действительно исполняются, чем
список правил, который никто не запускал. Подмножество названо прямо, чтобы
его не выдали за полный линт.

**Долг.** Полный линт по сырому коду — отдельная задача (нужен обратный
перевод кода в IR).

### D-059. Baseline-0 заморожен; аудио-часть — честный долг

**Контекст.** Пока не зафиксировано, с чем сравнивать, любое «стало лучше» —
мнение. Спринт S0.2 требует корпус из 60 промтов с разбивкой и заморозкой.

**Решение.** `corpus/baseline0/`: 60 промтов (4 квадранта × 5 жанров ×
3 плотности), сплит 36/12/12 детерминированно по sha256 id, для каждого
промта — план по правилам, скомпилированный код, IR-хэш, code-хэш и
символьный разбор. Манифест подписывает sha256 обоих файлов; `npm run
check:baseline` в CI ломает сборку при любой правке корпуса.

**Почему.** Заморозка — это и есть Baseline-0: не «эталонные примеры», а
слепок системы на момент заморозки, с которым можно сравнивать честно.

**Долг.** Аудио-часть Baseline-0 (WAV + MetricsReport + renderFingerprint) не
собрана: рендер требует браузера, а в CI это 60 офлайн-рендеров. Планируется
отдельным прогоном (`npm run spike:offline` уже умеет рендерить). До этого
Baseline-0 — это код и символьный разбор, а не звук.

### D-060. Дорожка H: пары строятся на правилах против мутации

**Контекст.** Метки — узкое место проекта: без них нельзя проверить
символьный скор, обучить Taste Model и честно сказать «стало лучше».

**Решение.** Очередь пар — детерминированная: A — план по правилам, B —
мутация того же плана; стороны переставлены по хэшу индекса, каждая десятая
пара — повтор с переставленными сторонами (измеряет надёжность рецензента).
Страница `/tinder.html` рендерит оба варианта в браузере тем же движком,
выравнивает громкость **только гейном** (без лимитера) и переставляет треки
по каналам случайно. Метки пишутся в JSONL без PII; экспорт — NDJSON
chosen/rejected, удаление — одной командой.

**Важная деталь.** Мутация не всегда меняет план: у эмбиента нет ударных, а
мутация плотности бьёт по ударным — получалась пара «сам с собой», то есть
фиктивное сравнение. Поэтому кандидаты перебираются, пока коды не разойдутся;
если не разошлись ни одна мутация — берётся другой план того же промта.

**Почему.** «Пара» из двух одинаковых треков даёт рецензенту ложную метку:
он вроде бы выбрал, а на самом деле сравнивал одно с тем же.

**Долг.** Активный отбор пар (где модель неуверена) отложен: очередка v0 идёт
по порядку. Публичная ссылка для друзей-рецензентов — только с разрешения
владельца (rate-limit, без PII).

### D-061. Механика ответа модели чинится кодом, а не моделью

**Контекст.** Первый же живой прогон планировщика (14.11.2026, боевой сервер,
OpenAI) показал: модель отвечает, но её план не проходит Zod — система молча
уходила в правила. Причина измерена по живому ответу, а не предположена:

```
layers.texture.plan: Invalid enum value.
  Expected 'drums' | 'bassline' | …, received 'тихий виниловый шум и тёмная атмосфера'
```

Модель трактует поле `plan` как «описание партии» и пишет туда естественный
язык. Восемь слоёв из восьми были такими.

**Решение.** Три вещи, каждая по своему основанию.

1. **Детерминированная починка** (`server/ir/normalize.js`): `plan` берётся по
   роли (`planForRole`), выдуманные роли выбрасываются, недостающий регистр
   ставится по роли, числа вне диапазона обрезаются, «IV/3» → «IV». Каждая
   правка записывается в `notes` — видно, что именно изменилось.
2. **Живой ремонтный ретрай**: в промпт повтора попадают прошлый ответ модели
   и список конкретных ошибок Zod. До этого повтор был повтором того же
   запроса — модель физически не могла узнать, что не так, и второй ответ
   был тем же.
3. **Явный контракт**: в краткой схеме enum-поля описаны словами
   («ОДНО слово из списка, а НЕ описание»).

**Почему именно так.** Это и есть принцип брифа: «LLM решает что, код решает
как». Тип партии — это механика, а не музыкальное намерение: модель сказала
«педальный слой, тихий», код решил, что это `pad`. Спорить с моделью о типе
партии — бессмысленная трата вызовов; спорить о гармонии или энергии — нужное
дело.

**Чем проверено.** `tests/unit/ir-normalize.test.js` — тесты построены на
реальном ответе модели; `tests/unit/skills-planner.test.js` — ретрай несёт
ошибку, починка закрывает класс ошибок без повторного вызова.

**Честная оговорка.** Починка чинит форму, а не вкус: если модель сказала
«три секции по одной ноте» — это останется «тремя секциями по одной ноте».
Качество плана на живых прогонах пока не измерено человеком.

### D-062. Dockerfile копирует скил-карты: /api/skills иначе даёт 500

**Контекст.** После первого деплоя этой сессии `/api/health` был зелёным, а
`/api/skills` отдавал 500 с ENOENT: `scandir '/app/skills'`. Причина:
`.dockerignore` исключает `corpus`, `docs`, `tests`, а Dockerfile копировал в
образ только `dist`, `server`, `src`, `scripts` — каталог `skills/` в образ
не попадал.

**Решение.** `COPY skills ./skills` в Dockerfile. Плюс: отсутствие каталога
карт теперь проверяется гейтом `check:skills` (он читает карты с диска), а
деплой проверяет `/api/skills`, а не только `/api/health`.

**Почему это отдельное решение.** Зелёный `/api/health` доказывает, что
процесс жив, но не что все маршруты работают: ошибка чтения файлов возникает
внутри обработчика. Смоук деплоя расширен: после деплоя проверяются и
`/api/skills`, и `/api/preference/queue`, и `/tinder.html`.

### D-063. Метрики и веса скора живут в одном реестре

**Контекст.** Символьные веса скора жили в `src/oracle/score.js`, критерии
аудио-блока — в `server/music/compose/audio-score.js`, формула смешивания
v1/v2/аудио — там же, а третий набор весов (критерии v2) — в
`server/music/score-v2.js`. Плюс в комментарии аудио-блока была написана
формула `v1·0.5 + v2·0.3 + аудио·0.2`, которой в коде не было: код считал
`v1·0.48 + v2·0.32 + аудио·0.2`. То есть и веса, и их описание расходились
между собой.

Бриф §2.8 требует, чтобы «ни одна метрика не становилась целью оптимизации,
пока она не проверена против человеческих суждений». С тремя разбросанными
наборами весов это требование невыполнимо: у веса не было места, где можно
поставить «не проверено».

**Решение.** `src/metrics/registry.js` — единственный источник:

* 43 метрики: `id`, `label`, `unit`, `range`, `target`, `source`, `version`;
* критерии символьного скора (`SCORE_CRITERIA`), критерии аудио-блока
  (`AUDIO_SCORE_CRITERIA`), веса блоков (`SCORE_COMBINE`) — с явным полем
  `validated: false`;
* `src/metrics/extract.js` — единственное место, где отчёт превращается в
  числа по id (чтобы объявление и измерение не разъезжались).

Потребители переведены на реестр: `src/oracle/score.js` и
`server/music/compose/audio-score.js`. Числа не изменились — формула
смешивания зафиксирована тестом, комментарий приведён в соответствие с
кодом.

**Почему так.** Реестр — это не «бумага ради бумаги», а цена ответа на
вопрос «какой вес чем проверяется». Без общего места любой вес выглядит
одинаково доверенным, а это прямой путь к Goodhart.

**Проверка.** `npm run check:taste` требует: id уникальны, покрытие
экстракторами 100 %, суммы весов 100/100/1. Тест
`tests/unit/taste.test.js` сверяет, что веса в отчёте совпадают с
реестром, а формула смешивания даёт прежние числа (72 / 80 / 77.6).

**Остаётся.** `validated: false` у всех весов — до допуска Taste Model.

### D-064. Пара рождается вместе со своими признаками

**Контекст.** Дорожка H работала: человек слушал пары, выбирал победителя,
метка писалась в `preferences.jsonl`. Но метка содержала только хэши двух
треков — «победил вот этот». Обучение на таких данных невозможно в принципе:
нечем сравнивать победителя с проигравшим. Taste Model из брифа §7.4 была
невозможна не из-за нехватки данных, а из-за нехватки способа их
использовать.

**Решение.** Реестр пар `server/data/pairs.jsonl`. Пара кладётся в реестр в
момент создания вместе с **IR обеих сторон**, а не только с хэшами кода.
Отсюда:

* признаки пересчитываются из IR при обучении → смена состава признаков не
  убивает старые пары;
* аудио-признаки (L0) приходят с меткой из браузера: страница «Тиндер»
  меряет обе стороны тем же DSP-ядром, что и студия (LUFS, true peak,
  crest, клиппинг), и отправляет их вместе с выбором.

Хранение: `server/preference/ledger.js`. Маршрут `server/routes/preference.js`
стал тонким слоем над хранилищем (было 320 строк логики вперемешку с HTTP).

**Почему так.** Разделение «как хранится» и «как отдаётся по HTTP» нужно
было не для красоты: обучение (`server/taste/*`) читает те же данные из
того же места. Второй формат — это второй источник правды, а значит
источник расхождений.

**Проверка.** `tests/unit/taste-http.test.js` — сквозной путь: очередь →
пара с IR → метка с аудио → обучающий вектор признаков.

**Остаётся.** Прокси-пары (best-of-N) помечены `source: 'proxy'` и весят
≤ 0.2; в вердикт о допуске они не входят.

### D-065. Выученная цель допускается в скор только после leave-prompt-out CV

**Контекст.** Обучить модель можно на чём угодно; вопрос в том, можно ли
ей доверять. Бриф §7.4: в Score допускается только при CV-accuracy ≥ 60 % и
выше базовых линий («всегда-громче», текущий символьный скор) с 95 % CI,
и не используется при < 60 парах.

**Решение.** `src/taste/cv.js`:

* проверка — **leave-prompt-out**: целый промт уходит в тест, потому что
  пары одного промта не независимы (бриф §7.2), и обычная случайная
  разбивка дала бы модели подсказку;
* базовые линии обязательны и считаются на тех же парах;
* интервал — Уилсона (не нормальный: на малых n тот даёт неправдоподобные
  границы);
* вердикт объясняется словами: `reasons[]` — почему не допущено.

Пока допуска нет, веса символьного скора продолжают работать как есть, с
пометкой «не проверено на людях». Модель при этом обучается и сохраняется —
чтобы её можно было посмотреть глазами.

**Почему так.** Хорошая модель с плохой проверкой хуже, чем её отсутствие:
она молча уводит оптимизацию в сторону, проверенную ровно ноль раз.

**Проверка.** `npm run check:taste` — 20 проверок, включая «без живых пар
модель не допускается» и «при 40 парах не допускается».

**Остаётся.** На 14.11.2026 живых пар 0 → модель не допущена, вердикт
записан в `docs/evidence/taste/gate.json` и `docs/TASTE.md`.

### D-066. Данные меток изолированы каталогом STRUDEL_DATA_DIR

**Контекст.** Тесты дорожки H писали в настоящий
`server/data/preferences.jsonl`: файл сохранялся, стирался и
восстанавливался. Пока это работало, оно означало, что прогон тестов
рискует уничтожить метки владельца (при падении теста файл остаётся
удалённым), а параллельные тестовые файлы мешают друг другу: один стирает
файл, который только что записал другой.

**Решение.** Каталог данных переопределяется переменной окружения
`STRUDEL_DATA_DIR` (`server/preference/ledger.js` → `dataDir()`). Тесты
поднимают свой временный каталог. Значение по умолчанию — прежний
`server/data`.

**Почему так.** Метки — главный дефицит проекта. Делать так, чтобы
автоматический прогон тестов мог их потерять, — недопустимо.

**Проверка.** `tests/unit/preference.test.js` и `tests/unit/taste*.test.js`
работают во временных каталогах; `npm test` не трогает `server/data`.

**Остаётся.** Файлы `server/data/*.jsonl` и модель — вне git (см.
`.gitignore`).

### D-067. Сбойная мутация не должна рушить весь best-of-N

**Контекст.** `searchBest` защищал вызов оценки, но не вызов мутации.
Мутация `boostSection` выбирает секцию из `ir.sections`: если секций нет,
`pick` бросает исключение, и весь поиск падал целиком, а не выбывал один
кандидат.

**Решение.** Мутация обёрнута в `try/catch` (кандидат выбывает, остальные
оцениваются), а сама операция `boostSection` на пустом списке секций
возвращает описание вместо исключения.

**Почему так.** Поиск — рычаг «вычисления вместо надежды на удачный промт».
Один вырожденный план не должен отключать рычаг целиком.

**Проверка.** `tests/unit/taste.test.js` — прокси-пара строится из плана без
секций и не роняет выборку.

### D-068. Стороны пары рендерятся последовательно

**Контекст.** `src/tinder.js` готовил пару через
`Promise.all([renderCandidate(a), renderCandidate(b)])`. Оффлайн-рендер
переключает глобальный аудиоконтекст движка, поэтому параллельные рендеры
перехватывали контекст друг у друга: одна сторона выходила нормальной, вторая
— тихой (`lufsI = null`), а в консоли сыпалось 198 исключений
`InvalidAccessError` про разные аудиоконтексты. Подробно — E-014.

**Решение.** Стороны рендераются последовательно. Фрагмент пары сокращён с
16 до 8 тактов (16 секунд на сторону при 120 BPM).

**Почему так.** Оффлайн-рендер здесь — операция с глобальным состоянием, а
не чистая функция: параллелить её нельзя. Плюс выигрыш времени: 20 пар
укладываются в «6 минут в день», а не в 20 минут ожидания.

**Проверка.** `tests/unit/tinder-render.test.js` — guard-тест на исходник
(рендер последователен, фрагмент ≤ 20 с). Живой замер в браузере: обе
стороны дали LUFS −21.2 и −19.4, цель выравнивания −21.2 LUFS, консоль
без единой ошибки.

### D-069. Очередь пар продолжается, а не начинается заново

**Контекст.** `GET /api/preference/queue` всегда отдавал пары с нулевого
смещения. Каждый сеанс предлагал владельцу одни и те же первые двадцать
промтов — приёмка §7.2 (≥50 РАЗНЫХ промтов) была недостижима в принципе, а
рецензент вязался в одни и те же двадцать треков.

**Решение.** Смещение считает сервер: `nextQueueOffset()` берёт максимальный
индекс пары, по которой уже есть суждение, и очередь начинается со
следующей. Непройденные пары возвращаются, пройденные не повторяются.
Пусть клиент задаёт смещение явно — он может (нужно для отладки).

**Почему так.** Приёмка измеряет «сколько разных промтов услышано», а не
«сколько пар оценено». Счётчик покрытия (`labelCoverage`) теперь в отчёте
гейта и в строке прогресса на странице.

**Проверка.** `tests/unit/preference.test.js` — очередь сдвигается после
метки; `npm run check:taste` — в пуле 60 разных промтов (порог 50).

### D-070. Метка от рендера без сэмплов не идёт в обучение

**Контекст.** Если сэмплы не загрузились (сеть, CDN), трек звучит неполным:
без ударных или без пианино. Сравнение двух неполных треков учит модель не
тому. Но останавливать суждение из-за сбоя сети нельзя — тогда дорожка H
встаёт целиком.

**Решение.** Честная деградация: страница ждёт сэмплы, а если их нет —
помечает метку `degraded: true` и предупреждает рецензента. Метка
сохраняется (это труд человека), но в обучающую выборку не попадает:
`skipped.degraded` в `server/taste/dataset.js`.

**Почему так.** Данные не теряются и не портят модель. Требование «оба
набора на месте» проверяется чистой функцией `allSamplesReady`
(`src/samples-ready.js`), а не глазами.

**Проверка.** `tests/unit/samples-ready.test.js`,
`tests/unit/taste.test.js` (degraded-метка исключена из выборки).

### D-071. Метка проверяется по хэшам, а не только по id пары

**Контекст.** Реестр пар идентифицирует пару по `pairId`. Если коды треков
изменились (движок обновили, промты перегенерировали), старый `pairId`
указывает уже на другую пару — и модель обучалась бы на признаках одного
трека, сравнивая их с другим.

**Решение.** При сборке выборки хэши сторон метки сверяются с хэшами пары
(в любом порядке). Не совпали — метка помечается `skipped.stale` и в
обучение не идёт.

**Почему так.** Молчаливое обучение на неверных парах хуже, чем их
отсутствие: оно даёт правдоподобные, но бессмысленные числа.

**Проверка.** `tests/unit/taste.test.js` — метка с чужими хэшами
исключается.

## Фаза 3 — режим «Разбор» (Deep Dive)

Сессия «Producer's Deep Dive × Strudel AI Composer». Решения ниже — по результатам
замеров стенда (`docs/AUDIT.md`, 14.11.2026), проб на настоящем Strudel и кода
режима «Разбор» (`server/deepdive/`). Формат записи расширен по сравнению с
предыдущими фазами: добавлены **варианты**, **последствия и риски** и **статус** —
потому что часть решений (лицензии, домен, TTL) ждёт владельца.

### D-072. Железа хватает с ограничениями: без GPU, лимит RAM, режим «по кнопке»

**Контекст.** План владельца требовал выяснить железо до стройки (§10-A.4):
правило «GPU по требованию» не было закрыто. Замер сделан на боевом стенде
`root@34.88.114.146` (`docs/AUDIT.md` §6, `docs/ARCHITECTURE_MAP.md` §5.2):

| величина | сервер | машина владельца |
|---|---|---|
| CPU | 2 vCPU, Intel Xeon @ 2.20 ГГц | Ryzen 5 5500 (12 потоков) |
| RAM | 3.8 ГБ всего, ~2.7 ГБ доступно, **swap 0** | 15.9 ГБ |
| Диск | 38 ГБ, свободно **8.0 ГБ** | — |
| GPU | **нет** | NVIDIA GeForce RTX 2060, 8 ГБ |

**Варианты.** (а) арендовать или купить GPU-хост; (б) считать всё на CPU сервера;
(в) считать на машине владельца.

**Решение.** Вариант (б) с явными ограничениями. GPU на сервере нет и в текущем
объёме работ не закупается. RAM 3.8 ГБ при нулевом swap — жёсткий потолок:
разделение на стемы обязано идти сегментами, иначе OOM. Диск — 8 ГБ свободно:
Chromium и веса моделей помещаются впритык. Тяжёлые операции (разделение,
офлайн-рендер) — по кнопке или ночью, а не в общем потоке. Машина владельца
(RTX 2060) — отдельный продукт «Demucs на машине владельца»: её цифры нельзя
выдавать за серверные.

**Почему так.** «Хватает / не хватает» без цифр — гадание. Допущение A4 из
`docs/BRIEF.md:94` закрывается фактами: ресурсов хватает **с ограничениями**.
Бюджет на GPU не согласован, а «Demucs на CPU» — единственный вариант, который
можно проверить сегодня.

**Последствия и риски.** Разделение на CPU не укладывается в «вау за 60 с»
(точный p95 — предмет замера S2, который ещё не выполнен). Если S2 покажет
p95 > 3 мин, вопрос GPU возвращается владельцу (`docs/PARKING.md`). Диск впритык:
каждая новая модель, кэш или второй браузер требуют чистки.

**Проверка.** `docs/AUDIT.md` §6 (замеры), `docs/ARCHITECTURE_MAP.md` §5.2-5.3 и
§5 (A4 закрыт фактами).

**Статус.** принято.

### D-073. Офлайн-рендер живёт в headless-Chromium-воркере, бандл собирается при сборке образа

**Контекст.** На сервере нет ни Web Audio, ни `OfflineAudioContext` — это
Node-процесс. Значит, «отрендерить код в WAV» на сервере нельзя тем путём,
которым это делает студия в браузере.

**Варианты.** (а) `node-web-audio-api` в Node; (б) headless Chromium; (в) рендер
в браузере пользователя с загрузкой результата на сервер.

**Решение.** Вариант (б): отдельный воркер `server/deepdive/render/render-worker.mjs`
поднимает headless-Chromium, отдаёт страницу `render-page.html` с бандлом
`dist/render-bundle.js` и забирает WAV, метрики и события паттерна. Бандл
собирается esbuild'ом **на этапе сборки образа** (`npm run build:render`): в
рантайме esbuild'а нет, и воркер ничего не собирает на лету.

**Почему так.** Тот же движок (superdough + `@strudel/webaudio`), что и в студии:
иначе метрики двойника и метрики студии считались бы разными величинами.
Вариант (в) отдаёт расчёт клиенту — метрики перестают быть проверяемыми на
сервере, а «честность» становится декларацией.

**Последствия и риски.** В образе нужен браузер; headless Chromium ≈ 300-500 МБ
RAM при 3.8 ГБ у сервера. По `docs/BRIEF.md:71` это должен быть ОТДЕЛЬНЫЙ
контейнер с жёсткими лимитами CPU/RAM, чтобы не влиять на соседние сервисы.
Путь к браузеру задаётся через `CHROME_PATH` — иначе воркер не стартует, и режим
не должен молча деградировать в «пустой разбор» (`docs/DEEPDIVE_API.md` §1.4).

**Проверка.** `server/deepdive/render/render-worker.mjs` (шапка, выбор браузера,
сборка бандла), `server/deepdive/render/dist/render-bundle.js`,
`docs/DEEPDIVE_API.md` §1.4.

**Статус.** принято.

### D-074. Детерминизм рендера проверяется по расхождению, а не по байтам

**Контекст.** `docs/BRIEF.md:73` оставлял решение открытым: «Рендер повторяем
бит-в-бит в пределах одной платформы; между платформами сравнение с допуском
(maxAbsDiff ≤ 1e-4, |ΔLUFS| ≤ 0.05); решение — в DECISIONS». На одной платформе
детерминизм уже доказан побитово: `maxAbsDiff = 0`, `rmsDiff = 0`
(`docs/SPIKE-AUDIO.md` §H3, `tests/spike/browser/out-offline.txt`).

**Варианты.** (а) требовать байт-в-байт всегда; (б) сравнивать по допуску
расхождения; (в) не сравнивать прогоны вовсе.

**Решение.** Вариант (б). Критерий детерминизма — `maxAbsDiff ≤ 1e-4`
(и `|ΔLUFS| ≤ 0.05`) при ОДНОМ И ТОМ ЖЕ паспорте рендера `renderFingerprint`
(браузер, версия движка, ОС, sampleRate, sha256 кода). Байтовое сравнение
остаётся внутренним критерием одной платформы.

**Почему так.** При переносе WAV через 16-битное квантование один сэмпл из
1 536 000 может перевернуться ровно на 1 LSB (1/32768 = 3.05e-5). Это шум
квантования, а не расхождение звука; критерий «бит-в-бит» сделал бы метрики
несравнимыми между машиной владельца и сервером. Объём замера — 16 с рендера
(8 тактов при 120 BPM, 48 кГц, стерео): 768 000 кадров × 2 канала = 1 536 000
сэмплов.

**Последствия и риски.** Допуск 1e-4 не отличает «тот же звук» от «звук,
отличающийся на один LSB» — поэтому паспорт рендера обязателен: без него
расхождение нельзя интерпретировать, и две разные платформы дадут числа,
которые нельзя сравнивать.

**Проверка.** `docs/BRIEF.md:73` (допуск), `src/audio/render/offline.js`
(`compareRenders`: `maxAbsDiff`, `rmsDiff`), `docs/SPIKE-AUDIO.md` §H3.

**Статус.** принято.

### D-075. `cps` в Strudel — это `bpm/240`, а не `bpm/4`

**Контекст.** В Strudel один цикл = один такт = 4 доли. `setCpm(bpm)` — это
циклов в минуту, то есть `bpm/4` (см. D-010), а `cps` (cycles per second) —
циклов в секунду: `cps = bpm/240`. В коде студии `DEFAULT_CPS = 0.5` подписана
«120 BPM» — это сходится только с `bpm/240` (120/240 = 0.5), и не сходится ни
с чем другим. При этом комментарий в `src/audio/render/offline.js` утверждал
`cps = bpm / 4`, то есть описывал cpm, а не cps: расхождение в 60 раз внутри
одного файла.

**Варианты.** (а) переименовать константу в `cpm` и пересчитывать длительность;
(б) оставить `cps` и исправить комментарий; (в) не считать время самому, только
через `setCpm`.

**Решение.** Вариант (б). `cps` в проекте — всегда `bpm/240`. Комментарий
исправлен: длительность такта = `240 / bpm` секунд (как и считает
`server/deepdive/transpiler.js`). `cps = bpm/4` — это cpm, другое имя.

**Почему так.** Ошибка здесь не слышна — она тихо сдвигает весь трек по времени
и ломает сравнение с оригиналом на уровне сетки.

**Последствия и риски.** В коде студии встречается `setCpm(bpm/4)` (D-010) —
это другой путь, cpm; смешивать их нельзя. Внешние источники регулярно пишут
«cps = bpm/4» — это не переносить.

**Проверка.** `src/audio/render/offline.js:15` (`DEFAULT_CPS = 0.5` = 120/240)
и комментарий над ним; `tests/unit/render-wav.test.js:43` — то же определение
в тесте серверного рендера («cps — ЦИКЛЫ В СЕКУНДУ: 120 BPM → 0.5»); D-010
в этом же файле журнала.

**Статус.** принято.

### D-076. Свинг — это измеренный микротайминг, а не параметр `swingBy`

**Контекст.** Скил-карты предписывают `.swingBy(.12, 8)` для хэтов, и это надо
было проверить на настоящем движке. Проба `tests/spike/swing-semantics.probe.mjs`
(прогнана в этой сессии на Strudel 1.3.0) дала:

| вариант | событий за такт | что это |
|---|---|---|
| `s("hh*16")` | 16 | базовая сетка |
| `.swingBy(.12, 8)` | **24** | события ДУБЛИРУЮТСЯ |
| `.swingBy(.12, 4)` | 20 | то же |
| `.swingBy(.12, 16)` | 32 | то же |
| `.swing(.12)` | 16 | **no-op**: времена совпадают с базовой сеткой |

**Варианты.** (а) `.swingBy()`; (б) `swing(x)`; (в) измеренный микротайминг
`.late(ms(x))` внутри групп `.beat("шаги",16).gain()`.

**Решение.** Вариант (в). Свинг выражается ИЗМЕРЕННЫМ микротаймингом: удары
раскладываются в группы с их собственными шагами сетки, а измеренное отклонение
внутри шага — через `.late(ms(x))`. Ни `.swingBy()`, ни `swing(x)` не используются.

**Почему так.** `.swingBy` в 1.3.0 меняет КОЛИЧЕСТВО событий (16 → 24): ритм
двойника перестаёт быть измеренным ритмом трека. `swing(x)` без второго аргумента —
no-op: свинг просто исчезает, и это хуже, потому что ошибка не видна нигде.

**Последствия и риски.** Измеренный сдвиг округляется (шаг — до 1/16, сдвиг — до
5 мс), поэтому двойник не воспроизводит свинг побитово: остаток виден в метрике
`groove.swing_delta`. Проба привязана к версии движка: при смене Strudel её надо
перезапустить, иначе решение может устареть.

**Проверка.** `tests/spike/swing-semantics.probe.mjs` (таблица выше — вывод
прогона); `src/schemas/track-spec.schema.js` — поля `groups` с `lateMs`.

**Статус.** принято.

### D-077. Код-двойник строится в общем формате TrackSpec

**Контекст.** У студии две разные схемы плана (`docs/ARCHITECTURE_MAP.md` §2.2),
а «Улучшить», «Ещё вариант» и «Предложенные правки» работают с ПЛАНОМ, а не с
текстом кода. Чтобы двойник не жил в параллельном UI и отдельном компиляторе,
он должен быть обычным планом студии.

**Варианты.** (а) свой формат двойника + свой компилятор; (б) общий TrackSpec +
существующий компилятор.

**Решение.** Вариант (б). `server/deepdive/transpiler.js` строит каноническую
TrackSpec (`src/schemas/track-spec.schema.js`) и отдаёт её существующему
компилятору `server/music/compiler/index.js`. На выходе — план, код и отчёт
о принятых решениях.

**Почему так.** Тогда «Улучшить», «Ещё вариант» и «Предложенные правки»
работают с двойником бесплатно: они правят ПЛАН, а код пересобирается из него.

**Последствия и риски.** Двойник ограничен тем, что умеет выражать схема
TrackSpec. Измеренную величину, которую схема не покрывает, нельзя «протащить»
в код — придётся расширять схему (D-078). Это осознанное ограничение: лучше
план без числа, чем число без источника.

**Проверка.** `server/deepdive/transpiler.js` (шапка, раздел «ФОРМАТ»),
`src/schemas/track-spec.schema.js`, `server/music/compiler/index.js`.

**Статус.** принято.

### D-078. Расширения TrackSpec — только необязательные

**Контекст.** Двойнику нужно выразить то, чего в схеме раньше не было:
динамику отдельного удара, измеренный свинг, группы ударов с микротаймингом и
разные паттерны по секциям.

**Варианты.** (а) расширить схему обязательными полями; (б) добавить необязательные
поля; (в) завести отдельную схему для двойника.

**Решение.** Вариант (б). В TrackSpec добавлены НЕОБЯЗАТЕЛЬНЫЕ поля:
`part.gainPattern`, `part.swing`, `part.groups`, `part.sections` — все
`optional()`. Спеки без них компилируются как раньше: обратная совместимость
сохранена, существующий корпус и тесты не затронуты.

**Почему так.** Обязательные поля сломали бы валидность всего, что уже есть
(корпус, пресеты, тесты) и потребовали бы миграции. Необязательные поля дают
двойнику нужную выразительность и не трогают старую студию.

**Последствия и риски.** В проекте две схемы плана (`docs/ARCHITECTURE_MAP.md`
§2.2) — риск перепутать их; спасает то, что всё проверяется Zod'ом на входе.
Пустые или бессмысленные значения отсекаются схемой, а не «разумением» на
стороне LLM.

**Проверка.** `src/schemas/track-spec.schema.js` (все четыре поля — `optional()`),
`server/music/spec/check.js`.

**Статус.** принято.

### D-079. Внутри секции берётся доминирующий такт, и это написано в отчёте

**Контекст.** Формат секции в TrackSpec — ОДИН повторяющийся паттерн
(`arrange([cycles, CONST])`), а имена секций ограничены девятью значениями
(intro/verse/chorus/drop/build/breakdown/bridge/fill/outro). Bar-level вариация
внутри секции форматом не выражается.

**Варианты.** (а) усреднять удары по секции; (б) брать доминирующий (самый частый)
такт; (в) разбить секцию на подсекции.

**Решение.** Вариант (б). Внутри секции берётся ДОМИНИРУЮЩИЙ ТАКТ — самый частый
её рисунок (подпись «шаг:сэмпл»). На один шаг сетки — самый громкий удар; шаг
округляется до 1/16, сдвиг — до 5 мс. Ограничение записывается в отчёт
(`report.warnings`), а не прячется.

**Почему так.** (а) смешивает удары разных тактов и даёт фанк, которого в треке
нет. (в) ломает формат секции и требует расширения схемы секций. Для монтажей и
фанков с повторяющимся баром (а это ядро gold set) доминирующий такт — точное
попадание.

**Последствия и риски.** Для треков с постоянной вариацией двойник — приближение.
Число различных рисунков в секции полезно как индикатор: 1 — точное попадание,
>1 — приближение, и это должно быть видно в отчёте.

**Проверка.** `server/deepdive/transpiler/grid.js` — `buildGroupsForSection`
(комментарий «ОГРАНИЧЕНИЕ ФОРМАТА», подсчёт `barSignature`).

**Статус.** принято.

### D-080. Сравнение слоёв считается ОДНИМ И ТЕМ ЖЕ кодом в Node

**Контекст.** Оригинал — файл пользователя (стемы Demucs), двойник — наш
отрендеренный код. Сравнивать их надо одним кодом, иначе «разница» окажется
разницей реализаций, а не разницей треков.

**Варианты.** (а) считать метрики в Python; (б) считать в Node теми же модулями,
что и студия; (в) сравнивать на слух / A/B без чисел.

**Решение.** Вариант (б). `server/deepdive/compare.js` использует
`src/audio/dsp/onsets.js` (атаки, F-measure, корреляция огибающих),
`src/audio/dsp/mel.js` (log-mel, косинус) и `src/audio/dsp/loudness.js` (LUFS) —
те же модули, что и студия. Слой сравнивается только тогда, когда есть ОБЕ
стороны; отсутствующий слой — «нет данных» (`missing_layers`), а не ноль.
Общая оценка — средневзвешенное по тем слоям, которые реально измерены.

**Почему так.** Отсутствующий слой, посчитанный как 0, штрафует двойник за то,
чего в треке нет. Вокал не воспроизводится по построению (D-087) — это не
«0 % похоже», а отсутствие измерения.

**Последствия и риски.** Общее число между разными треками несопоставимо, если
у них разные наборы измеренных слоёв; поэтому в каждой записи метрик идут
`measured_layers` и `missing_layers`. Метод версионируется
(`deep-dive/compare@0.1.0`): смена формулы — смена версии, старые и новые числа
нельзя смешивать.

**Проверка.** `server/deepdive/compare.js` (шапка «ЧЕСТНОСТЬ», `LAYER_WEIGHTS`,
`missing_layers`), `docs/DEEPDIVE_API.md` §4 («сравнение невозможно → „нет
данных“, а не ноль»).

**Статус.** принято.

**Контекст.** Пайплайн разбора смешивает два стека. Node-часть студии уже умеет

**Проверка.** `server/deepdive/analysis/worker.py` (шапка: разграничение

### D-082. pip на сервере — только CPU-индекс PyTorch и без кэша

**Контекст.** Сервер без GPU, 3.8 ГБ RAM, 8 ГБ свободного диска. Обычный
`pip install demucs` подтягивает PyTorch с CUDA-колёсами (порядка 5 ГБ) — они
не влезают в диск и в рантайме не используются.

**Варианты.** (а) обычный `pip install`; (б) CPU-индекс PyTorch + `--no-cache-dir`;

**Решение.** Вариант (б): PyTorch ставится только с CPU-индекса

**Почему так.** 8 ГБ диска и 3.8 ГБ RAM — не место для CUDA-колёс, которые
никогда не запустятся; кэш pip при 8 ГБ — та же проблема в миниатюре.

**Последствия и риски.** Правило зафиксировано как требование к установке, но

Цифра «~5 ГБ» — оценка по составу CUDA-колёс, фактический объём подтверждается
установкой на сервере. Если появится GPU-хост, правило пересматривается.

**Проверка.** `docs/AUDIT.md` §6 (диск и RAM сервера), `docs/LICENSES.md` §1

**Долг.** Рецепт установки в репозитории не зафиксирован: команда описана здесь
и должна быть перенесена в скрипт/документ развёртывания образа.

**Статус.** принято.

### D-083. Лицензионная политика режима «Разбор»: NC/AGPL не подключаем, Demucs — по флагу

**Контекст.** Реестр `docs/LICENSES.md`. Правило стека: по умолчанию только
MIT/BSD/ISC/Apache. Самая частая ошибка в таких проектах — посмотреть лицензию
КОДА и забыть про ВЕСА: у Demucs код — MIT, а веса «provided only for scientific
purposes» (формулировка автора, `docs/LICENSES.md` §1).

**Варианты для Demucs.** (а) использовать `htdemucs` как есть; (б) не использовать
разделение вовсе; (в) использовать, но в коммерческом режиме — не по умолчанию.

**Решение.** По умолчанию НЕ подключаем Essentia (AGPL-3.0, модели CC BY-NC-SA),
madmom (BSD, модели NC), ADTOF (CC BY-NC-SA) и любые NC/AGPL-компоненты.
Demucs: код — MIT (использовать можно), но ВЕСА имеют ограничение «только для
научных целей» → в коммерческом режиме разделение на стемы по умолчанию ВЫКЛЮЧЕНО
и включается явным флагом, а в отчёте ставится пометка, что стемы получены
моделью с неясным коммерческим статусом весов. Разделение кода и весов — это
разные лицензии, и проверяются они отдельно.

**Почему так.** AGPL на сетевом сервере обязывает публиковать исходники сервиса.
NC-модели закрывают коммерческий путь целиком. Формулировка «только для научных
целей» не является разрешением на коммерческое использование.

**Последствия и риски.** Без стемов режим «Разбор» теряет второй «вау» (карту
аранжировки) и часть метрик: слои «ритм» и «бас» помечаются «нет данных», а не
выдумываются. Коммерческий статус Demucs-весов остаётся за владельцем
(`docs/LICENSES.md` §5, пп. 1 и 8). Общий вопрос «будет ли студия коммерческой»
меняет почти весь список стека — он задан первым.

**Проверка.** `docs/LICENSES.md` §1-2 и §5; `docs/DEEPDIVE_API.md` §1.1
(`separate` по умолчанию `0`).

**Статус.** принято (политика по умолчанию); коммерческий статус Demucs-весов —
решение владельца.

### D-084. Приватность: аудио не покидает сервер, отчёт отдаётся по токену

**Контекст.** Принцип P4 промта миссии: «Private by default» — аудио видит
только владелец, TTL хранения, удаление по запросу; приватная ссылка — ТОЛЬКО
производные данные (метрики, карта, рецепты, код), без чужого аудио и стемов.

**Варианты.** (а) хранить аудио постоянно; (б) временная папка + TTL + токен
на производные; (в) отдавать ссылку с самим отчётом и аудио.

**Решение.** Аудио пользователя не покидает сервер: оригинал и стемы живут во
временной папке задачи и удаляются по TTL — предлагаемое значение 7 дней
(§7 промта; точное значение требует подтверждения владельцем). Доступ к отчёту —
по ссылке с токеном, и по ссылке отдаются ТОЛЬКО производные данные: измерения,
карта секций, рецепты, код, метрики. Производные данные (темп, лад, структура)
можно выгружать отдельно по явному действию пользователя. Удаление — по запросу,
не дожидаясь TTL.

**Почему так.** Ссылка с аудио внутри — это ссылка на чужой трек; минимальный
принцип: в ссылке только числа и код, аудио остаётся на сервере и умирает само.

**Последствия и риски.** TTL 7 дней — предложение, а не факт; короткий TTL означает,
что ссылка на разбор перестаёт работать. Кэш по хэшу файла конфликтует с TTL:
закешированный хэш не должен продлевать жизнь аудио — это надо реализовать и
проверить. Наличие токена — не замена аутентификации: доступ по ссылке по смыслу
равен публикации производных данных.

**Проверка.** `docs/DEEPDIVE_API.md` (принцип 4 «Private by default», §2 —
состав `payload`), `docs/DEEPDIVE_API.md` §1.1 (поле `file`).

**Статус.** предложено (TTL 7 дней — значение по умолчанию из плана; требует
подтверждения владельцем).

### D-085. Дефолты режима: русский язык, MIDI в обе DAW, некоммерческий режим, self-hosted

**Контекст.** §6-S6 промта: «Решения с дефолтами (не блокируйся, зафиксируй в
DECISIONS.md, владельцу — на подтверждение)». Часть дефолтов не выбирается, а
констатирует текущую реальность.

**Варианты.** По языку — RU/EN; по DAW — MIDI-экспорт / `.als`+`.flp`; по режиму —
коммерческий/некоммерческий; по домену — текущий `IP.sslip.io` / нормальный домен.

**Решение.** Дефолты режима «Разбор»:

| что | дефолт | статус |
|---|---|---|
| язык интерфейса и отчётов | **русский** | принято |
| DAW | поддержка обеих веток (Ableton и FL Studio) через **MIDI-экспорт**, без `.als`/`.flp` | принято |
| коммерческий режим | **некоммерческий** по умолчанию, при этом стек остаётся без NC/AGPL | принято |
| домен | **self-hosted**, текущий прод `music.34.88.114.146.sslip.io` | принято (констатация факта) |
| публичный SaaS-домен | решение владельца позже | открыто |

**Почему так.** Язык RU — владелец русскоязычный, отчёты читает он.
MIDI — единственный формат, который переносится и в Ableton, и в FL Studio
перетаскиванием; `.als`/`.flp` — проприетарные и требуют своего формата.
Некоммерческий режим при стеке без NC/AGPL не запирает дверь к монетизации:
в стеке нет компонента, который пришлось бы выбрасывать при смене режима.
Домен `IP.sslip.io` снижает доверие (`docs/AUDIT.md` §7), но менять его — решение
владельца, а не наше.

**Последствия и риски.** `shveyka-igolka.ru` не резолвится ни с сервера, ни с
машины — вопрос DNS к владельцу (`docs/AUDIT.md` §7). Публичный домен стоит
поднять до первого публичного демо — это в парковке, не в этой фазе.

**Проверка.** `docs/AUDIT.md` §7 (домен), `docs/DEEPDIVE_API.md` §3 (правила UI).

**Статус.** принято, кроме публичного домена — открыто.

### D-086. Baseline двойника снимается ДО улучшений, итерации сравниваются с baseline

**Контекст.** §3.3 (шаг 9) и §9.1 промта: «baseline записать ДО улучшений», «каждое
улучшение подтверждается цифрой». Плюс P7: LLM не слушает аудио — он получает
JSON измерений и пересказывает/кодит по ним.

**Варианты.** (а) сравнивать итерацию с предыдущей итерацией; (б) сравнивать
каждую итерацию с baseline; (в) сравнивать только по вкусовому впечатлению.

**Решение.** Baseline-метрики двойника снимаются ДО любых LLM-улучшений
(итерация 0, `label: "baseline"`). Каждая итерация LLM-цикла сравнивается с
baseline, а не с предыдущей итерацией. Модель получает ТОЛЬКО JSON измерений и
метрик и не может добавлять числа: числа, которых нет во входе, в отчёт не
попадают.

**Почему так.** «Улучшение» относительно предыдущей итерации может быть
деградацией относительно baseline — и это видно только при сравнении с
baseline. Модель, которая «добавляет» числа, ломает измеримость: правка,
придуманная ею, неотличима от измеренной.

**Последствия и риски.** Если baseline не снят, метрики итераций бессмысленны:
пайплайн обязан остановиться с честной ошибкой, а не продолжать «улучшать»
неизвестно что. Сравнение с baseline не отменяет лог итераций (что изменено,
метрики до/после) — он остаётся в отчёте по каждой итерации.

**Проверка.** `docs/DEEPDIVE_API.md` §1.2 (модель получает только JSON измерений
и метрик), §2 (`code_twin.metrics[]` с `iteration: 0, label: "baseline"`),
§4 (ошибки не молчат).

**Статус.** принято.

### D-087. Вокал и точное сведение не воспроизводятся — и это пишется в каждом отчёте

**Контекст.** P3 и §3.2 промта: «ориентир, не клон», вокал не воссоздаём.
`server/deepdive/transpiler.js` фиксирует и остальные ограничения: в Strudel
нет portamento/glide (в реестре публичного API его нет — есть только legato,
меняющий длительность, а не высоту), тембр задаётся синтезатором, а не сэмплом
оригинала.

**Варианты.** (а) обещать клон; (б) обещать скелет и писать ограничения в отчёт;
(в) промолчать об ограничениях.

**Решение.** Вариант (б). Продукт — «узнаваемый скелет трека в коде», а не клон.
Вокал, точное сведение и мастеринг НЕ воспроизводятся. Ограничение фиксируется
в отчёте КАЖДОГО разбора — обязательный блок `honesty.caveats`, минимум:
«вокал не воспроизводится», «точное сведение и мастеринг не воспроизводятся»,
«это ориентир по измеримому скелету, не клон трека».

**Почему так.** Продукт, который обещает больше, чем умеет, разрушает доверие
сильнее, чем скромный «ориентир». Ограничение в отчёте — это одновременно
честность и защита от ложных ожиданий; скрытое ограничение всплывает на первом
же публичном сравнении.

**Последствия и риски.** Метрики похожести не равны «похоже на слух»: тембр и
сведение не воспроизводятся по построению, поэтому потолок log-mel cosine
ограничен, и слепый A/B остаётся обязательной проверкой, а не украшением.

**Проверка.** `docs/DEEPDIVE_API.md` §2.2 (`honesty.caveats` обязателен),
`server/deepdive/transpiler.js` (шапка, «ГЛАВНОЕ ОГРАНИЧЕНИЕ»).

**Статус.** принято.

### D-088. Загрузка файла — отдельный multipart-маршрут с отдельным бюджетом

**Контекст.** Аудит нашёл два блокера приёмки файла: `express.json` с лимитом
100 KB (`server/index.js:91`) — трек через JSON не пройдёт; общий rate limit
`/api` = 20 запросов/мин на IP (`server/index.js:80-89`) — загрузка и SSE-поток
разбора упрутся в этот лимит, причём он общий со «швейкой» и студией.

**Варианты.** (а) поднять общие лимиты `/api`; (б) отдельный маршрут и отдельный
бюджет для `/api/deepdive/*`; (в) принимать файл base64 внутри JSON.

**Решение.** Вариант (б). Разбор принимает файл только как `multipart/form-data`
на `POST /api/deepdive/analyze` (лимит 100 МБ, длительность ≤ 10 мин), у
`/api/deepdive/*` свой бюджет rate-limit, не общий с остальным API. Проверка
типа — по содержимому, не по расширению.

**Почему так.** Общий лимит 20 req/min рассчитан на лёгкие запросы студии.
Разбор — одна долгая операция с потоком событий; поднимать общий лимит значит
разрешить ему вытеснять обычных пользователей студии. Вариант (в) упирается в
лимит 100 KB и в base64-раздувание.

**Последствия и риски.** Маршрута в коде пока нет — контракт зафиксирован в
`docs/DEEPDIVE_API.md` §1.1, реализация в долгу. Изоляция: ffmpeg/ffprobe
должны работать в песочнице без сети с лимитами CPU/RAM/времени (§11 промта).

**Проверка.** `docs/AUDIT.md` §7 (пункты 2 и 3), `server/index.js:79-91`,
`docs/DEEPDIVE_API.md` §1.1.

**Статус.** принято (контракт); реализация маршрута — долг.

### D-089. CPU-only — осознанное отклонение правила «p95 > 3 мин → GPU»

**Дата: 14.11.2026. Решение владельца. Не пересматривать без нового запроса.**

**Контекст.** План проекта содержал правило: если p95 ожидания превышает
3 минуты — поднимаем GPU. Замер на боевом стенде (2 vCPU, 3.8 ГБ RAM, GPU
нет) дал: `htdemucs` — 3.45–6.6 × realtime (60 с аудио → 207–396 с; 240 с
аудио → 1356 с), `htdemucs_ft` — 22.3 × realtime (60 с аудио → 1336 с). По
этому правилу вопрос GPU возвращался владельцу (D-072, `docs/PARKING.md`).

**Решение.** GPU не берём. Разделение на стемы — честный фоновый режим:
пользователь заранее видит оценку времени, задача живёт на сервере без
открытой вкладки, а вторая тяжёлая задача ждёт в очереди. Время ожидания не
критично, бюджет — 0.

**Почему так.** Это осознанный выбор владельца, а не упущение: платить за
GPU-инстанс ради режима, которым пользуются нечасто, невыгодно, а
ожидание в фоне для этого продукта приемлемо. Правило «p95 > 3 мин → GPU»
с этого момента **не действует**: оно было написано под предположение, что
у разбора есть потолок ожидания. Потолка нет — есть честная оценка и
механизм, который не даёт двум тяжёлым задачам столкнуться (D-091).

**Отклонение от плана — это зафиксировано здесь намеренно.** Будущие сессии
не должны «исправлять» это обратно: если правило снова начнут применять,
это будет означать, что решение владельца отменили, а не что забыли
прочитать. Смена решения возможна только по прямому запросу владельца.

**Последствия и риски.** Разбор со стемами на 4-минутном треке занимает
~27 минут (верхняя оценка по худшему замеру). «Быстрый разбор» в интерфейсе
невозможен — значит, вход в режим должен честно называть время. Риск
другого рода: долгий разбор на 3.8 ГБ RAM без страховки упирается в OOM —
поэтому мьютекс и swap обязательны (D-091).

**Проверка.** `src/deepdive/estimate.js` (коэффициенты только из замеров),
`docs/SESSION_REPORT.md` §4 и §8, `docs/PARKING.md` (GPU-хоста больше нет в
списке «нужно решение»).

**Статус.** принято владельцем 14.11.2026; действует.

### D-090. Время в интерфейсе — честная оценка по худшему замеру, а не «примерно»

**Контекст.** На CPU разделение занимает десятки минут. Прежний интерфейс
показывал один спиннер и этапы без времени, а паспорт трека (темп, лад,
громкость) приходил только вместе с финальным результатом — то есть через
полчаса, хотя измерения были готовы через секунды.

**Решение.**

1. **Оценка считается по длительности трека и по ВЕРХНЕМУ замеру**
   (6.6 × realtime, округление вверх до целых минут). Для 4-минутного трека
   это ~27 минут, а не «~15 минут». Показывается диапазон: нижняя граница —
   лучший замер (3.45 ×), верхняя — худший.
2. **Паспорт приходит сразу**, отдельным событием `passport`, ДО разделения
   на стемы. Измерения видны за секунды; стемы — потом.
3. **Прогресс идёт по этапам**, а не одним спиннером; у долгого этапа есть
   обратный отсчёт «осталось ~N мин», который пересчитывается на клиенте.
4. **Тексты нейтральные**: описывают, что происходит. Никаких обещаний
   качества и никаких «стоит того».
5. **«Высокое качество» (`htdemucs_ft`) — спрятан** под «экспериментальный
   ночной режим» с честной оценкой (22.3 × realtime, ~90 минут на
   4-минутный трек) и с пометкой, что память поджимается.
6. **Задача переживает вкладку**: результат пишется на диск, доступен по
   прямой ссылке `/razbor/<job-id>` (без аккаунтов), а после обрыва SSE
   клиент получает текущее состояние задачи по `GET /api/deepdive/jobs/:id`
   и доводит разбор до конца.

**Почему так.** «Быстро» без цифр — это обещание, которое на этом железе не
сдерживается, и именно оно убивает доверие сильнее, чем честное «27 минут».
Разница между «~15 минут» и «14–27 минут по замерам» — это разница между
маркетингом и продуктом. Паспорт за секунды вместо получаса — это и есть
то, ради чего пользователь вообще открывает разбор.

**Последствия и риски.** Оценка — модель по замерам, а не обещание: при
другой нагрузке сервера реальное время может отличаться. Поэтому диапазон
показывается вместе с основанием («верхняя граница по худшему замеру»), а
не одно число. Пермилинк открывает результат только после завершения
задачи: незаконченная задача после перезапуска сервера пропадает, и клиент
об этом говорит прямо, а не показывает пустую страницу.

**Проверка.** `src/deepdive/estimate.js`, `tests/unit/deep-dive-estimate.test.js`
(27 минут для 4 минут аудио — как отдельный тест), `server/routes/deepdive.js`
(события `job`/`passport`), `src/deepdive/api.js` (реконнект по GET),
`docs/DEEPDIVE_API.md` §1.1.

**Статус.** принято; реализовано и измерено на проде 14.11.2026.

### D-091. Защита от OOM — механизм (мьютекс + очередь), а не правило

**Контекст.** На сервере 3.8 ГБ RAM. `htdemucs` в одиночку занимает ~1.75 ГБ
и помещается, но разбор и сборка образа одновременно — это OOM (замер:
rc=137, ядро убило Demucs на 29-й секунде). «Не гонять разбор и деплой
одновременно» было написано в отчёте как правило — но правило держится
только на памяти читателя.

**Решение.** Три механизма вместо правила:

1. **Мьютекс тяжёлых операций (flock).** Python-воркер берёт `heavy.lock`
   (`fcntl.flock`) вокруг запуска Demucs. Файл лежит в общем томе с хостом,
   поэтому блокировка работает и между процессами, и между контейнерами.
2. **Очередь разделения с concurrency = 1.** Вторая задача не начинает
   тяжёлую работу, а ЖДЁТ — со статусом «в очереди», который видит
   пользователь. Мьютекс задачи (`job.lock`) держит приложение: пока идёт
   разбор со стемами, деплой не может пересоздать контейнеры и убить Demucs
   на середине.
3. **Деплой берёт те же локи.** `deploy/deploy-server.sh` перед сборкой
   ждёт завершения текущих разборов (маркеры `running/`), берёт `job.lock`
   и `heavy.lock` и собирает образ под ними. Нарушить «не деплоить во время
   разбора» механически невозможно: либо деплой ждёт, либо новый разбор
   ждёт.

**Swap — страховка, а не основа.** Добавлено 4 ГБ swap
(`fallocate -l 4G /swapfile`, `chmod 600`, `mkswap`, `swapon`, запись в
`/etc/fstab`, `vm.swappiness=10`). Swap не даёт задачам умереть; мьютекс не
даёт им столкнуться. Правило «мьютекс — основное, swap — страховка»
зафиксировано здесь, чтобы порядок не перепутали.

**Почему так.** Пользователь не может выполнить правило «не деплоить во
время разбора» — он не знает, что деплой идёт, и не обязан знать. А
разработчик, который «не помнит», — это тот же класс проблем. Механизм
живёт в коде и одинаково работает для всех.

**Последствия и риски.** Разборы со стемами выстраиваются в очередь: если
две задачи пришли одновременно, вторая ждёт (это видно и честно сказано).
Деплой при живом разборе ждёт до `LOCK_WAIT_S` (по умолчанию 2 часа) и
потом отменяется с понятным сообщением. Цена swap — 4 ГБ диска: свободно
стало 5.4 ГБ вместо 9.4 ГБ, и это надо отслеживать (диск и так впритык).

**Проверка.** `server/deepdive/lock.js`, `server/deepdive/queue.js`,
`server/deepdive/analysis/ddworker/http.py` (`heavy_lock`),
`deploy/deploy-server.sh`, `deploy/docker-compose.strudel.yml` (том
`/opt/dd-lock`), `tests/unit/deep-dive-queue.test.js` (очередь и мьютекс),
замер двух параллельных запусков на сервере — `docs/SESSION_REPORT.md` §3.

**Статус.** принято; реализовано и проверено на сервере 14.11.2026.

### D-092. Хоп в Python-воркер — без встроенных таймаутов HTTP-клиента

**Контекст.** Разделение на стемы идёт через Python-воркер по HTTP. Клиент
ходил туда глобальным `fetch` — это undici, у которого есть собственные
дефолты: `headersTimeout` = 300 с и `bodyTimeout` = 300 с. Воркер отвечает на
`/separate` ОДНИМ ответом — после конца Demucs, а это на 2 vCPU 13–20 минут.
То есть встроенный таймаут клиента срабатывал ЗАДОЛОГО до результата: задача
заканчивалась ошибкой «Сервис анализа недоступен: fetch failed», стемов не
было, метрик не было — при том, что Demucs продолжал работать и через 14
минут отдавал `200` (замер в логе воркера: старт 19:52:12, ответ 20:12:27,
1214 с).

**Решение.** Клиент воркера ходит через `node:http`/`node:https`
(`server/deepdive/analysis/client.js`). У клиента Node таких дефолтов нет:
единственный таймаут — тот, что задаёт вызывающий (для разделения — 3 ч).
Отдельно зафиксировано: таймаут ответа воркера не должен быть короче худшего
замера Demucs. 300 с — это не «страховка от зависания», это тихое уничтожение
результата.

**Почему так.** Таймаут транспорта — не страховка, а молчаливая потеря работы:
работа сделана, а её выбросили. Явная ошибка («разделение не удалось») лучше
пустого результата с ложными «нет данных».

**Последствия и риски.** Реальное время разделения на 4-минутном треке —
13–20 минут, и клиент это держит. Побочный эффект: зависший воркер будет
висеть до своего таймаута (3 ч) — это осознанно, Demucs должен останавливаться
мьютексом и дедлоком, а не молчанием сокета.

**Проверка.** `tests/unit/deep-dive-worker-client.test.js` — клиент не
использует `fetch`, длинный ответ доезжает целиком, собственный таймаут
обрывает ожидание. Замер на проде — `docs/SESSION_REPORT.md` §5.2.

**Статус.** принято; реализовано и измерено на проде 14.11.2026.

### D-093. Имена сэмплов в разборе — только из реестра банков

**Контекст.** Транспайлер разбора переводит ноты General MIDI в имена сэмплов
Strudel по таблице `GM_TO_SAMPLE`. В таблице стояли `oh`, `crash`, `ride` и
`rim` — **таких имён в банке `dirt-samples` нет** (в реестре банков есть
`808oh`, `cr`, `perc`). Сэмпла нет — нет и звука: движок бросает «sound oh
not found! Is it loaded!» и падает весь рендер двойника, а вместе с ним — все
метрики похожести.

**Решение.** Справочник приведён к реестру банков
(`server/music/data/sample-banks.json`): открытый хайхет — `808oh`, тарелка —
`cr`, для ride и rim берутся существующие имена. Добавлен резолвер
`sampleNameForHit`: он берёт имя по ноте GM, затем метку удара (если она есть
в банке), иначе `perc` — и **не может** вернуть имя вне банка. Тест сверяет
справочник с реестром.

**Почему так.** Тот же принцип, что и в промптах студии (`oh` и `sh` были
убраны оттуда): имя сэмпла — это ссылка на файл, и ссылка обязана
проверяться автоматически, а не глазами. Один несуществующий сэмпл убивал весь
разбор, а страница выглядела «просто пустой».

**Проверка.** `tests/unit/sample-names.test.js` (сверка справочника и
резолвера с реестром банков), `tests/unit/deep-dive-transpiler.test.js` (код
исполняется в настоящем движке и даёт события).

**Статус.** принято; реализовано и измерено на проде 14.11.2026.

### D-094. Главная страница — обложка, студия живёт на `/studio.html`

**Контекст.** До 15.11.2026 корень сайта (`/`) отдавал студию: три колонки,
шесть панелей в левой, около 30 кнопок, из которых на первом экране видны
четыре с неочевидными названиями («🧩 Спланировать и собрать», «🎲 Ещё
вариант», «🧬 Варианты плана», «🛠 Починить по разбору»). Новый человек видит
пустой редактор кода в центре, микшер справа и журнал внизу — то есть
инструмент, а не результат. Проверка живого прод-сайта 15.11.2026
(`https://music.34.88.114.146.sslip.io/`) это подтвердила: 69 интерактивных
элементов на странице, из них 4 в зоне первого взгляда, ни одного намёка, что
делать сначала.

При этом режим «Разбор» — вторая вкладка той же страницы — умеет объяснить
себя одной фразой: «Загрузите трек: сервер измерит темп, лад, громкость,
структуру и слои, соберёт из измеренного скелета код-двойник и сравнит его с
оригиналом. Каждое число — измерение, а не догадка». Лучший текст продукта
был спрятан за вторым табом.

**Решение.** Разделить две поверхности на две страницы:

* `/` — обложка: одно обещание, одно действие (поле описания + кнопка
  «Создать трек»), четыре кликабельных примера, объяснение, чем продукт
  отличается, и честный блок ограничений. Страница не тянет движок Strudel:
  генерация живёт в студии, обложка только зовёт.
* `/studio.html` — рабочая студия (бывший корень).
* `/tinder.html` — страница суждения: инструмент рецензента, не продукт.

Обложка не тянет `src/main.js` и движок: `dist/assets/main-*.js` весит
~99 КБ, а `strudel-engine` — ~713 КБ. На обложке это не нужно.

**Почему так.** Два разных продукта («описал и услышал» и «разбери чужой
трек») с разными аудиториями, разными скоростями (5 секунд против 35 секунд
паспорта и 14–27 минут со стемами) и разными сценариями нельзя показывать
одной страницей: либо виден бенч, и теряется результат, либо виден результат,
и теряется бенч.

**Последствия и риски.** Ссылки на треки (`#c=…`) строятся от
`location.pathname` (`src/core/share.js`), поэтому после переезда они
автоматически указывают на `/studio.html#c=…` — менять ничего не пришлось.
Маршрут `/studio.html` отдаётся сервером как есть: `express.static` +
fallback на существующий `.html` в `dist/` (`server/index.js`). Старые ссылки на
`/` со студией теперь ведут на обложку — это осознанно: старый `/` был
нечитаемой страницей, и возврат к ней ничего не улучшает.

**Проверка.** `npm run build` — в `dist/` появляются `index.html`,
`studio.html`, `tinder.html`; живая проверка обеих страниц в браузере.

**Статус.** принято; реализовано 15.11.2026.

### D-095. Студия перестроена в три шага с прогрессивным раскрытием

**Контекст.** В студии 30 кнопок и 6 панелей, и все они видимы сразу. Это
плохо по двум причинам. Первая — когнитивная: человеку нужно решить, из чего
начать, а вариантов тридцать. Вторая — инженерная: то, чем пользуются редко
(план композиции, IR-трансформации, пресеты, журнал), занимает место
экранного внимания, которого не хватает результату.

**Решение.** Студия разложена на три шага, между которыми можно ходить
кнопками в шапке шагов:

1. **Опишите** — крупное поле описания, одна главная кнопка «Создать трек»,
   четыре примера в один клик. Режим генерации и альтернативные пути
   («Спланировать и собрать», «Ещё вариант», «Варианты плана») убраны под
   раскрывающийся блок «Другие способы».
2. **Слушайте** — визуализация партий во всю ширину, оценка трека с
   замечаниями по измерениям и четыре действия с понятными названиями:
   «🎼 Разобрать трек», «🛠 Исправить по замечаниям», «🎲 Сравнить два
   варианта», «🎲 Ещё вариант».
3. **Правьте** — редактор кода, микшер, «попросить правку», панели плана и
   истории. По умолчанию скрыты; открываются кнопкой «Показать код».

Переход 1→2 происходит сам после успешной генерации (событие
`studio:track-ready`), 2→3 — по кнопке. Параметры адреса `?prompt=…&autogen=1`
подставляют описание и запускают генерацию: обложка ведёт в студию по этой
ссылке, поэтому путь «описал → услышал» не прерывается перезагрузкой.

**Почему так.** Первое действие должно быть единственным, а следующий шаг
должен наступать сам. Прятать нужно не «лишние функции», а то, что нужно
редко: функции не исчезают, они перестают конкурировать за внимание.

**Последствия и риски.** Ни один `id` не переименован и не удалён — вся
существующая разметка и JS-привязки остались в силе, поэтому поведение
движка, разбора и разметки не менялось. Ничего не удалено из проекта: шаг 3
содержит весь прежний интерфейс целиком, включая журнал и пресеты.

**Проверка.** `npm test` (854 теста) и `npm run build` — зелёные; живая
проверка: обложка → «Создать трек» → студия с подставленным описанием →
генерация → переход на шаг «Слушайте».

**Статус.** принято; реализовано 15.11.2026.

### D-096. Позиционирование: массовая аудитория, но с честным блоком ограничений

**Контекст.** Решение владельца 15.11.2026: продукт адресуется широкой
аудитории («генератор музыки как Suno»), а не нише битмейкеров и не
портфолио-кейс для LLM-инженеров. Это меняет требования к первой странице:
обещание должно читаться за три секунды, а первый экран — приводить к
результату за один клик.

**Решение.** Обложка построена как путь «описание → результат»: одно поле,
одна кнопка, четыре примера. Одновременно на обложке есть блок «Честно о
границах»: нет вокала, это не мастеринг, оценка по метрикам — не вкус. Ссылки
на «Разбор чужого трека» (режим с честной оценкой 14–27 минут со стемами)
вынесены во второй блок и помечены как инструмент для продюсеров.

**Почему так.** Продукт, который обещает то, чего не умеет, получает первую
отрицательную оценку от первого же пользователя, и никакая последующая
работа её не отменит. Честный блок ограничений стоит дешевле рекламации и
работает на доверие, которого у нового продукта нет. Кроме того, честность —
это ровно то, чем этот продукт отличается: «каждое число — измерение, а не
догадка» должно быть видно сразу, а не после регистрации.

**Последствия и риски.** Массовая аудитория упирается не в интерфейс, а в
качество звука: сэмплы и синтезаторы дают узнаваемый, но не «студийный»
результат. Это отдельная работа (D-089: GPU не берём; качество улучшается
составом сэмплов и разбором, а не железом) и в этой сессии не решалась.
Настоящий потолок зафиксирован в презентации: «7.3 из 10 — сильный
инженерный проект, средний продукт».

**Статус.** принято; реализовано 15.11.2026.

### D-097. Локальные вычисления разрешены: тяжёлое считается на машине владельца

**Контекст.** D-089 закрыл покупку серверного GPU: 2 vCPU Xeon дают 207–396 с
на 60 с аудио (`htdemucs`), а `htdemucs_ft` — 1336 с (22.3× realtime), то есть
сервер физически не тянет ни разбор, ни ночной завод. Владелец открыл другое
условие: LLM остаётся облачным (ключ с запасом), а **рендер, сепарация и
анализ идут на машине владельца**. Это не отмена D-089, а другое направление
работы: деньги тратятся не на сервер, а на железо, которое уже есть.

**Решение.** Разделяем вычисления по границе:
- **LLM — в облаке**, через существующий `server/llm/router.js`. Ключ живёт в env
  демона или сервера (выбор фиксируется при сборке демона), в репозитории ключей
  нет, `check:secrets` это проверяет.
- **Рендер, сепарация, анализ — на машине владельца.** Тот же движок Strudel и тот
  же DSP: `renderFingerprint` и детерминизм (maxAbsDiff = 0 между прогонами)
  сохраняются. Рендер идёт через headless Chromium (`playwright-core`), браузер
  ищется через `CHROME_PATH` — на машине владельца проверено: Chrome стоит в
  `C:\Program Files\Google\Chrome\Application\chrome.exe`.
- **Сервер — витрина, оркестрация и L2-игра** (всё, что живёт меньше минуты).

**Альтернативы.** (1) Аренда GPU — отклонена владельцем ранее (D-089). (2) Один
изменяемый «тяжёлый» слой на сервере — отклонена: 22× realtime означает 1356 с на
4-минутный трек, это неприемлемо. (3) Всё локально, включая LLM — отклонена:
модель на машине владельца означает менять стек и тащить рантайм.

**Последствия и риски.** Появляется отдельный пакет `local/` в репозитории:
очередь задач, WebSocket-мост, авторизация по токену, офлайн-режим (демон живёт
без сервера). Прямое следствие для продукта: цикл «спросил → услышал» становится
возможным — сейчас 56.4 минуты на трек делают его невозможным. Цена: демон надо
поддерживать на чужой ОС, и у первого пользователя его нет. Гейт фазы B: first-twin
≤7 мин локально, полный трек ≤15 мин, бит-в-бит совпадение fingerprint с сервером.

**Статус.** принято; реализация — фаза B.

### D-098. Общая оценка нормируется по покрытию, а покрытие публикуется всегда

**Контекст.** `server/deepdive/compare.js` считает `overall` как средневзвешенное по
**присутствующим** слоям: если бас не измерен, знаменатель меньше, и трек без баса
может получить «идеальную» оценку. Наивная «починка» — делить на 4.00 всегда —
ломает другое: трек, где два слоя измерены, получил бы 0.35–0.40 и выглядел бы
испорченным из-за отсутствия данных, а не из-за плохого звука. Намерение
зафиксировано в шапке модуля с самого начала: «общая оценка — среднее по слоям,
а не по слоям, которых нет». Это продуктовое решение, а не опечатка.

**Решение.** Знаменатель остаётся нормированным по покрытию, но покрытие
становится **частью результата, а не спутника**:
- в ответе появляется `coverage: {covered, total, label: "3/4", complete, measured,
  missing}`;
- `missing_layers` публикуется всегда и явно: «нет данных» ≠ 0;
- **единый балл без покрытия публиковать запрещено** — контракт
  `contracts/deep-dive.schema.json` требует `coverage` рядом с `overall`;
- слой с отсутствующим измерением не получает «украшающую» оценку: `null` → «нет
  данных», а не 0.5.

**Альтернативы.** (1) Фиксированный знаменатель 4.00 — отклонено: наказывает за
отсутствие данных, а не за качество. (2) Считать `overall` только при полном
покрытии — отклонено: лишает нас 70% измерений, которые у нас есть. (3) Один
балл + «штраф за неполноту» — отклонено: штраф снова смешивает «плохо звучит» и
«не измерено».

**Последствия и риски.** Оценка перестаёт быть самодостаточной цифрой: читать её
вне отчёта нельзя. В отчёт выводится строка «покрытие 3/4». Для гейта качества
это означает, что сравнивать треки можно только при равном покрытии — иначе
сравнение бессмысленно (учтено в рефайн-цикле).

**Статус.** принято; реализовано 15.11.2026 (`server/deepdive/compare.js`,
`contracts/deep-dive.schema.json`, `server/routes/music.js`).

### D-099. Лицензии сэмплов — машинный реестр, публикация заблокирована до решения владельца

**Контекст.** 42 сэмпла из 44 приезжали с внешнего CDN без единой записи о
лицензии; `docs/LICENSES.md` был читаемым текстом, который нельзя проверить
машиной. Пока лицензия не прочитана из первоисточника, «не нашёл запрета» ≠
«разрешено» — и по нашему же правилу такой компонент не должен попадать в стек.
Аудит показал: два банка не подтверждены — `github:tidalcycles/dirt-samples`
(состав есть, происхождение не документировано, папка `breaks125` нарезана из
чужих записей) и `shabda:piano` (каждый сэмпл имеет свою лицензию, NC-фильтр
инструмента их не разделяет). Всего 219 имён сэмплов без подтверждения.

**Решение.** Реестр становится машинным и проверяемым:
- источник истины — `server/data/sample-banks.json` (банки и имена) и
  `server/data/sample-licenses.json` (лицензия, источник, дата, вердикт);
- `server/music/licenses.js` считает `confirmed` / `requiresDecision` по записи,
  а не по впечатлению;
- `npm run check:licenses` проверяет механику реестра (каждая запись полна, каждый
  банк описан, лишних записей нет) и **красит публикационные ворота**, пока есть
  неподтверждённые банки: `releaseBlocked: true`;
- публикационные ворота живут отдельной командой — `npm run gate -- --release` —
  и в базовый `npm run gate` не входят, чтобы базовый гейт не был красным из-за
  чужого решения;
- атрибуция каждого банка (TASL) отдаётся наружу функцией `attributionFor`, чтобы
  атрибуция была не «в описании», а в ответе.

**Что нужно от владельца (открыто).** Два решения:
1. `dirt-samples` — оставить как есть (тогда NC/неизвестное происхождение
   тянется на продукт) или заменить банк;
2. `shabda:piano` — читать лицензию каждого сэмпла по Freesound id (нужен ключ
   Freesound API или серверная фильтрация по `--licenses cc0|by|by-nc`) или
   исключить банк.
Пока решения нет, публикация закрыта — это осознанный блок, а не сбой.

**Последствия и риски.** Гейт `check:licenses` в `npm run gate` зелёный (механика
цела), а `--release` — красный: разница намеренная и видна в сводке. Демо обложки
(`public/demo/preview.wav`) собирается только из чистых осцилляторов, поэтому
лицензионного риска не добавляет.

**Статус.** принято; механика реализована 15.11.2026, решение владельца — открыто.

### D-100. Источник истины для 100 дорожек: IR, но решение принимается спайком с числами

**Контекст.** В проекте два компилятора, то есть два мира. **TrackSpec-путь**
(`src/schemas/track-spec.schema.js` → `server/music/compiler/index.js`) — живой:
студия, compose, разбор. Мелоедия статична (пул паттернов в
`server/music/knowledge/roles.js:33`), гармония — сдвиг ступеней по корням, шины
только `sends.{delay,room}`. **IR-путь** (`src/ir/schema.js`, `src/ir/compiler.js`) —
параллельный мир, в UI не подключён: зато в нём есть мотивы, sidechain-шины (≤16),
orbit-ревер (≤8), 17 чистых трансформ с измеренными дельтами, римская гармония и
нестатичная мелодия. Потолок 12 частей упирается не в «железо», а в идентичность
части: `$<ROLE>:` — это одновременно метка, ключ микшера и единица линта
(`src/studio/compile.js`, `src/core/code-model.js:21`, `server/skills/lint.js:185`),
а список ролей продублирован в пяти местах.

**Решение (предварительное, требует спайка).** Кандидат — **IR как источник
истины, TrackSpec как адаптер** (мост уже есть: `server/music/compose/score-adapter.js`).
Причины: правка «сделай партию виолончели мрачнее» без перегенерации остальных
дорожек — это ровно `src/ir/transforms.js`; на TrackSpec-пути такого механизма
нет вообще; IR-схема ближе к иерархии «Score → Section → Part → Group».

**Условие.** Это решение **не окончательное**, пока не пройдёт спайк фазы C (1
день): сколько стоит подключить IR к студии. Если спайк показывает больше 5
инженерных дней на мост — возвращаемся к «TrackSpec + новая схема идентичности
частей». Решение пишется с числами, не с мнением.

**Про нумерацию.** Промт-гайд ожидал, что «источник истины» станет D-098. Но
номер D-098 уже занят решением о покрытии оценки (оно реализовано и упомянуто в
`contracts/deep-dive.schema.json`), а D-099 — решением о лицензиях (на него
ссылается `server/music/licenses.js`). Поэтому источник истины — **D-100**.
Расхождение с гайдом — сознательное: два решения не могут иметь один номер.

**Побочный эффект, который нельзя забыть.** До спайка нужно перебазировать критерий
`parts` в `server/music/references.js` / `score.js`: сейчас мягкая цель 4–7 партий,
и трек из 100 дорожек получит худший балл по этому критерию (вес 10, линейный
спад вне диапазона). Иначе гейт качества будет рубить ровно то, ради чего делается
фаза C.

**Статус.** предварительно принято; окончательное решение — после спайка фазы C.

### D-100 (окончательное, после спайка фазы C). Источник истины — TrackSpec с новой схемой идентичности частей

**Условие, которое было поставлено.** «Если спайк показывает больше 5 инженерных
дней на мост — возвращаемся к варианту „TrackSpec + новая схема идентичности
частей“». Спайк выполнен (`tests/spike/parts-100.probe.mjs`), условие
сработало. Ниже — только измеренные факты и вывод из них.

**Факт 1. Потолок в 12 партий — общий для обоих путей.**

| Схема | 100 частей | Причина отказа |
|---|---|---|
| IR (`src/ir/schema.js`) | **отклонено** (4.9 мс) | `Invalid enum value … received 'p1'` — `layers` это `record(RoleSchema, …)`, а `RoleSchema = z.enum(IR_ROLES)` |
| TrackSpec (`src/schemas/track-spec.schema.js`) | **отклонено** (1.0 мс) | `parts.roles` — `z.record(z.enum([12 ролей]), …)` |
| StudioSpec (`src/studio/model.js`) | **отклонено** (1.1 мс) | refine «parts.roles: неизвестная роль» |

`IR_ROLES` = 12. То есть «100 дорожек» не может сделать **ни один** из двух
путей: новая схема идентичности частей нужна в любом случае. Значит, выбор
«источника истины» не снимает главный блокер, а добавляет к нему мост.

**Факт 2. Мост TrackSpec→IR не существует.** Поиск по `toIR|fromIR|specToIR|
irFromSpec` — ноль совпадений. Есть только IR→код (`src/ir/compiler.js`) и
IR→спека v2 (`buildSpec` там же). Плюс факт из гайда, который не подтвердился:
`server/music/compose/score-adapter.js` — это адаптер **скоринга** v2
(`scoreWithV2`), а не мост TrackSpec↔IR. Мост придётся писать, и он не может
быть бесс lossless: TrackSpec хранит паттерн мини-нотацией, а IR — планом
(`plan`, `density`, `register`, `motifId`).

**Факт 3. Слой кода новую грамматику уже держит.** Код с метками `$P001:`
…`$P100:` разобран полностью: `parseParts` → **100 из 100**, снимок микшера →
**100**, solo заглушил **99** остальных. Регулярка студии
(`src/core/code-model.js:4`) — `[A-Za-z]\w*`, то есть `$P001:` и `$VIOLIN_1:`
подходят уже сегодня. Строгих мест, где ломается новая грамматика, **два**:
`server/music/compiler/index.js:187` и `server/music/compose/compiled.js:29`
(оба — `/^\$[A-Z]+:/`). Гайд называл четыре-пять мест — это завышенная оценка.

**Факт 4. Рендер 100 дорожек работает, но микс клиппит.** 100 партий × 16
тактов: рендер **ок**, wall **25.0 с** (движок 24.7 с) на 32 с аудио; событий
1600, максимум одновременных — **100**. True peak **+6.02 dBTP**, клиппинг
**1660** отсчётов: сумма 100 партий по 0.02 даёт линейное усиление 2.0, то
есть ровно +6 dB. Значит бюджет полифонии и плотности — не «пожелание», а
обязательный механизм (иначе гейт C не пройдёт ни по одному миксу).

**Факт 5. Связанность с 12 ролями — 23 продакшн-файла и 21 тест-файл.**
Списки ролей используются в `src/studio/model.js`, `src/ir/schema.js`,
`server/ir/{schema-json,normalize}.js`, `server/music/knowledge/roles.js`,
`server/music/compose/pipeline.js`, `src/studio/bus.js`, `src/ir/arrangement.js`,
`server/deepdive/{refine/helpers,pipeline/constants}.js`, `src/metrics/extract.js`,
`src/oracle/metrics.js`, `server/agent/library.js` и далее; в тестах — от
`ir-schema.test.js` до `deep-dive-transpiler.test.js`.

**Оценка стоимости моста (оценка, не измерение; выведена из пунктов 1–5).**
Мост IR→студия = новая идентичность в IR (1.5 дня) + компилятор IR с метками
частей (1 день) + модель студии (1.5 дня) + **новый адаптер TrackSpec→IR
(3–5 дней, потери в представлении паттернов)** + регресс по 21 тест-файлу и
смежным путям (2 дня) + перенос типизированных правок с IR на новую схему
(2–3 дня) ≈ **11–15 дней**. Это выше порога гайда (5 дней), поэтому
правило срабатывает: возвращаемся к «TrackSpec + новая схема идентичности
частей».

**Решение (окончательное).** Источник истины для студии — **TrackSpec** с
новой схемой идентичности частей: часть получает **собственный id** (`P001`,
`VIOLIN_1`), а роль (`kick`, `bass`, `violin`) становится её **атрибутом**, а не
ключом. IR остаётся вторым источником: он используется там, где нужны его
возможности (мотивы, римская гармония, шины), и его результаты приводятся к
TrackSpec-совместимому виду через `buildSpec`. Отдельная работа (D-105):
типизированные правки переносятся с IR на модель «id + роль», иначе требование
гейта C («правка одной партии без перегенерации остальных») останется
невыполнимым.

**Почему не «IR как источник истины».** Не потому что IR хуже: он сильнее по
музыке. А потому, что мост дороже порога, который поставил сам гайд, и потому
что главный блокер (идентичность частей) общий для обоих путей — то есть
выбор пути не влияет на его стоимость и не снимает его.

**Альтернатива, которую отвергли.** «Сделать 12 ролей × 8 дублей = 96
партий» — то есть оставить enum и размножить роли. Отвергнута: это не 100
разных дорожек с разными тембрами и партиями, а 12 ролей по 8 копий, а
сгруппированные дорожки (струнные секции по 8 голосов) всё равно не получают
разных паттернов.

**Статус.** окончательно принято (спайк фазы C выполнен: `tests/spike/parts-100.probe.mjs`).

### D-105. Типизированные правки переносятся с IR на модель «id + роль»

**Контекст.** Требование гейта C: правка «замени тембр виолончели и сделай её
партию мрачнее в сцене 2» выполняется **без перегенерации остальных 99
дорожек**. Механизм, который это умеет, есть только в IR: `src/ir/transforms.js`
— 17 чистых трансформов с измеренными дельтами, покрытые
`tests/unit/ir-transforms.test.js`. На TrackSpec-пути аналога нет: правки
разбора (`server/deepdive/refine/ops.js`) работают со слоями по **роли**
(`LAYER_ROLES`), то есть «правка всех скрипок», а не «правка скрипки №3».

**Решение.** Поскольку источником истины остаётся TrackSpec (D-100),
типизированные правки переносятся на новую модель «id + роль»: трансформ
адресует партию по **id** и возвращает измеренную дельту. Роль при этом
остаётся группировкой (для микшера и бюджета), а не адресом.

**Условие.** Пока модель «id + роль» не введена, правка конкретной дорожки
невозможна ни на одном пути — и гейт C недостижим. Поэтому работа над
идентичностью частей идёт **первой** в фазе C, а бюджет полифонии — сразу
после неё (без него микс из 100 дорожек клиппит: измерено, +6.02 dBTP).

**Статус.** принято.

### D-106. Команды студии адресуют партию по идентификатору

**Контекст.** После D-100 роль перестала быть адресом партии, но контракт
команд студии (`src/studio/bus.js`) продолжал адресовать **роль**: payload
`setMix`/`setRole`/`mutate`/`editNotes`/`applyAutoMix` требовал `role` из
enum'а из 12 значений. Для 7 дорожек это работало; для 100 — нет: две
партии одной роли неразличимы, а правка «скрипка №3» невозможна в принципе.

**Решение.** Поле `role` в payload'ах команд заменено на `id`
(идентификатор партии), тип команды `setRole` переименован в `setPart`.
Ключ `mix.parts` в модели проекта — тоже идентификатор партии, и теперь
проверяется на существование в `spec.parts.roles`: правка не может уйти
в партию, которой нет. Автоматизация (`automation[].target.kind = 'part'`)
адресует партию тем же идентификатором.

**Что не изменилось.** Сами спеки: ключ `parts.roles` по-прежнему принимает
легаси-форму (ключ = роль, без поля `role`), поэтому корпус, gold-set и
промпты валидируются как раньше. Переименование команд — ломающее
изменение внутреннего контракта; внешних вызовов, кроме QA-подсказок
(`src/audio/qa.js`) и тестов, в проекте нет.

**Почему не «оставить оба поля».** Два способа адресовать одну сущность —
это два источника истины. Именно из-за этого в проекте уже было два
компилятора (TrackSpec и IR).

**Статус.** принято и реализовано.

### D-107. Бюджет полифонии и громкости голоса считаются при экспансии

**Контекст.** Трек из 100 дорожек, собранный «в лоб», клиппит: измерено
+6.02 dBTP и 1660 клиппированных отсчётов (tests/spike/parts-100.probe.mjs).
Причина арифметическая: 100 партий по 0.02 дают линейное усиление 2.0, то
есть ровно +6 дБ. Механизма, который бы это предотвращал, в проекте не было
вообще.

**Решение.** Два ограничения, оба считаются в экспансии
(`src/music/expand.js`):

1. **Бюджет плотности на голос** (`GROUP_BUDGET`): не более N атак на такт
   на одну дорожку группы. Нарушение — прореживание рисунка, шаг
   удваивается (детерминированно).
2. **Бюджет атак на трек** (`globalAttackBudget`): не менее 24 и не более
   1.4 атаки на дорожку. Если трек перегружен, голоса прореживаются по кругу.
3. **Громкость голоса** (`GROUP_LEVEL`): сумма голосов группы держится у
   0.40, каждый голос получает 0.40 / N. Это громкостная разкладка, а не
   «приглушение всего подряд»: сумма 100 голосов остаётся управляемой.

**Калибровка измерением.** При `GROUP_LEVEL = 0.28` рендер оперы (66
дорожек, 64 с звука) дал LUFS-I −18.47 при true peak −4.51 dBTP: тихо, но
чисто. При `0.40` — LUFS-I −15.37, true peak −1.42 dBTP, клиппинг 0.
Коридор громкости проекта — −16…−12 LUFS (`src/audio/metrics-report.js`),
потолок true peak — ≤ −1 dBTP. Обе цифры — из рендера, не из оценки.

**Побочный эффект, который пришлось учесть.** Прореживание не может ставить
тишину внутрь группы `<0 2 4>`: Strudel такую запись не парсит (рендер падал
на `n("<0 ~ ~ ~")`). Поэтому токенизатор mini-нотации держит группы целыми,
а прореженная группа схлопывается до первого элемента.

**Статус.** принято и реализовано.

### D-108. Агент получил два инструмента масштаба

**Контекст.** Гейт C требует, чтобы правка дорожки выполнялась агентом. До
этого агент умел `edit_ir` — правку в мире IR, который к студии не подключён
(D-100). То есть требование было бы выполнено только формально.

**Решение.** В реестр агента добавлены два инструмента:

- `expand_plan` — план (форма, гармония, состав групп) -> спека с 30-100+
  дорожками, с бюджетом полифонии и честным отчётом о бюджете;
- `edit_part` — правка ОДНОЙ дорожки по идентификатору (`VIOLIN_3`):
  тембр, рисунок, громкость, роль, переопределение в секции. Остальные
  дорожки не трогаются и не перегенерируются — это проверяется тестом
  (побайтовое сравнение кода остальных дорожек).

**Почему не один инструмент.** Экспансия и правка — разные операции с
разными контрактами: первая строит трек из плана, вторая меняет одну
дорожку существующего. Смешивать их в один тулз означало бы, что модель
не может сказать «разверни, потом поправь третью скрипку» двумя шагами.

**Статус.** принято и реализовано.

## Фаза A — помощник-агент

### D-101. Режим агента выбирается по цели запроса, а не по первому совпадению слов

**Контекст.** Гейт A (§8 гайда) требует, чтобы запрос «найди в интернете, что
такое phonk drift, и сделай бит в этом стиле» агент проходил сам: ищет → читает →
строит план → компилирует → играет. Режимы были описаны как «ресёрч — поиск»,
«композитор — музыкальные тулзы», и `detectMode()` выбирал режим по первому
совпавшему regex. Запрос гайда содержит и поиск, и композицию — побеждал поиск,
агент попадал в режим «Ресёрч» без `compose_spec` и `compile` и половину запроса
выполнить не мог. Замер: до правки план на запрос гайда содержал
`web_search, library_search` и не содержал ни сборки, ни компиляции; кода трека
не было (0 символов).

**Решение.** Режим определяется по цели запроса: если в запросе есть и поиск, и
сборка, побеждает сборка (`wantsComposition` проверяется первым), потому что
цель — бит, а поиск лишь подготовительный шаг. Правки (`wantsDirector`) имеют
приоритет над сборкой — «поменяй тембр» не должно переписывать трек.

**Побочное следствие.** В режиме «Композитор» доступны и веб-инструменты
(`web_search`, `web_fetch`): чтобы сделать бит в стиле, нужно понять стиль.
Без этого гейт A недостижим — агент не может ни найти, что такое phonk drift,
ни прочитать найденное. Лимиты режима при этом выросли осознанно: шагов 6→8,
вызовов 8→10, источников 0→4.

**Связка «поиск → чтение».** Модель не знает адрес страницы заранее, поэтому
шаг `web_fetch` не может быть в плане: он добавляется в очередь шагов сразу
после успешного `web_search`, по адресу из первого результата. Шаг виден в
панели отдельной карточкой с пометкой «шаг добавлен после поиска» — то есть
план не переписывается задним числом, а шаг честно помечен как добавленный.

**Альтернативы.** (1) Пятый режим «исследование+сборка» — отклонён: гайд
описывает четыре режима, а лишний режим усложняет паспорт без выигрыша.
(2) Оставить выбор за пользователем — отклонён: гейт A требует, чтобы запрос
проходил сам, без ручного выбора режима.

**Замер после правки.** План на запрос гайда: `web_search, library_search,
compose_spec, compile`; трек собран (2806 символов кода); поиск без ключа
деградировал честно («Интернет недоступен: не задан EXA_API_KEY»), агент не
упал и перешёл к сборке. Гейт A: 15/15 (`npm run gate:a`,
`docs/evidence/agent/gate-a.json`).

**Статус.** принято.

### D-102. Расход агента показывается честно: оценка помечена оценкой, ноль цены — это «не измерена»

**Контекст.** Событие `usage` отдавалось, но панель его не обрабатывала: вместо
расхода пользователь видел строку «Инструментов вызвано: N» — то есть
**расход токенов не был виден вообще**, хотя гейт A требует именно этого.
Вторая проблема — в самом счётчике: когда провайдер не отдал счётчики токенов
(или это мок-LLM в CI), `usageSummary()` давал ноль, и ноль показывался как
факт. Это прямое нарушение закона проекта «нет данных ≠ 0».

**Решение.**
1. Ноль измеренных токенов — это «нет данных», а не «бесплатно». Если
   счётчиков провайдера нет, цикл считает оценку по объёму промпта и ответа
   (`estimateUsage`) и **помечает её**: `estimated: true`. Панель пишет
   «Токенов ≈ 401 (оценка: провайдер не отдал счётчики)».
2. Цена показывается числом только если модель известна (`priceKnown: true`).
   Иначе — «Цена не измерена (модель или провайдер неизвестны)». Молчаливый
   ноль цены означал бы «бесплатно», а это выдумка.
3. Ответ из кэша — отдельная формулировка: «Ответ взят из кэша — токены не
   тратились».
4. Оценка считается по полному промпту ответа (план + наблюдения), а не по
   голому запросу: оценка по запросу занижала расход в разы.

**Побочный эффект.** Глобальная статистика (`/api/stats`) при этом не
загрязняется оценками: оценка живёт в событии `usage` агента, а в статистику
попадают только записи провайдера. Иначе «цена ночи» была бы выдумкой.

**Альтернатива.** Записывать оценку и в статистику — отклонён: тогда отчёт о
цене ночи смешивал бы измеренное и выдуманное.

**Статус.** принято.

## Фаза B — local-first

### D-103. Локальный демон: SSE вместо WebSocket, очередь на диске вместо памяти

**Контекст.** Гайд (§9) требует «отдельный пакет `local/` в репо (Node): очередь
задач, WebSocket-мост к серверу и фронту, авторизация по токену». Два пункта
требуют решения, а не буквального исполнения.

**WebSocket → SSE.** Проект уже стримит всё, что длиннее одного ответа, через
SSE: агент (`/api/agent`), разбор, композиция. Прогресс задачи — это поток
событий в одну сторону (демон → клиент), а команды идут обычными HTTP-запросами.
WebSocket дал бы двусторонний канал, которого не требуется, ценой новой
зависимости (`ws`) — то есть сменой стека, которую гайд запрещает («не менять
стек», §16). Решение: **SSE + HTTP POST**, тем же протоколом, что и остальной
проект.

**Очередь в памяти → на диске.** Демон живёт на машине владельца, и связь с
сервером рвётся: сон, Wi-Fi, перезапуск сервера. Очередь в памяти процесса
теряет принятую задачу при обрыве — а это минуты рендера. Решение: журнал
`queue.jsonl` (append-only): задача и её финал — строки журнала; при старте
демон перечитывает журнал и возвращает в работу всё, у чего нет терминальной
записи. Измерено: задача, принятая демоном, переживает убийство процесса
(`SIGKILL`) и дожидается финала во втором демоне поверх того же журнала.

**Авторизация.** Токен обязателен: без `LOCAL_DAEMON_TOKEN` демон **не
стартует** (fail-closed). Открытый в сеть рендерер — дыра. Сравнение токена —
постоянного времени (`timingSafeEqual`), чтобы его нельзя было перебирать по
времени ответа. Явный opt-in `LOCAL_DAEMON_ALLOW_ANON=1` оставлен только для
локальных экспериментов и не включается по умолчанию.

**Демон не пишет свой рендер и свой анализ.** Он вызывает те же модули, что и
сервер: `server/deepdive/render/render-worker.mjs` и
`server/deepdive/analysis/client.js`. Иначе «локальный» результат отличался бы
от серверного и сравнивать их было бы бессмысленно.

**Замеры (машина владельца: 12 CPU, 16 ГБ RAM, Windows).** Рендер 16 тактов
(32 с аудио) — **1.9 с**; полный 4-минутный трек — **77.2 с** против 56.4
минуты на сервере (в 43.8 раза быстрее, при пороге гайта ≤15 мин). Очередь
пережила убийство демона: восстановлена 1 задача, финал `done`.

**Статус.** принято.

### D-104. «Бит-в-бит» для рендера — это допуск проекта, а не равенство файлов

**Контекст.** Гейт B требует «бит-в-бит рендер совпадает с серверным
fingerprint». Замер это опроверг: WAV-файлы локального и серверного рендера
**различаются** (sha256 не совпадает). Разбор расхождения измерен
(`tests/spike/browser/determinism-probe.mjs`):

| Паттерн | Файлы идентичны | Звук |
|---|---|---|
| чистый осциллятор | да | maxAbsDiff = 0 |
| чистый сэмпл | да | maxAbsDiff = 0 |
| осциллятор + сэмпл | **нет** | maxAbsDiff = 1 LSB (3.05e-5) в 12–24 сэмплах из 3–6 млн |

**Решение.** Формулировка «бит-в-бит» в гайде не выдерживает проверки: для
смеси осциллятора и сэмпла рендер расходится на 1 LSB 16-битного звука. Но
это **в пределах допуска проекта** (docs/BRIEF.md:73: maxAbsDiff ≤ 1e-4 в
нормализованном виде, |ΔLUFS| ≤ 0.05). Поэтому:

* гейт B проверяет **допуск**, а не равенство файлов;
* `renderFingerprint` (движок, частота, sha256 кода, версия браузера)
  сравнивается **точно** — и он совпадает;
* «побайтово идентичны» остаётся отдельной строкой в отчёте и честно
  помечается «нет», когда это так.

**Почему это важно.** Если бы «бит-в-бит» осталось в требованиях без допуска,
любой честный замер давал бы красный гейт на недетерминизме в 1 LSB — то есть
гейт перестал бы измерять проект и начал бы измерять шум округления. Допуск
проекта для этого и написан.

**Побочный эффект.** Комментарий в `server/deepdive/render/render-worker.mjs`
обещал `maxAbsDiff = 0` для всех случаев — это было неверно и исправлено на
фактическое поведение.

**Статус.** принято.

### D-109. Тема трека одна на весь трек; фразы — A | A' | B | A'', группы берут тему по-своему

**Контекст.** До фазы D лид брал один из двух-трёх шаблонов из матрицы ролей
(`server/music/knowledge/roles.js`), и все скрипки в оркестре играли одно и
то же. Замер на треке из 66 дорожек: у 18 скрипок было **3 уникальных ритма**.
Форма трека ни на что не влияла — каждая секция играла тот же рисунок.

**Решение.**

1. **Тема — одна на весь трек.** Она определяется зерном и стилем
   (`trackTheme`) и не зависит от числа голосов. Это и есть «оркестр», а не
   набор солистов: расхождение голосов — это дивизи, а не разные темы.
2. **Фраза — четыре варианта:** `A` (тема, половинная каденция — конец на
   доминанте), `A'` (транспозиция), `B` (ретроград инверсии), `A''`
   (возвращение с полным разрешением `V–I` в двух последних нотах).
3. **Группы берут тему по-своему:** струнные — три четверти, медные — инверсия
   (ответ), деревянные — удлинённые ноты, клавишные — ровные доли, хор — две
   половинные, солист несёт тему в её собственном ритме, арпеджио — тема в
   ровных долях. Голоса внутри группы делят варианты фразы.
4. **Секции получают варианты по энергии:** тихая — предпосылка (`A`), средние
   — `A'` и `B`, громкая — вывод (`A''`). Назначение не зависит от порядка
   секций в треке — только от энергии.
5. **Длительности пишутся в мини-нотации.** Семантика `@` измерена пробой
   (`scripts/probe-duration-semantics.mjs`): в последовательности единица =
   1/(сумма длительностей) цикла, поэтому `0@8 4@8` — это две половинные
   ноты, а не две шестнадцатые. Без этого голоса звучали бы стаккато-пульсом.
6. **Прореживание сохраняет длительности:** снятая нота не исчезает, её
   длительность переходит к предыдущей (`thinPattern`).

**Почему это важно.** Редактируемость — единственное преимущество проекта
перед генеративными сервисами («поменяй тему у виолончели в 17-м такте»).
Тема, ставшая общей для трека, делает такой запрос осмысленным: у партии
есть материал, который можно заменить, а не заново придумать.

**Цена.** Плотность атак выросла (167 атак на такт при 66 голосах вместо
81). Бюджет полифонии пересчитан: `globalAttackBudget` = 3 атаки на голос
(было 1.4 — коэффициент был откалиброван на статичных шаблонах, где голос
играл одну шестнадцатую и молчал).

**Альтернатива, отклонённая.** Тема на группу (каждая скрипка — своя). Дала бы
«богатый» оркестр, но разрушила бы связность: сорок восемь скрипок поют
разное, и трек перестаёт быть треком.

**Статус.** принято.

### D-110. Метрики мелодии: развитие меряется по высотам, каденция — по тону трезвучия тоники, «нет данных» = null

**Контекст.** Фаза D дала мелодии движение, но инструмент, который должен это
измерять, нельзя писать так, чтобы он врал. Два спорных места решаются
явно.

**Решение.**

1. **Развитие (`motifDevelopment`) меряется по ВЫСОТАМ, а не по
   интервальному рисунку.** Транспозиция фразы (`A'` против `A`) сохраняет
   рисунок, но это развитие, а не повтор. Рисунок (интервалы) — это
   связность (`motifCoherence`), высоты — это развитие. Меры разведены:
   статичный трек получает связность 1 и развитие 0, а не «идеальную оценку
   за развитие».
2. **Устойчивая ступень (`cadenceClarity`) — тон трезвучия тоники:** ступени
   0, 2 и 4 лада. Это тоника, её терция и квинта (доминанта) — одна и та же
   формула в мажоре и миноре, потому что трезвучие тоники всегда состоит из
   этих ступеней. Субтоника (6) и вторая ступень в мажоре — проходящие
   ступени, они устойчивость не дают.
3. **Разрешение (`resolution`) — доля концов фраз на тонике (0).** Полное
   разрешение и половинная каденция — разные вещи, и скор должен видеть их
   раздельно.
4. **«Нет данных» — это `null`, а не 0.** У трека с одной секцией развития по
   построению нет; у ноты вне лада каденции нет. Критерий скора может задать
   `noDataScore` — отсутствие данных не штрафует трек, у которого просто нет
   нескольких секций.
5. **Секции привязаны к форме по строке компилятора** `// Форма: intro(4) →
   verse(4) → drop(8)`: куски `arrange` разложены по секциям в порядке формы.

**Почему это важно.** Правило сессии — «нет данных ≠ 0». Если бы развитие
дефолтилось в 0, статичный трек получал бы «нет развития» и это читалось бы
как «измерено: развития нет». Если бы каденция считалась по любой устойчивой
ступени, трек, кончающийся на проходящей, получал бы «ясную каденцию».

**Статус.** принято.

### D-117. Бюджет ночи — жёсткий стоп платных вызовов, а не предупреждение

**Контекст.** Владелец дал кредит Exa на $19 и ключ Freesound на ночь. Если
бюджет не ограничен, ночной агентный цикл (поиск + чтение страниц + сборка
трека на LLM) способен съесть кредит незаметно: платные вызовы идут изнутри
цикла, и человек их не видит. Предупреждение в логе стопом не является.

**Решение.**

1. **Бюджет — стоп внутри сервера.** `server/agent/budget.js` считает потраченное
   по `usageSummary().byFeature.web_search` — то есть по измеренным ценам
   провайдера, а не по оценке — и возвращает состояние `exhausted`.
   `webSearch` при исчерпанном бюджете **не делает запрос** и возвращает
   честную деградацию («бюджет ночи исчерпан, отвечаю по локальной
   библиотеке»). Это поведение зафиксировано тестом.
2. **Лимиты ночи — переменные окружения** с зафиксированными умолчаниями:
   `NIGHT_EXA_BUDGET_USD=2.00` (резерв владельца ≥$17 от кредита $19),
   `NIGHT_EXA_CALL_CAP=40`, `NIGHT_FS_REQUEST_CAP=300`,
   `NIGHT_LLM_BUDGET_USD=5.00`.
3. **Цена поиска измеряется, а не оценивается.** Exa отдаёт
   `costDollars.total`; эта величина записывается через `recordUsage` с
   `estimated: false` и фичей `web_search` (D-102). Поэтому `/api/stats`
   показывает настоящую цену поиска, и бюджет считается по факту.
4. **Известное ограничение.** Счётчики живут в памяти процесса: сервер,
   поднятый один раз на ночь, считает верно, но перезапуск обнуляет счёт.
   Это записано как ограничение, а не как «всё точно».

**Альтернатива, отклонённая.** Считать бюджет только в скриптах гейтов.
Отклонено: платный вызов идёт изнутри сервера, и скрипт увидит его после
того, как деньги потрачены. Стоп должен быть там, где принимается решение
о вызове.

**Замер.** 16.11.2026: живой прогон гейта A — два поиска, `$0.0140` из
лимита `$2.00`; запись видна в `/api/stats` по фиче `web_search`.

**Статус.** принято.

### D-118. Режим «композитор» обещает трек: сборка и компиляция — гарантия режима

**Контекст.** Живой прогон гейта A (16.11.2026, настоящая модель) показал:
на запрос «найди в интернете, что такое phonk drift, и сделай бит в этом
стиле» модель вызвала `web_search`, дважды `web_fetch` и `library_search` —
и не вызвала `compose_spec`. Агент честно отчитался о выполненных шагах, но
трека не было: запрос «сделай бит» остался без ответа по существу.

**Решение.**

1. **Сборка и компиляция входят в гарантию режима «композитор».** Если после
   выполнения плана спеки нет — она собирается; если кода нет — он
   компилируется. Это касается обоих контуров агента (нативного и
   текстового): `ensureComposed` в `server/agent/loop.js` дополняет уже
   выполненные шаги.
2. **Гарантия не дублирует работу.** Инструмент, который уже вызывался, не
   вызывается повторно: набор вызванных инструментов передаётся в
   `ensureComposed`.
3. **Деградация сохраняется честной.** Если `compose_spec` собрал спеку из
   библиотеки (модель не ответила), это по-прежнему видно в `degraded` — гарантия
   обещает трек, а не «модель ответила».

**Альтернатива, отклонённая.** Требовать от модели, чтобы она запланировала
сборку (подсказкой в промпте). Отклонено: это оставляет результат за
выбором модели — а режим, который обещает трек, обязан его вернуть. Кроме
того, живой прогон показал, что модель в этом сценарии план без сборки
выбирает регулярно.

**Замер.** 16.11.2026: живой гейт A — 20/20 проверок, код трека получен
(3054 символа) при плане модели без `compose_spec`. Юнит-тест
«режим „композитор“ обещает трек» закрывает это как инвариант.

**Статус.** принято.

### D-111. Измерительный рефайн поверх compose («Учитель»): правила по замеренным дефицитам, LLM в цикле нет

**Контекст.** Диагноз G гайда: глубокие разборы треков учили только человека,
читающего отчёт, — измерение никуда не возвращалось. Готовый движок рефайна
(`server/deepdive/refine/loop.js`) умеет «сгенерил → отрендерил → измерил →
изменил → перерендерил», но работает он с планом разбора и с LLM в цикле.

**Решение.**

1. **Новый модуль `server/music/compose/measured-refine.js`** (имя
   `server/music/compose/refine.js` занято существующим spec-level refine,
   контракт которого нельзя ломать). Контракт как в ТЗ: `refineComposed({spec,
   code, seed, render, measure, applyOp, maxIterations, budgetMs, signal,
   onEvent})`; события SSE: `refine_start`, `rendered`, `measured`,
   `edit_applied`, `rerendered`, `refine_done`.
2. **Решает таблица правил, а не модель.** Порядок фиксирован: R3 (клиппинг) →
   R1 (пик) → R2 (громкость) → R4 (связность мотива) → R5 (энтропия
   контура) → R6 (покрытие — не правится, публикуется). При равенстве
   дефицитов партии берутся по идентификатору (`localeCompare('en')`).
   Правки — только типизированные операции реестра D-105/D-106
   (`setGain`, `setPattern`) по id партии.
3. **Шаг громкости считается от текущей амплитуды, а не от нуля.** Измерено
   16.11.2026 (рендер одной партии, RMS): «без gain» → −19.55 дБ,
   `.gain(1)` → −17.61 дБ, `.gain(0.7943)` → −19.61 дБ. То есть «без gain» —
   это амплитуда движка ≈ 0.7943 (−2 дБ), а `.gain(x)` задаёт амплитуду
   буквально. Отсюда `DEFAULT_PART_GAIN = 0.7943`: без этой поправки первый
   шаг правила оказывался на 2 дБ громче задуманного, и на замере это
   выглядело как «правка не помогает».
4. **Ухудшение откатывается.** Если замер после правки хуже прежнего, цикл
   возвращает предыдущую версию и останавливается (`stoppedBy: 'worse'`).
   Цикл не имеет права «улучшить» звук до худшего состояния.
5. **Улучшение меряется непрерывной технической шкалой (0..1), а не
   признаком «зелёный/красный».** Пик 0.79 dBTP и пик −0.2 dBTP оба
   «красные», но второй ближе к норме, и цикл должен видеть движение.
   Порог улучшения — EPS = 0.01; две итерации без движения → стоп
   `plateau`.
6. **Правило R5 не исполняется: коридор энтропии контура не откалиброван.**
   В проекте нет измеренных границ, поэтому правило молчит, а не угадывает.
   Долг зафиксирован здесь.
7. **Покрытие слоёв не измеряется** (рендер идёт одним миксом), поэтому
   `coverage = null` — «нет данных», а не «4/4».
8. **Интеграция — флаг `measuredRefine: true`** в `/api/music/compose`,
   по умолчанию выключен. Существующий spec-level refine не тронут.

**Замер (16.11.2026, настоящий рендер в headless Chromium).**

| Случай | До | После | Итог |
|---|---|---|---|
| ambient (тише коридора) | L0 67, LUFS −16.71, пик −4.52 | L0 100, LUFS −15.77, пик −3.58 | цель достигнута за 1 итерацию, звук изменён |
| techno (микс обрезается в PCM) | L0 33, LUFS −13.60, пик +0.30, clip 10902 | L0 33, LUFS −14.54, пик +0.25, clip 6249 | улучшено измеримо; до нормы не доведено (см. ниже) |

**Измеренное ограничение.** У плотного материала crest ≈ 19.7 дБ
(`docs/evidence/refine/compose-refine.json`): пик держится около 0 dBTP,
пока микс обрезается в PCM, и потолок пика вместе с коридором LUFS
недостижимы общей регулировкой. Правила улучшают звук измеримо, но зелёного
трека из такого материала не получается. Это свойство материала и уровня
библиотечных планов, а не рефайна.

**Альтернатива, отклонённая.** Оставить рефайн с LLM в цикле (как в
deep-dive). Отклонено: цена и недетерминированность; «код собирает
компилятор, не модель», а решение по измеренным дефицитам таблица правил
принимает сама.

**Статус.** принято.

### D-112. Style-mining: библиотека измеренной статистики, а не сэмплов

**Проблема.** Глубокие разборы треков учили только человека: отчёт читают
глазами, и ни одно число из него не попадало в следующий трек. Композитор
работал по матрице ролей, где грув задан статическими шаблонами.

**Решение.**

1. **Три модуля.** `server/music/mining/extract.js` (паспорт → фичи),
   `server/music/mining/aggregate.js` (фичи → статистика стиля),
   `server/music/mining/library.js` (чтение библиотеки и дайджест для промпта),
   `server/music/mining/groove.js` (профиль паттерна и подбор по измеренному
   груву).
2. **Из библиотеки — только статистика.** Переносятся распределения,
   гистограммы, средние и квантили: темп, вес бэкбита, свинг, гистограмма

3. **Порог источников: 5.** Стиль с меньшим числом разборов помечается
   `sparse: true` и в промпт композитора не идёт: вывод по двум трекам — это

4. **Потребление библиотеки демонстрируемо.** Числа попадают в промпт

   выбирается под измеренную гистограмму атак (`matchMinedPattern`). Без
   измерений поведение прежнее: библиотека молчит.
5. **Идемпотентность.** Сборка библиотеки даёт байт-в-байт одинаковый JSON:
   ключи отсортированы, числа округлены.

**Честная перепись (16.11.2026, измерено).** Паспортов глубокого разбора на
машине нет: рабочий каталог `%TEMP%/strudel-deepdive` пуст, в

лежат только сгенерированные кандидаты. Поэтому библиотека зафиксирована
честно: `sources: 0`, `target: 20`, стилей нет. Добирать паспорта
синтетикой и выдавать их за разборы запрещено.

**Что нужно владельцу.** На машине, где работает сепарация:


file.json` или из `--style`.

**Альтернатива, отклонённая.** Складывать в библиотеку сами паттерны
ударных («как в этом треке»). Отклонено: это переработка чужого
материала; разрешено только статистическое описание.

### D-114. Поиск сэмплов в Freesound: двойной фильтр лицензий, fail-closed

**Проблема.** Фаза E («Охотник») требует искать редкие звуки в интернете.
Единственный источник с внятной лицензией — Freesound, но там лицензия у
каждого образца своя, и несвободное (NC, ND) встречается. Ошибка тут стоит
дорого: несвободный сэмпл, попавший в пул, — это юридическая проблема, а не
технический дефект.

**Решение.**

1. **Фильтр лицензий двойной и fail-closed.**
   * На стороне сервиса: `filter=license:"Creative Commons 0"` (или
     `"Attribution"`), плюс ограничение длительности
     `duration:[0 TO N]`.
   * На нашей стороне: каждый результат проверяется по своему полю
     `license`; всё, что не совпало с белым списком, **выбрасывается**.
     Неизвестная лицензия — отказ, а не «наверное, свободная».
   * Белый список: только `cc0` и `cc-by`. В форме названия
     («Creative Commons 0», «Attribution») и в форме URL, которую Freesound
     отдаёт по факту.
2. **Ключ не течёт.** Он живёт только в заголовке `Authorization: Token …`,
   в адрес не попадает, а из текста ошибки вырезается. Значение ключа не
   отдаётся и в статусе службы — только имя переменной.
3. **Хосты.** Превью и описания берутся только с `freesound.org` и его CDN;
   любой другой хост отбрасывается. Это защита от подменённой ссылки.
4. **Ограничения.** Не больше 1 запроса в секунду (лимиты Freesound:
   60/мин) и не больше `NIGHT_FS_REQUEST_CAP` запросов за ночь (по умолчанию
   300). Бюджет — стоп, а не предупреждение.
5. **Кэш.** Результаты поиска кэшируются на 24 часа: каталог сэмплов меняется
   медленно, а запрос платный.
6. **Деградация.** Без ключа инструмент не падает: он говорит, что поиск
   сэмплов недоступен, и агент продолжает по локальной библиотеке. Это
   отдельная способность с отдельным ключом (`FREESOUND_API_KEY`), а не
   «интернет».
7. **Режим «Охотник»** (`hunter`): `freesound_search` → `compose_spec` →
   `compile`. Распознаётся по словам «редкий/необычный/странный звук».
8. **Отклонённые результаты показываются честно** — числом `filteredOut`,
   а не молча выбрасываются.

**Замер (16.11.2026, живой Freesound).**

| Запрос | Лицензия | Принято | Отклонено | Пример |
|---|---|---|---|---|
| `glass impact metallic` | cc0 | 5 | 0 | `Hard Glass Impact` (0.65 с), CC0 |
| `analog drum loop` | by | 5 | 0 | пять лупов 7.57–7.67 с, CC-BY 4.0 |

Провайдер отдаёт лицензию URL-ом (`http://creativecommons.org/publicdomain/zero/1.0/`)
— именно поэтому вторая проверка обязательна.

**Альтернатива, отклонённая.** Один фильтр на стороне сервиса. Отклонено:
провайдер меняет форму ответа, а лицензия — единственное, за что отвечает
наш проект.

**Статус.** принято.

### D-115. Локальный пул сэмплов «Охотника»: паспорт звука и лицензия как часть записи

**Проблема.** D-114 дал поиск в Freesound, но найденный звук существовал
только как строка в ответе поиска: его нельзя было услышать повторно,
измерить и найти снова по описанию. Строить бит «вокруг тембра» по одному
названию — значит угадывать тембр, а не знать его.

**Решение.**

1. **Паспорт звука** (`server/samples/passport.js`) — измеренные признаки
   одного сэмпла тем же DSP, что и в остальном проекте (`src/audio/dsp/*`):
   громкость (LUFS-I, peak, crest), спектр (центроид, rolloff, плоскостность,
   полосы), транзиенты (число, плотность, времена), тон (медианная F0, нота,
   доля голоса), темп по атакам. Чего измерить не удалось — `null`, не 0.
   В паспорт не переносится ни одна последовательность нот источника:
   паспорт описывает звук, а не копирует материал.
2. **Пул** (`server/samples/pool.js`, `data/samples/pool.json`) — реестр
   записей `{id, name, author, url, license, licenseId, passport, file}`.
   **Запись без разрешённой лицензии (cc0/cc-by) в пул не попадает** —
   отказ на входе (`addToPool`), а не предупреждение. Строка атрибуции TASL
   готовится всегда и лежит в записи.
3. **Аудио — вне git.** Реестр `pool.json` в git идёт, сами звуки
   (`data/samples/audio/`) — нет: пул живёт на машине владельца и в
   публичный релиз не входит. Раздел лицензий пула в `docs/LICENSES.md`
   генерируется из реестра (`npm run licenses:pool`), свежесть проверяется
   воротами (`--check`).
4. **Слой пула в реестре лицензий.** `licenseReport` показывает пул рядом
   с банками, но пул **не блокирует** банковый релиз: у каждого сэмпла своя
   лицензия, проверенная на входе.
5. **Скачивание** (`server/samples/download.js`) — только превью с
   разрешённых хостов Freesound (проверка D-114), лимит 10 МБ, таймаут 20 с,
   приведение к WAV через ffmpeg.
6. **Тулзы агента:** `sample_passport` (скачать → измерить → зарегистрировать)
   и `pool_search` (поиск по описанию против измеренного характера). Режим
   «Охотник»: `freesound_search` → `sample_passport` → `compose_spec` →
   `compile`. Без ключа Freesound — честная деградация по библиотеке.
7. **Локальный демон** получил задачу `passport`: измерение файла считается
   на машине владельца тем же общим модулем, что и на сервере (D-097).
8. **Маршруты:** `POST /api/samples/passport` (снять паспорт и
   зарегистрировать; `measure:false` — только регистрация) и
   `GET /api/samples/pool` (содержимое; `?q=` — поиск).

**Альтернатива, отклонённая.** Хранить найденные сэмплы в общей библиотеке
банков. Отклонено: банки — это релизный слой с проверкой владельца, а пул —
локальный рабочий слой «Охотника»; смешивать их — значит либо блокировать
работу владельца воротами релиза, либо пускать непроверенное в релиз.

**Статус.** принято.

### D-119. Паспорт в план: измеренные признаки сэмпла управляют треком, сэмпл звучит в рендере

**Контекст.** Паспорт звука и пул «Охотника» готовы (D-115), но композитор
строил бит вокруг НАЗВАНИЯ звука, а найденный сэмпл нигде не звучал:
рендер знал только банки `SAMPLE_SETS`. Живой проход гейта E не был
измерен. Замер 16.11.2026 на машине владельца: живой поиск Freesound —
0.3 с, скачивание+паспорт — 2.2 с, полный end-to-end с рендером — 6.0 с
(бюджет гейта ≤180 с).

**Решение.**

1. **Измеренное → музыкальное** (`server/music/compose/sample-plan.js`):
   тон (f0) → тональность трека; темп атак → BPM; плотность атак →
   ритмический рисунок партии сэмпла (атак на такт при ИТОГОВОМ темпе);
   центроид/характер → текст плана для модели. Гармония секций
   переносится в тональность сэмпла с сохранением качеств аккордов.
2. **Пороги честности.** Тон считается надёжным при доле тональных кадров
   ≥0.3; темп — при уверенности ≥0.3. Ниже порога — «нет данных» с
   причиной в `sources`, а не выдуманное число. Лад из одного тона не
   измерить: минор — осознанное допущение, помеченное в тексте.
3. **Детерминированная гарантия.** `compose_spec` принимает `sampleId`;
   партия `HUNTER_1` (роль perc) добавляется в спеку детерминированно
   ПОСЛЕ ответа модели (или запасного плана) — модель не может потерять
   сэмпл. Измеренные признаки идут и в промпт модели (`sampleDigest`).
4. **Сэмпл звучит в рендере.** WAV пула раздаются локальным статическим
   сервером рендер-воркера (`/pool-audio/<id>.wav`, только имя файла,
   обход каталога отвергается); браузер грузит их same-origin через
   `poolSamples` в аргументах рендера. Ошибка загрузки сэмпла — ошибка
   рендера: молча играть бит без найденного звука нельзя.
   `renderFingerprint` получает поле `pool_samples` — внешнее состояние
   рендера видно в паспорте. Задача `render` демона пробрасывает
   `poolSamples` (D-097: тот же движок локально).
5. **Гейт E** (`npm run gate:e`, `--live`): офлайн 9/9 на синтезированном
   WAV; живой 10/11 + 1 честное «нет данных» (LLM-провайдер недоступен,
   план собран из библиотеки). Отчёты — `docs/evidence/agent/gate-e*.json`.

**Альтернатива, отклонённая.** Встраивать WAV в код как data-URL.
Отклонено: код раздувается на мегабайты, лимиты инструмента и детерминизм
кода ломаются; same-origin раздача держит код чистым, а звук — рядом.

**Статус.** принято.
