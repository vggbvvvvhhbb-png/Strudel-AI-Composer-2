# Режим «Разбор» (Deep Dive) — API-контракт

Документ фиксирует **внешний** контракт режима «Разбор»: по нему пишутся
серверный пайплайн, UI-панель и цикл самоулучшения. Внутренние детали
(как считаются метрики) живут в коде и в `contracts/deep-dive.schema.json`.

Принципы, которые контракт не нарушает:

1. **Измеряем, а не угадываем.** Каждое число в ответе получено из аудио.
2. **Каждый вывод — с уверенностью и доказательством.** У числа есть
   `confidence`/метрика, из которой оно получено.
3. **Ориентир, не клон.** Двойник воспроизводит измеримый скелет
   (темп, лад, структура, ритм, роли), а не точное сведение и вокал.
4. **Private by default.** Аудио не уходит наружу: оно живёт во временной
   папке на сервере, удаляется по TTL.

---

## 1. Точки входа

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/deepdive/analyze` | Разбор трека: файл → измерения → двойник. **SSE.** |
| `POST` | `/api/deepdive/refine` | Итерации самоулучшения по метрикам. **SSE.** |
| `GET` | `/api/deepdive/jobs/:id` | Состояние последней задачи (JSON). |
| `GET` | `/api/deepdive/health` | Состояние режима «Разбор» (воркер, рендерер). |

### 1.1 `POST /api/deepdive/analyze`

Тело — `multipart/form-data`:

| Поле | Тип | Обязательное | Смысл |
|---|---|---|---|
| `file` | файл | да | Аудиофайл трека (wav/mp3/ogg/flac), до 100 МБ |
| `separate` | `1`/`0` | нет | Разделить на стемы (Demucs). По умолчанию — `0`. |
| `model` | строка | нет | Модель разделения: `htdemucs` (по умолчанию) или `htdemucs_ft` — «высокое качество», экспериментальный ночной режим (22.3 × realtime, ~90 мин на 4-минутный трек, память поджимается). Имя вне белого списка игнорируется — берётся `htdemucs` |

Ответ — поток `text/event-stream`. Каждое событие — одна строка
`data: {JSON}\n\n`, поле `type` определяет тип события.

| `type` | Поля | Когда |
|---|---|---|
| `job` | `id`, `permalink`, `separate?`, `model?` | Сразу после приёма файла: идентификатор задачи и прямая ссылка |
| `stage` | `stage`, `label`, `progress` (0..1), `detail?`, `eta?` | Начало/прогресс этапа |
| `passport` | `payload` (измерения + структура), `estimate` | Сразу после базового анализа — **до** разделения на стемы |
| `result` | `payload` (см. §2), `permalink?` | Финальный результат |
| `error` | `message`, `detail?`, `stage?` | Ошибка; поток закрывается |

Последовательность этапов (`stage`):

```
upload → analyze → [queue] → [separate] → stems → twin → render → compare → done
```

- `upload` — файл принят и сохранён во временную папку.
- `analyze` — темп, лад, громкость, спектральный баланс, стерео, структура.
- `queue` — тяжёлая операция ждёт в очереди (разделение идёт по одной).
- `separate` — разделение на стемы (если `separate=1`).
- `stems` — дескрипторы слоёв: активность по секциям, атаки, питч, аккорды.
- `twin` — построение код-двойника (TrackSpec → Strudel-код).
- `render` — офлайн-рендер двойника в WAV.
- `compare` — сравнение оригинала и двойника по слоям.
- `done` — результат готов.

### 1.1.1 Паспорт сразу (`passport`)

Событие `passport` приходит сразу после базового анализа и ДО разделения на
стемы: паспорт трека (темп, лад, громкость, баланс, стерео, секции) не
должен ждать самую долгую операцию.

```jsonc
{
  "type": "passport",
  "payload": {
    "measurements": { … },
    "structure": [ … ],
    "track": { "id": "…", "duration_s": 214.5, "file_name": "…" }
  },
  "estimate": {
    "minutesMin": 14,
    "minutesMax": 27,
    "label": "14–27 мин",
    "basis": "замер: 60 с аудио → 207–396 с, 240 с аудио → 1356 с (2 vCPU)",
    "separate": true
  }
}
```

**Оценка честная и консервативная.** Верхняя граница считается по ХУДШЕМУ
замеру на этом железе (6.6 × realtime), округление — вверх до целых минут.
Для 4-минутного трека это ~27 минут, а не «~15 минут». Коэффициенты живут в
`src/deepdive/estimate.js` и берутся только из измерений
(`docs/SESSION_REPORT.md` §4). Основание оценки приходит вместе с ней —
чтобы «27 минут» можно было проверить, а не принять на веру.

Для этапа `separate` событие `stage` дополнительно несёт `eta`:

```jsonc
{ "type": "stage", "stage": "separate", "label": "…", "progress": 0.35,
  "eta": { "seconds": 1584, "label": "14–27 мин" } }
```

Клиент считает обратный отсчёт сам: сервер во время Demucs молчит.

### 1.1.2 Прямая ссылка на задачу

Идентификатор задачи — UUID. Ссылка `/razbor/<job-id>` открывает разбор
заново: без аккаунтов, по одному только идентификатору (D-084).

- Готовый результат лежит на диске (`<DD_WORKSPACE_DIR>/<job-id>/job.json`)
  и переживает перезапуск сервера.
- Незаконченная задача после перезапуска не восстанавливается: клиент
  получает 404 и говорит об этом прямо.

### 1.1.3 Обрыв потока

Разбор на CPU идёт десятки минут, и связь может оборваться. После обрыва
клиент опрашивает `GET /api/deepdive/jobs/:id` (раз в 5 с) и доводит
разбор до результата. Обратный прокси для `/api/deepdive/*` обязан отдавать
поток без буферизации и без сжатия — см. `deploy/caddy-music.conf`
(`flush_interval -1`).

### 1.2 `POST /api/deepdive/refine`

Тело — JSON:

```json
{
  "job": "<id задачи>",
  "iterations": 3
}
```

Поток SSE того же формата. Этапы: `refine-1` … `refine-N`, затем `result`
с `payload.code_twin.iterations` — полным журналом итераций.

Модель получает **только** JSON измерений и метрик. Ей нельзя добавлять
числа, которых нет в измерениях.

### 1.3 `GET /api/deepdive/jobs/:id`

```json
{ "ok": true, "id": "…", "status": "done", "progress": 1, "result": { … },
  "permalink": "/razbor/…", "fromDisk": false }
```

`status`: `queued` | `running` | `done` | `error`.

`fromDisk: true` означает, что задача найдена на диске, а не в памяти —
то есть сервер перезапускался, а результат сохранился. Этот эндпойнт также
используется клиентом после обрыва SSE-потока.

### 1.4 `GET /api/deepdive/health`

```json
{
  "ok": true,
  "worker": { "available": true, "url": "http://127.0.0.1:8010", "versions": { … } },
  "render": { "available": true, "bundle": "…", "builtAt": "…" }
}
```

Если воркер или рендерер недоступны — `ok: false` с перечислением того,
что именно недоступно. Режим не должен молча деградировать в «пустой разбор».

## 2. Результат (`payload`)

Результат соответствует `contracts/deep-dive.schema.json` (версия `0.1`).
Ниже — оглавление; точные ограничения типов — в схеме.

```jsonc
{
  "schema_version": "0.1",
  "track": {
    "id": "…",
    "duration_s": 214.5,
    "file_name": "…",
    "source": "upload"            // upload | own-demo
  },
  "measurements": {
    "tempo": {
      "bpm": 92.0,
      "confidence": 0.87,
      "candidates": [{ "bpm": 46.0, "kind": "half_time", "confidence": 0.51 }]

    "spectral_balance": { "sub": 0.3, "low": 0.25, "low_mid": 0.2,
                          "mid": 0.15, "high_mid": 0.07, "high": 0.03 },
    "stereo": { "correlation": 0.87, "width": 0.61 }

  "structure": [
    { "index": 0, "start_s": 0.0, "end_s": 27.3, "label": "A", "energy": 0.42 }
  ],

          "bass":   { "note_overlap": 0.8, "mean_midi_delta": 0.4 },
          "timbre": { "logmel_cosine": 0.55 },
          "groove": { "envelope_correlation": 0.42 }
        } }
    ],
    "iterations": [
      { "iteration": 1, "label": "iteration-1", "changes": [ "…" ],
        "metrics": { "overall": 0.68, "layers": { … } },
        "delta": { "overall": 0.07 }, "honesty": { "claims": [], "caveats": [ "…" ] } }
    ],
    "honesty": {
      "claims": [ "темп 92 BPM — измерено" ],
      "caveats": [ "вокал не воспроизводится", "точное сведение не воспроизводится" ]
    }
  },
  "versions": { "schema": "0.1", "worker": "…", "render": "…", "compiler": "…" },
  "errors": [ { "stage": "stems", "message": "…" } ]

```

### 2.1 Матрица «секция × слой»

Считается из `stem_descriptors.<слой>.activity` (ключ — индекс секции) и
`structure[index].label`. Это основной «вау»-экран: цветом показывается,
где какой слой играет.

### 2.2 Честность

`code_twin.honesty.caveats` — обязательный список ограничений. Для режима
«Разбор» он всегда содержит как минимум:

- «вокал не воспроизводится»;
- «точное сведение и мастеринг не воспроизводятся»;
- «это ориентир по измеримому скелету трека, а не его клон».

Список один на весь проект (`server/deepdive/caveats.js`) — и разбор, и цикл
самоулучшения показывают его одинаково.

**Деградация без разделения на стемы.** Если стемы не разделились (разделение
выключено или не удалось), двойник всё равно строится: ритм берётся из самого
микса. При этом:

- в `stem_descriptors` **ничего не добавляется** — там только измеренные стемы;
- в `caveats` добавляется «ударные не разделены: ритм двойника извлечён из
  микса, часть атак может принадлежать другим слоям»;
- в `errors` запись **не** появляется: разбор прошёл, это не поломка.

Правило: измеренное и выведенное не смешиваются.

## 3. Правила для UI

1. Панель «Разбор» — **отдельная вкладка/секция**, не ломает существующую
   студию. Все `id` новых элементов начинаются с `dive-`.
2. Режим включается **feature flag** (`?dive=1` или переключатель), чтобы
   старая студия работала как раньше.
3. Каждый вывод показывается числом + подписью уверенности.
4. Прогресс идёт по этапам SSE; при ошибке — человекочитаемый текст,
   а не стектрейс.
5. Кнопка «Показать код» открывает сгенерированный Strudel-код и **не**
   перезаписывает код в редакторе без явного подтверждения.
6. A/B-плеер: оригинал ⇄ двойник, переключение мгновенное.

## 4. Ошибки

Формат: `{ "error": "текст для человека" }`. Коды статуса — как в остальном
проекте: 400 (плохой запрос), 413 (файл слишком большой), 429 (лимит),
500 (внутренняя). Для SSE — событие `{type:'error', message}`.

Частые случаи:

| Ситуация | Поведение |
|---|---|
| воркер анализа недоступен | `stage: worker`, сообщение «сервис анализа недоступен», разбор прерывается |
| Demucs не хватило памяти | `stage: separate`, сообщение с фактической причиной; разбор продолжается **без** стемов |
| рендер двойника упал | `stage: render`, `code_twin.render.status = "failed"`, код и план остаются |
| сравнение невозможно | метрика помечается «нет данных», а не нулём |
