## 1. Как устроен контур (кратко, по коду)

```
браузер (студия)
   │  same-origin: /api/local/*
   ▼
сервер (server/routes/local.js)  ── токен живёт ТОЛЬКО здесь ──┐
   │  Bearer <LOCAL_DAEMON_TOKEN>                                 │
   ▼                                                            ▼
локальный демон (local/daemon.mjs)  ← 127.0.0.1:3213, fail-closed
```

- Транспорт — **SSE + HTTP POST**, не WebSocket (D-103).
- **Браузер к демону напрямую не ходит** (D-121): токен не покидает сервер,
  звук и прогресс идут через same-origin прокси.
- Демон: `HOST=127.0.0.1`, `PORT=3213` (`LOCAL_DAEMON_PORT`), токен
  **обязателен** — без `LOCAL_DAEMON_TOKEN` демон не стартует (fail-closed,
  exit 1). Сравнение токена — `timingSafeEqual`.
- Очередь: `queue.jsonl` (append-only, переживает SIGKILL), `concurrency=1`,
  уборка завершённых задач по TTL (`LOCAL_DAEMON_TASK_TTL_MS`, по умолчанию 6 ч).
- Приём задач ограничен: `LOCAL_DAEMON_RATE_MAX` задач в минуту (по
  умолчанию 30), тело запроса — до 8 МБ, payload — строгая Zod-схема
  (неизвестное поле — отказ).

Переменные окружения:

| Переменная | Где | Смысл |
|---|---|---|
| `LOCAL_DAEMON_TOKEN` | демон **и** сервер | общий секрет; на сервере — единственное место, где он живёт |
| `LOCAL_DAEMON_URL` | сервер | адрес демона (например `http://127.0.0.1:3213`) |
| `LOCAL_DAEMON_HOST` | демон | по умолчанию `127.0.0.1`; `0.0.0.0` — только с allow-list |
| `LOCAL_DAEMON_PORT` | демон | по умолчанию 3213 |
| `LOCAL_DAEMON_ALLOW_ANON` | демон | `1` — запросы без токена; только для локальных экспериментов |
| `LOCAL_DAEMON_ALLOWED_HOSTS` | демон | дополнительные Host через запятую (нужен для LAN-режима) |
| `LOCAL_DAEMON_ALLOWED_ORIGINS` | демон | дополнительные Origin через запятую (домен студии) |
| `LOCAL_DAEMON_RATE_MAX` | демон | лимит приёма задач в минуту |
| `LOCAL_DAEMON_TASK_TTL_MS` | демон | время жизни завершённой задачи |
| `LOCAL_DAEMON_STATE` | демон | каталог очереди и рендеров (по умолчанию `local/.state`) |

## 2. Сгенерировать токен

Токен — случайная строка, **не менее 32 символов**; демон предупреждает о
слабом токене при старте, но не запрещает (решение — за владельцем).

```powershell
# 48 байт энтропии → 64 символа base64url
$bytes = New-Object byte[] 48
[System.Security.Cryptography.RandomNumberGenerator]::Fill($bytes)
[Convert]::ToBase64String($bytes).TrimEnd('=').Replace('+','-').Replace('/','_')
```

Токен **не** пишется в репозиторий. Он живёт только в `.env` (файл в
`.gitignore`) — и на сервере, и для демона.

Проверка, что секрет не утёк: `npm run check:secrets` (шаг ворот).

## 3. Ротация токена (P3.3)

Порядок важен: сначала сервер и демон должны узнать новый токен, иначе связь
между ними порвётся на минуты.

1. **Сгенерировать** новый токен (раздел 2).
2. **Остановить демон** (`Ctrl+C` в его окне) — он читает токен при старте.
3. **Обновить `.env`**: новое значение `LOCAL_DAEMON_TOKEN` (одно и то же
   для сервера и демона).
4. **Перезапустить демон** с новым `.env`:
   ```powershell
   node local/daemon.mjs
   ```
   Ожидаемый вывод: `[local] демон слушает http://127.0.0.1:3213 (очередь: …)`.
   Предупреждение `⚠ Слабый LOCAL_DAEMON_TOKEN` — значит, токен короче 32
   символов или однообразный; заменить.
5. **Перезапустить сервер** (`node server/index.js`) — он тоже читает токен
   при старте.
6. **Проверить fail-closed и связность:**
   ```powershell
   # без токена — 401
   Invoke-WebRequest http://127.0.0.1:3213/health -UseBasicParsing -SkipHttpErrorCheck |
     Select-Object StatusCode
   # с токеном — 200 (подставьте свой, не коммитьте)
   $t = $env:LOCAL_DAEMON_TOKEN
   Invoke-WebRequest http://127.0.0.1:3213/health -Headers @{Authorization="Bearer $t"} `
     -UseBasicParsing -SkipHttpErrorCheck | Select-Object StatusCode
   # через серверный прокси (same-origin для браузера)
   Invoke-WebRequest http://127.0.0.1:3001/api/local/status -UseBasicParsing |
     Select-Object -ExpandProperty Content
   ```
   Ожидание: `401` без токена, `200` с токеном, `/api/local/status` →
   `configured: true, available: true`.
7. **Убрать старый токен** из `.env` и из истории процесса: старый токен
   больше не работает (сравнение по равенству, «срок» мгновенный).

**Если демон и сервер стартуют с разными токенами:** сервер получит 401 от
демона и покажет в студии «демон недоступен» с кодом 401. Это не поломка
контура, а правильная реакция на рассинхрон.

## 4. Если токен утерян или есть подозрение на утечку

Порядок — **сначала закрыть, потом разбираться**:

1. **Остановить демон** (`Ctrl+C`). Пока он жив — вектор жив.
2. **Сменить токен** (раздел 3) — новый токен не переиспользуется.
3. **Проверить, что старый токен больше не работает**: запрос без нового
   токена → 401; со старым токеном → 401.
4. **Посмотреть журнал демона**: `local/.state/queue.jsonl` и консоль демона.
   Токен в них **не пишется** — журнал проходит через `redactSecret`
   (проверено тестом). Если токен всё-таки найден в тексте — это дефект
   редактирования, его надо зафиксировать как дефект, а не молча править.
5. **Проверить клиентский бандл**: токен не должен попадать в `dist/`.
   Проверка: `npm run build`, затем поиск значения токена в `dist/` — если
   найдено, это утечка через фронтенд (в текущей архитектуре невозможно:
   браузер ходит только к `/api/local/*`).
6. **Проверить чужие процессы**: демон слушает `127.0.0.1`, поэтому из сети
   недоступен. Если `LOCAL_DAEMON_HOST=0.0.0.0` — демон доступен из LAN,
   и это меняет риск: см. раздел 5.

**Чего не делать:** не публиковать токен в issue/чате/репозитории и не
переиспользовать его после ротации.

## 5. Периметр: Host, Origin, лимиты

Что уже делает демон (проверено тестами, не «по описанию»):

| Проверка | Поведение |
|---|---|
| `Host`-заголовок | принимаются только `127.0.0.1:PORT`, `localhost:PORT`, `[::1]:PORT` (+ `LOCAL_DAEMON_ALLOWED_HOSTS`) — защита от DNS rebinding |
| `Origin`-заголовок | пустой — допустим (серверный прокси `Origin` не шлёт); непустой — только локальный или из `LOCAL_DAEMON_ALLOWED_ORIGINS`; чужой → 403 |
| Токен | `Authorization: Bearer`, сравнение постоянного времени; без токена → 401 |
| Payload | строгая Zod-схема по типу задачи; неизвестное поле → отказ |
| Тело | больше 8 МБ → 413 |
| Приём | больше `LOCAL_DAEMON_RATE_MAX` в минуту → 429 с `Retry-After` |
| Идемпотентность | повторная отправка с тем же `id` не ставит работу второй раз |
| Аудио | только из каталога `renders`; обход пути (`../`) → 404 |
| Секреты | токен не пишется ни в лог, ни в `queue.jsonl`, ни в текст ошибки |

**LAN-режим.** Если демон должен слушать не только петлю:
`LOCAL_DAEMON_HOST=0.0.0.0` **плюс** явный `LOCAL_DAEMON_ALLOWED_HOSTS` и
`LOCAL_DAEMON_ALLOWED_ORIGINS`. Без allow-list демон в LAN не отвечает —
это by design, а не поломка.

**CORS сам по себе не авторизует.** Авторизация — токен; Origin — фильтр,
а не замена токену.

## 6. Chrome Local Network Access (знание, P3.5)

**Сегодня это знание, а не код:** браузер ходит к демону только через
same-origin прокси сервера (D-121), поэтому LNA **не задействован** и
разрешение браузера не требуется.

Если в будущем появится прямой путь браузер → демон, вот что нужно знать
заранее (по документации Chrome):

- `http://localhost` — потенциально надёжный контекст. **Самоподписанный
  `https://localhost` не нужен** и создаёт проблемы доверия (предупреждения,
  исключения для сертификата).
- Публичный сайт → `localhost`/local-network: Chrome требует разрешения
  **Local Network Access** (нужен secure context):
  - `fetch` и подресурсы — **Chrome 142**;
  - WebSocket/WebTransport — **Chrome 147**;
  - в **Chrome 145** разрешение разделено на `local-network` и
    `loopback-network`;
  - в **Chrome 156** убирается временный opt-out;
  - заголовки PNA (Private Network Access) устарели.
- Разрешение даёт **пользователь**, а не браузер автоматически; mixed-content
  для локальных запросов ослабляется при выданном разрешении.
- Запросы из Service/Shared Worker требуют предварительного grant у origin.
- Firefox тоже shipped это поведение; Brave — своё localhost-разрешение.
- `fetch` можно аннотировать `targetAddressSpace: "local"` (нужно для
  корректного определения адресного пространства).
- **Разрешение браузера ≠ авторизация.** Даже выданное разрешение не
  заменяет токен и allow-list.

**Следствие для проекта:** прямой путь браузер → демон — это отдельное
решение владельца (D-запись), и оно потребует UX разрешения и feature-detect.
Сегодня контур D-103/D-121 работает и ломать его не нужно.

### 6.1. Что измерено на машине владельца (19.11.2026, E-044)

Документация выше остаётся верной, но часть её утверждений раньше была
«знанием из документации». Теперь есть замер на настоящем браузере.

**Стенд.** Демон поднят на `127.0.0.1:3213` (токен задан, fail-closed).
Рядом подняты два обычных HTTP-сервера с permissive-CORS:

- `http://192.168.1.6:8080` — origin в локальной сети (сценарий «студия
  открыта в сети Wi-Fi, владелец заходит с другого устройства»);
- `http://127.0.0.1:8081/ping` — цель, которая **пишет каждый запрос в лог**
  (нужно, чтобы отличить «запрос не дошёл» от «ответ спрятан CORS»).

**Браузер:** Chrome **148.0.7778.280**, Electron 42.11.16 (встроенный браузер
сессии), Windows.

**Результаты:**

| Запрос (из origin `http://192.168.1.6:8080`) | Ответ | Запрос дошёл до цели? |
|---|---|---|
| `fetch('http://127.0.0.1:8081/ping')` | **200**, тело прочитано | да, цель залогировала запрос |
| то же с `targetAddressSpace: 'local'` | **200** | да |
| `fetch('http://192.168.1.6:8081/ping')` | **200** | да |
| `fetch('http://127.0.0.1:3213/health')` (демон), `mode: 'cors'` | «Failed to fetch» | **да** (no-cors вернула opaque-ответ) |
| `fetch('http://127.0.0.1:3213/health')`, `mode: 'no-cors'` | opaque, статус 0 | да, запрос отправлен |

**Что из этого следует (важно для решения о прямом пути):**

1. **Chrome 148 в этой сборке НЕ блокирует запрос из приватной LAN-origin в
   loopback** — разрешение LNA не запрашивалось, запрос дошёл, ответ прочитан.
   Значит для сценария «студия в локальной сети → демон» браузерного
   разрешения не нужно.
2. **Демон недоступен из браузера не из-за LNA, а из-за собственной политики:**
   он отвечает `403 {"error":"Origin не в списке доверенных"}` на Origin
   браузера и `401` без Origin, а **не отдаёт CORS-заголовков** — поэтому
   браузер прячет отказ («Failed to fetch»). Проверено с машины:
   `fetch('http://127.0.0.1:3213/health', {headers:{Origin:'http://192.168.1.6:8080'}})`
   → 403; без Origin → 401.
3. Токен демона в браузере не нужен и не попадает: авторизация — на сервере
   (D-121). Если в будущем появится прямой путь, **демон обязан отдавать
   CORS-заголовки** для origin'а студии — иначе отказ будет выглядеть как
   «сеть не работает», а не как «доступ запрещён».
4. `targetAddressSpace: 'local'` в этом браузере принимается и не ломает
   запрос; сам по себе он разрешения не даёт.

**Что осталось «нет данных»:** сценарий «публичный сайт → localhost». На
машине владельца нет интернета и DNS (`example.com` не резолвится), поэтому
публичный origin не создать. Поведение Chrome для public→loopback в этой
сборке **не измерено** — для него нужен интернет и отдельный прогон.

> **Обновлено 19.11.2026 (E-047):** этот пробел **закрыт** — публичный origin
> удалось создать, сценарий измерен в **настоящем Chrome 158**. См. §6.2.

### 6.2. Публичный origin → loopback в настоящем Chrome 158 (19.11.2026, E-047)

Это ровно тот сценарий, ради которого Local Network Access и существует. В
E-044 он остался «нет данных»; здесь — измерен.

**Стенд.** Публичная страница-зонд развёрнута на внешнем origin
(`https://5whh8l06ukzr9.space.mcode.io`, secure context = true). Цель —
обычный HTTP-сервер на `127.0.0.1:8123` с permissive-CORS, который **пишет
каждый запрос в лог**: без этого «Failed to fetch» не отличить от «ответ
спрятал CORS». Браузер — **настоящий Google Chrome 158.0.8127.36** (headless,
`C:\Program Files\Google\Chrome\Application\chrome.exe`), а не встроенный
Electron. Зонд: `scripts/probe-lna-public.mjs`.

**Результат — все четыре запроса заблокированы, ни один не дошёл до цели:**

| Запрос с публичного origin | В странице | Дошёл до цели? | Что сказал Chrome |
|---|---|---|---|
| `fetch('http://127.0.0.1:8123/ping')` | «Failed to fetch» | **нет** | `blocked by CORS policy: Permission was denied for this request to access the 'loopback' address space` |
| то же с `targetAddressSpace: 'local'` | «Failed to fetch» | **нет** | `Request had a target IP address space of 'local' yet the resource is in address space 'loopback'` |
| `fetch('http://localhost:8123/ping')` | «Failed to fetch» | **нет** | то же — permission denied для `loopback` |
| `fetch('http://127.0.0.1:8123/ping', {mode:'no-cors'})` | «Failed to fetch» | **нет** | то же |

Все четыре — `net::ERR_FAILED`. Лог цели **пуст**.

**Что из этого следует.**

1. **Публичная страница не достучится до локального демона в Chrome 158.**
   Запрос **не покидает браузер**: сервер-цель не зафиксировал ни одного
   попадания. Это не CORS-заголовки нашей цели и не политика демона — это
   модель разрешений самого браузера.
2. **Аннотация `targetAddressSpace: 'local'` не обходит разрешение** и вдобавок
   даёт отдельный отказ: адресное пространство цели — `loopback`, а
   аннотировано `local`.
3. **Решение D-121 подтверждено измерением:** единственный рабочий путь к
   демону — same-origin прокси сервера. Если в будущем появится прямой путь
   браузер → демон, он упрётся в диалог разрешения LNA (в headless его выдать
   нельзя) — это отдельное решение владельца с UX и feature-detect.
4. **Честная граница замера:** в headless-Chrome диалога разрешения нет, поэтому
   измерен **отказ без выданного разрешения**. Мы не утверждаем, что Chrome
   **никогда** не пропустит такой запрос: в обычном окне пользователю показывается
   запрос разрешения, и исход зависит от его ответа. Измерено ровно то, что
   видно машине: без интерактивного grant запрос не проходит.

**Доказательство:** `docs/evidence/local/lna-public-2026-11-19.json`.

## 7. Браузерные вычисления (знание, P3.6)

Не новый ML в этой сессии — только карта «что где считать», чтобы следующий
раз не изобретали заново:

- **Real-time DSP** — `AudioWorklet`: отдельный аудио-поток, не блокирует
  главный поток; WASM внутри worklet'а — ради скорости. Инфраструктура
  worklet в проекте **уже есть**: `scripts/build-worklet.mjs`
  (`npm run build:worklet`, подключается как `prebuild`/`predev`).
- **CPU-bound ML** — `Web Worker` или WASM (ONNX wasm backend), **не**
  главный поток; внутри воркера нет DOM.
- **`SharedArrayBuffer`** требует заголовков COOP/COEP — это влияет на
  `helmet`: проверять фактические заголовки ответа, а не обещать, что они
  есть. В текущей конфигурации сервера `crossOriginEmbederPolicy` выключен
  явно (`helmet({ crossOriginEmbederPolicy: false })`) — то есть
  `SharedArrayBuffer` сейчас недоступен. Если понадобится — это отдельная
  задача с проверкой совместимости.
- **Новые зависимости и браузерный ML в объём P0–P3 не входят** и не
  добавлялись.

## 8. Быстрая проверка контура (без браузера)

```powershell
# 1. Демон жив и fail-closed
curl.exe -s -o NUL -w "%{http_code}" http://127.0.0.1:3213/health          # ожидается 401
# 2. С токеном
curl.exe -s -o NUL -w "%{http_code}" -H "Authorization: Bearer $env:LOCAL_DAEMON_TOKEN" http://127.0.0.1:3213/health   # 200
# 3. Чужой Host — отказ (защита от DNS rebinding)
curl.exe -s -o NUL -w "%{http_code}" -H "Host: attacker.example" -H "Authorization: Bearer $env:LOCAL_DAEMON_TOKEN" http://127.0.0.1:3213/health  # 403
# 4. Чужой Origin — отказ
curl.exe -s -o NUL -w "%{http_code}" -H "Origin: https://evil.example" -H "Authorization: Bearer $env:LOCAL_DAEMON_TOKEN" http://127.0.0.1:3213/health  # 403
# 5. Через серверный прокси (то, что видит браузер)
curl.exe -s http://127.0.0.1:3001/api/local/status
```

Ожидаемые коды: 401 / 200 / 403 / 403 / JSON со `configured: true`.
