01 — суть проекта

Три слоя измерений вместо веры в промты

Главная инженерная идея проекта: качество проверяется по трём слоям, от дешёвого к дорогому. Слой L1 отсекает мусор за миллисекунды, L0 даёт техника по аудио, L2 — только то, что стоит человеческого времени.

L1 — символьная музыкальность

Источник истины — события движка Strudel (queryArc), а не свой парсер mini-нотации. Считается форма, энергия, мотив, замыкание фразы, лок бас–кик.

Стоимость: миллисекунды

L0 — техника

Клиппинг, true peak, LUFS-I, повторяемость рендера, null-тест суммы стемов. Свой DSP по BS.1770-4, сверен с ffmpeg ebur128 (|ΔLUFS| ≤ 0.05).

Стоимость: секунды

L2 — люди

Слепой A/B с выравниванием громкости, порог по нижней границе Wilson, canaries против взлома метрик. Сейчас: 0 живых пар — слой честно не включён.

Стоимость: минуты человека

Что делает проект необычным. Правки («сделай мрачнее») идут не по тексту кода, а по типизированному Composition IR: модель отдаёт план, детерминированный компилятор собирает из него валидный по построению Strudel-код. Поэтому «мрачнее» — это измеримая правка, а не перегенерация. Сырой код от LLM живёт только в узкой свободной полосе и проходит валидаторские ворота.

Что здесь работает как задумано

  • Код написан компилятором, а не моделью: роль → шаблон из библиотеки → arrange() по секциям. Невалидный код невозможен по построению.
  • Бас транспонируется после .scale(key) — строго -12, иначе Strudel молча игнорирует значение.
  • Партии не сливаются в одну октаву: у каждой роли своя транспозиция.
  • Музыкальный разбор считается по событиям движка, а не по своему парсеру: на <0 5 2 6>/2 свой парсер даёт 1 событие, Strudel — 4.

Сквозной цикл замкнут

  • Правки «мрачнее / светлее / энергичнее» — типизированные трансформации IR, не перегенерация текста.
  • «Найти лучший (16)» — символьный поиск по 16 кандидатам, рендер только финалистам.
  • Правка микшера пишется в текст кода и переоценивается с дебаундом 250 мс.
  • Есть adversarial-фикстуры: эталон обязан набирать больше каждой из них, иначе падает тест.

05 — как считается оценка

Формула, которую можно проверить и оспорить

Общая оценка — взвешенное среднее по слоям, у которых есть данные. Слой без измерений исключается, а не штрафуется (правило D-080).

// server/deepdive/compare.js LAYER_WEIGHTS = { rhythm: 0.35, bass: 0.30, timbre: 0.25, groove: 0.10 } overall = Σ(value × weight) / Σ(weight) // только по слоям с данными // подстановка фактического прогона: overall = (0.4372×0.35 + 0.9629×0.25 + 0.5×0.10) / (0.35 + 0.25 + 0.10) = 0.6339 // бас выпал → знаменатель 0.70, а не 1.00
Следствие, которое стоит знать. Бас не измерился, поэтому его вес 0.30 выпал и знаменатель сжался до 0.70 — оставшиеся слои получили повышенный вес. Число 0.634 честное как «сходство по трём слоям», но оно не сравнимо с разбором, где бас измерился: там шкала другая. Это не баг расчёта, но это делает «общее сходство» нестабильной метрикой для сравнения разных треков между собой.

07 — оценка

7.3 из 10: сильный инженерный проект, средний продукт

7.3из 10 · взвешенная оценка

Это редкий проект, где инженерная культура обгоняет продукт. Решения принимаются по замерам, а не по ощущениям; каждое архитектурное решение записано с причиной; отрицательные результаты считаются поставкой. Такое встречается редко.

Но продуктовая сторона отстаёт: первый экран пустой, главный рычаг (человеческие метки) обесточен, а главная функция — разбор — на 4-минутном треке упирается в 56 минут и 2 vCPU. Между «инженерно отличным» и «пользовательским продуктом» остаётся вся дистанция.

Почему высокие баллы

  • 966 тестов зелёные на текущем коммите, линтер чист, бюджеты и проверки в гейте.
  • Свой DSP сверен с ffmpeg/libebur128, рендер повторяем бит-в-бит, в отчётах renderFingerprint.
  • Каждый дефект, найденный замером, закрыт коммитом с решением в журнале (D-089…D-093).
  • Деградация честная: «нет данных» ≠ ноль, оговорки пишутся в каждый отчёт.

Почему низкие баллы

  • Качество музыки не подтверждено слушателем: символьный скор — гипотеза, слой L2 пуст.
  • Главный фича упирается в железо: 56 минут на трек — это «фоновый режим», а не «продукт».
  • Бас-слой и грув не работают — два слоя из четырёх дают пустой или нулевой вклад.
  • Пустой первый экран, ослабленный CSP, открытая ссылка на разбор, домен временный.

08 — что делать дальше

Три шага, которые двигают проект сильнее всего

шаг 1

20 пар в день

Открыть /tinder.html и оставить 20 суждений — около 6 минут. Это единственный путь, который разблокирует выученную цель: сейчас 0 живых пар, нужно 50 разных промтов. Пока модель не проверена людьми, её нельзя ставить целью оптимизации — и проект сам это не даёт сделать.

Усилие: 6 минут в день

шаг 2

Починить бас, грув и звук разбора

Два слоя из четырёх дают ноль или «нет данных» на реальном треке, а аудио-рендер разбора падает на живом контексте. Это самый дешёвый способ поднять качество: измерить питч баса из разделенного стема, научиться считать грув так, чтобы нулевая корреляция давала 0, и гасить живое воспроизведение перед офлайн-рендером.

Усилие: 1–2 дня

шаг 3

Подключить учёт LLM

Одна строка в server/llm/router.js — и /api/stats перестаёт показывать нули. После этого можно честно назвать цену трека, «найди лучший» и ночного прогона, а не считать её на глаз.

Усилие: час

Честное предупреждение. На метриках общая оценка двойника сейчас 0.634, ритм F1 — 0.437. Это «узнаваемый скелет», а не «похожий трек». Пока честные метрики такие, продавать продукт как «сделает как оригинал» нельзя — и отчёт об этом честно предупреждает в каждом разборе. Это правильное поведение проекта, но это же и ограничение его текущей ценности.
