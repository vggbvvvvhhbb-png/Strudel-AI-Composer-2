# Символьный оракул — измерение трека без звука

*Версия 1 · 14 ноября 2026*

## Зачем

Бриф v2 §6: чтобы оценивать сотни кандидатов, нужен оракул, который работает
за миллисекунды. Рендер — это секунды, а перебрать сотню вариантов рендером
нельзя.

Оракул отвечает на вопрос **«структура трека осмысленна?»**, а не «красиво ли
это?». Второй вопрос — только человек (дорожка H).

## Экономика (измерено)

`tests/spike/oracle-timing.probe.mjs`, трек 48 тактов, 11 ролей:

| Путь | Время | Кандидатов/с |
|---|---|---|
| `queryArc` движка, 32 такта | 91 мс | 11 |
| `queryArc` движка, 64 такта | 146 мс | 7 |
| `compileIR` | 0.7 мс | 1400 |
| **Быстрый оракул (IR → события → метрики)** | **1.6…22 мс** | **45…600** |

Отсюда двухслойная архитектура.

## Слои

### Слой 1 — быстрый (`src/oracle/ir-events.js`)

События считаются прямо из IR, по тем же правилам, по которым компилятор
строит код: общие `grooveSteps`, `buildChordPlan`, `motifToMini`,
`roleLevel`. Одна правка — один источник истины.

Событие: `{ role, t, dur, pitches[], vel, sample, section, bar }`,
`t` — позиция в тактах (1 такт = 1.0).

### Слой 2 — точный (`server/music/strudel-runtime.mjs`)

Те же события, но из `queryArc` настоящего движка. Используется для
финалистов и для сверки.

### Граница точности (D-048)

| Что | Быстрый слой | Движок |
|---|---|---|
| Атаки всех ролей | **точно** | точно |
| Длительности | **точно** | точно |
| Число событий | **точно** | точно |
| Высоты ударных, баса, лида, арп | **точно** | точно |
| Высоты аккордов | приближение (каноническое сомкнутое расположение от якоря) | вокальный алгоритм движка |

У аккордов воспроизводится ритм, но не вокальный алгоритм: он нужен для
покадрового разбора голосов, а не для метрик (движение корней, напряжение,
регистр). Это объявлено явно, а не спрятано.

**Сверка обязательна:** `tests/unit/oracle-consistency.test.js` сравнивает
быстрый слой с движком по числу событий и таймингам атак на четырёх жанрах.
Расхождение = провал теста.

## Метрики (`src/oracle/metrics.js`)

| Метрика | Что значит |
|---|---|
| `energyProfile` | энергия по тактам: Σ (velocity × вес роли) |
| `targetProfile` | целевая кривая: энергия секции, развёрнутая по тактам |
| `energyCorrelation` | Пирсон между измеренным и целевым (цель ≥ 0.7) |
| `sectionContrasts` | косинусное расстояние векторов признаков соседних секций (цель ≥ 0.25) |
| `motifRecurrence` | сколько раз возвращается рисунок, в скольких секциях, сколько вариаций |
| `phraseClosure` | доля консеквентов, закрытых устойчивой ступенью (цель ≥ 0.7) |
| `bassKickLock` | доля атак баса, совпавших с киком (цель ≥ 0.6) |
| `scaleFit` | доля нот мелодии в ладе |
| `harmonicFit` | доля аккордовых тонов в ладе (септимы вне лада — норма) |
| `microtiming` | стандартное отклонение атак ударных от сетки, в мс |
| `variation` | доля уникальных тактов (ритм + высоты) |
| `roleBalance` | доля каждой роли в сумме уровней |

**Тональность мелодии и гармонии разные.** Септима доминанты по определению
вне тональной шкалы — штрафовать за это значит наказывать за правильную
гармонию. Поэтому `scaleFit` считается только по лиду и арпу, а аккордовые
тона живут в отдельной метрике.

## Линтер (`src/oracle/lint.js`)

Замечания того же формата, что у аудио-QA, но с типизированными
трансформациями IR вместо правок текста:

```js
{ code, severity: 'error'|'warning'|'info', params, suggestedTransforms, message }
```

Коды: `sections-too-few`, `empty-section`, `contrast-low`,
`energy-correlation-low`, `peak-not-above-break`, `no-hook`,
`hook-without-variation`, `phrase-not-closed`, `bass-kick-uncoupled`,
`notes-outside-scale`, `density-too-high`, `density-too-low`,
`bass-register-high`, `timing-mechanical`.

**Пороги зависят от жанра** (D-051). У D&B 33 события/с — норма, а не «каша»;
оффбитный бас в синтипопе — признак жанра, а не рассинхрон. Единые пороги
врали бы и врали бы постоянно.

Проверка линтера — mutation testing: в эталон вносятся заведомые дефекты,
линтер обязан их найти. Требование брифа: recall ≥ 95 %, precision ≥ 90 %.
Фактически recall = 100 % на 20 проверках (5 дефектов × 4 жанра), precision
= 100 % (на здоровых треках ошибок нет).

## Скор (`src/oracle/score.js`)

Семь составляющих, сумма 100: форма 20 · энергия 20 · мотив и фраза 15 ·
грув 15 · тональность 10 · плотность 10 · разнообразие 10. За штраф за
ошибки линтера снимается до 30 баллов.

**Скор — гипотеза, а не истина.** Он не проверен человеческими парами (H3),
поэтому не может быть целью оптимизации (анти-цель §2.8). Веса помечены
непроверенными, отчёт показывает все составляющие, а канарейки не дают ему
взломаться.

## Канарейки (`src/oracle/canaries.js`)

Пять подлых треков: три одинаковые секции · идеально ровный луп · случайные
ноты в ладу · тишина с одним кликом · плотный шум.

Правило: канарейка обязана получить скор **ниже медианы** нормального корпуса.
Иначе скор взломан, и эволюцию скилов останавливают.

## Поиск (`src/oracle/search.js`)

Best-of-N по детерминированным мутациям IR: шаблон грува, свинг, плотность,
фильтр, регистр, энергия секции, темп, гармония, вариация мотива, палитра.

```js
const result = searchBest(ir, { n: 16, topK: 3 });
// result.candidates — лучшие; result.elapsedMs — время
```

Мутации адресные (seed, индекс), поэтому выдача воспроизводима.

**Честная оговорка.** На треках с высоким исходным скором (90+) мутации
обычно его снижают: поиск работает как фильтр дефектов, а не как улучшатель.
Проверить, улучшает ли он (H2), можно только на человеческих парах.

## Критик (`src/oracle/critic.js`)

Замечания → предложенные трансформации → новый скор. Правка принимается,
только если скор вырос и число ошибок линтера не увеличилось; иначе откат.
Итераций не больше трёх, исходный IR не мутируется.

## API

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/music/ir/plan` | описание → IR → код + разбор |
| POST | `/api/music/ir/transform` | правка плана + дельта |
| POST | `/api/music/ir/search` | best-of-N |
| POST | `/api/music/ir/critique` | критик-цикл |

Серверный инвариант (§2.5) соблюдён: DSP считает браузер, сервер считает
только символьную структуру и проверяет форму отчётов.
