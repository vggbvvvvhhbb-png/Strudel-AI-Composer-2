# RUNBOOK — память Demucs на Windows (P0.8)

**Статус документа:** инструкция владельцу. Часть шагов уже выполнена на этой
машине (числа ниже), часть — **ОЖИДАЕТ ПРОВЕРКИ ВЛАДЕЛЬЦЕМ**: реальный отказ по
памяти на реальном треке воспроизвести не удалось, потому что причина
исторического сбоя (E-026) без его native stack не доказана.

**Кому:** владелец машины с RTX 2060 (8 ГБ VRAM), Windows, Python 3.12.16,
torch 2.5.1+cu121, Demucs 4.1.0 (`F:\strudel-env`).

**Что уже работает (не надо делать заново):**
- D-153 — предохранитель: при свободном commit memory меньше
  `DEMUCS_MIN_COMMIT_MB` (по умолчанию **3072 МБ**) Demucs **не запускается**,
  воркер отвечает терминальным отказом с числами.
- D-156 — мьютекс `heavy_lock` работает на Windows (`msvcrt.locking`),
  второй тяжёлый job ждёт, а не идёт параллельно.
- D-158 — отказ по памяти больше не «ошибка 500»: статус
  `insufficient_memory` с `kind`, `attempts[]`, `measured`, `degraded`.

**Чего этот runbook НЕ меняет:** пакеты, драйверы, файл подкачки и чужие
процессы не трогаем без отдельного решения владельца. Правится только
конфигурация Windows и порядок прогона.

---

## 0. Что означают коды отказа

| `kind` | Что случилось | Что делать |
|---|---|---|
| `commit_limit` | Windows не дал выделить память: WinError 1455 «paging file is too small» | файл подкачки (шаг 1) + закрыть тяжёлые приложения |
| `cuda_oom` | Не хватило VRAM/памяти аллокатора CUDA | лестница уже отработала (segment 7 → 5, без кеша CUDA); дальше — CPU или меньше сегмент |
| `host_alloc` | Не хватило обычной RAM (CPU-аллокатор PyTorch) | закрыть Chromium/Ollama, повторить (шаг 3) |
| `worker_crashed` | Процесс упал нативно (0xC0000005 / 137 / -9) | это сбой процесса, а не нехватка памяти; лестница не помогает; нужен native stderr из `demucs.stderr.log` |

Лестница деградации (по порядку): `baseline` → `shifts0` → `segment7` →
`segment5_overlap` → `no_cuda_cache` → `cpu` (только если свободного commit
хватает). Каждый шаг кроме первого ставит `degraded: true`.

**Честно:** влияние деградации на качество стемов **не измерено** («нет
данных»). Никто не обещает, что `segment 5` звучит так же, как `segment 7`.

## 1. Файл подкачки (решение владельца, шаг 1)

Windows без overcommit: лимит выделения = физическая RAM + файл подкачки.
Исторический отказ (E-026) — это лимит commit, а не «не хватило видеопамяти».

1. Проверить текущее состояние: Диспетчер задач → Производительность → Память →
   «Зафиксировано» / «Лимит» (или PowerShell: `Get-Counter '\Memory\Committed Bytes','\Memory\Commit Limit'`).
2. Если «Лимит» меньше физической RAM + 16 ГБ — увеличить файл подкачки:
   *Параметры системы → Дополнительные параметры → Дополнительно → Виртуальная
   память → Изменить* → «Управлять файлом подкачки вручную» → задать размер
   «по выбору системы» на диске со свободными **≥16 ГБ**.
3. Перезагрузка — обязательна, файл подкачки меняется только при старте Windows.
4. **Не** трогать пункт «Автоматически управлять размером файла подкачки» без
   отдельного решения: это может ухудшить (или улучшить) поведение машины
   владельца в других задачах.

**Замер, который уже есть (E-029, 19.11.2026):** доступный commit падал до
**12.22 МБ** при физически свободных **2032.72 МБ**; total commit 25398.86 МБ.
Это и есть signature лимита commit: физическая память была, а выделять было
нечего.

## 2. Снять baseline ДО прогона (шаг 2)

Записать в блокнот (или в `docs/EXPERIMENTS.md`, раздел «Результаты владельца»):

```
Дата/время: ______
Процесс                    Comitted Bytes   Commit Limit   GPU
chrome.exe                 __ МБ           __ МБ          __ МБ
ollama.exe                 __ МБ           __ МБ          __ МБ
node.exe (демон)           __ МБ           __ МБ          __ МБ
python.exe (воркер)        __ МБ           __ МБ          __ МБ
ИТОГО                      __ МБ           __ МБ
Свободный commit (в ответе воркера, поле measured.available_commit_mb): __ МБ
```

Команды:

```powershell
# Коммит и лимит — те же счётчики, что читает воркер (GlobalMemoryStatusEx)
Get-Counter '\Memory\Committed Bytes','\Memory\Commit Limit' | Select-Object -ExpandProperty CounterSamples |
  Select-Object Path, @{n='MB';e={[math]::Round($_.CookedValue/1MB,1)}}

# Видеопамять и её использование
nvidia-smi --query-gpu=name,memory.total,memory.used,utilization.gpu --format=csv

# Кто ест память — по процессам
Get-Process | Sort-Object WorkingSet64 -Descending | Select-Object -First 12 Name,Id,
  @{n='WorkingSetMB';e={[math]::Round($_.WorkingSet64/1MB,1)}}
```

Полезно: `measured.available_commit_mb` в ответе воркера — это тот же
свободный commit, что показывает Диспетчер задач. Значения должны сходиться
(±округление): если не сходятся — это отдельный дефект измерения, записать.

## 3. Прогон 60-секундного клипа (шаг 2)

```powershell
# 1) Поднять Python-воркер из корня проекта (свежий код)
F:\strudel-env\Scripts\python.exe server\deepdive\analysis\worker.py

# 2) Во время прогона — снимать память (шаг 3 сценария: в момент пика)
nvidia-smi --query-gpu=memory.used --format=csv -l 5

# 3) Живой гейт B: он сам ставит separate на собственный 60-секундный WAV
node scripts/gate-b.mjs --out docs/evidence/agent/gate-b-<ДАТА>.json
```

**Что смотреть в отчёте:**
- `separationSeconds` — время сепарации (измеренное значение, не ожидание);
- `firstTwinSeconds` — сепарация + рендер 16 тактов;
- `checks` — 13 проверок, из них 13-я («WAV побайтово идентичны») **не является
  успехом**: на этой машине разница 3.05e-5 при допуске 1e-4 (D-104),
  побайтовое равенство не заявляется;
- `attempts[]` — если сепарация шла по лестнице, здесь будут её шаги и
  `degraded`.

**Ориентир, который уже измерен (19.11.2026, E-031):** сепарация 60 с —
**7.677 с** wall, first-twin — **9.614 с** при лимите 420 с; свободный commit
во время сепарации опустился с **4364 МБ** до **3352 МБ**. Порог 3072 МБ
близок: на загруженной машине ожидаем **честный отказ по предохранителю**, а
не падение.

## 4. Прогон 4-минутного трека (шаг 2)

```powershell
node scripts/probe-reference.mjs --out docs/evidence/agent/reference-<ДАТА>.json
```

Тот же замер памяти до/во время/после. Паспорт референса содержит темп, лад,
`separationSeconds` и дескрипторы четырёх стемов. Если паспорта нет — в ответе
будет `status: insufficient_memory` с числами, а не выдуманный паспорт.

**Ориентир (E-031):** паспорт получен за 12.934 с; рендер 4-минутного трека —
54.7 с при лимите 900 с.

## 5. Закрыть Chromium и Ollama, повторить (шаг 3)

1. Закрыть **все** окна Chromium (движок рендера — самый крупный потребитель
   commit: демон поднимает headless Chromium, и он живёт между задачами).
2. Остановить Ollama, если она запущена (`ollama ps` — посмотреть, что живо).
3. Повторить пункт 3 и 4, записать числа в отдельную колонку.

Цель проверки — не «стало быстрее», а **виден ли эффект**: если без Chromium
commit падает заметно меньше, значит, упирается именно он, и это правильный
результат для планирования ресурсов.

## 6. Негативный тест: два прогона одновременно (шаг 4)

**Ожидание:** честный `insufficient_memory` (или ожидание в очереди), а **не**
краш и не «успех».

```powershell
# Два вызова separate одновременно — второй должен ждать мьютекс (D-156)
# или честно отказать по памяти (D-153/D-158)
```

Что должно быть верно:
- ни один процесс не упал нативно (код выхода 0xC0000005 / 137 не появился);
- в ответе второго — `kind` и числа, а не «неизвестная ошибка»;
- в `demucs.stderr.log` лежит полный native stderr (D-153) — он нужен, если
  отказ всё-таки случился.

Мьютекс уже доказан регрессией (`tests/unit/test_separation_worker.py`), а на
живой машине проверка D-156 выполнена. **ОЖИДАЕТ ПРОВЕРКИ ВЛАДЕЛЬЦЕМ** — тот
живой одновременный прогон, который даст числа «свободный commit при двух
задачах».

## 7. Записать результаты (шаг 5)

Формат — в `docs/EXPERIMENTS.md`, новый раздел `E-0NN`, по образцу E-029…E-032:

```
Дата, версии (torch/Demucs/Python), размер файла подкачки и «Зафиксировано/Лимит»
до, во время и после каждого прогона, nvidia-smi до/во время/после,
что запускалось (60 с / 4 мин / два одновременно), время сепарации,
first-twin, kind отказа при нехватке, degraded, attempts[],
закрывались ли Chromium/Ollama и что изменилось.
```

Обязательно: **отрицательный результат — тоже результат.** Если отказа не
было — так и пишем, что отказа не было, с числами.

## 8. Что менять НЕЛЬЗЯ

- **D-083:** веса Demucs «only for scientific purposes» — коммерческое
  разделение по умолчанию **выключено** и не включается. Статус весов не
  меняется.
- **D-089:** серверный GPU закрыт, CPU-only — не пересматривается.
- Не удалять `F:\strudel-env`, не переустанавливать torch/Demucs, не менять
  драйверы: цель — измерить существующую конфигурацию, а не чинить её
  переустановкой.
- Не обходить предохранитель 3072 МБ (`DEMUCS_MIN_COMMIT_MB=1`), чтобы
  «получить результат»: отказ по предохранителю — это правильное поведение.

## 9. Переменные окружения, которые это затрагивает

| Переменная | Где | Смысл |
|---|---|---|
| `DEMUCS_MIN_COMMIT_MB` | воркер | порог свободного commit, по умолчанию 3072 |
| `DD_HEAVY_LOCK` | воркер | путь файла мьютекса; на Windows по умолчанию — временный каталог пользователя |
| `DD_HEAVY_LOCK_WAIT_S` | воркер | сколько ждать занятый мьютекс, по умолчанию 3600 |
| `DD_PYTHON` | воркер | интерпретатор для Demucs (по умолчанию venv проекта) |
| `DD_PORT` | воркер | порт воркера, по умолчанию 8010 |
| `PYTORCH_CUDA_ALLOC_CONF` / `PYTORCH_ALLOC_CONF` | окружение | настройка аллокатора; значение владельца **не перезаписывается** воркером |
