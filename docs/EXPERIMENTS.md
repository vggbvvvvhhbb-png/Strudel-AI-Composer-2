## Закрытые и измеренные

### E-001. Символьный оракул успевает за поиск кандидатов — ✅

**Гипотеза.** События трека можно посчитать без движка и получить прирост
скорости в разы, не потеряв точности на ритмическом скелете.

**Метод.** `tests/spike/oracle-timing.probe.mjs`: один и тот же трек (48
тактов, 11 ролей) прогнан через `queryArc` движка и через быстрый оракул.

**Результат.**

| Путь | Время | Кандидатов/с |
|---|---|---|
| `queryArc`, 32 такта | 91 мс (мин 86) | 11 |
| `queryArc`, 64 такта | 146 мс | 7 |
| `compileIR` | 0.69 мс | 1443 |
| Быстрый оракул | 1.6…22 мс | 45…600 |

**Сверка точности.** `tests/unit/oracle-consistency.test.js`: на четырёх жанрах
число событий и тайминги атак совпадают с движком (допуск 0.01 такта на
микротайминг). У аккордов сверяются атаки, а не высоты: вокальный алгоритм
движка не воспроизводится (D-048).

**Решение.** ✅ Двухслойный оракул принят. Быстрый слой — для поиска, точный —
для финалистов. Расхождение слоёв ломает тест.

**Дата.** 14.11.2026.

### E-002. PRNG проекта давал неравномерное распределение — ✅ (дефект найден)

**Гипотеза.** FNV-1a в качестве источника случайности даёт равномерное
распределение по [0, 1).

**Метод.** `tests/spike/prng-distribution.probe.mjs`: 100 000 значений
`random01` + броски по 8 индексам подряд.

**Результат (до фикса).** Гистограмма по десятым интервалам:
`0.0 % 0.0 % 0.3 % 0.2 % 10.5 % 46.4 % 12.5 % 19.3 % 0.2 % 10.6 %`.
Среднее по восьми броскам — **0.681** вместо 0.5. Младший бит FNV для
последовательных ключей чередуется строго (`1010101010010101`).

**Причина.** У FNV-1a слабо смешиваются **старшие** биты, а `random01` берёт
именно их (`hash / 2^32`). Последовательные адреса отличаются последним
символом, и их хэши почти не расходятся в старших битах.

**Решение.** ✅ Добавлен финализатор `fmix32` (MurmurHash3) — avalanche-шаг.
После фикса гистограмма: `10.0 % 9.9 % 9.9 % 10.0 % 9.9 % 9.9 % 10.1 %
10.0 % 10.1 % 10.1 %`.

**Побочный эффект.** Сломанным оказался и отсев шагов по плотности в
`groove.js` — он считал своим FNV без финализатора. Теперь использует общий
`hash32`.

**Дата.** 14.11.2026.

### E-003. Линтер находит дефекты и не выдумывает замечания — ✅

**Гипотеза.** Линтер по структуре трека найдёт ≥95 % внесённых дефектов и не
даст ложных срабатываний на здоровых треках.

**Метод.** Mutation testing: 5 дефектов × 4 жанра = 20 проверок. Дефекты:
трек без формы, пустая секция, механический тайминг, бас в середине, ноты вне
лада.

**Результат.** Recall **20/20 = 100 %** (порог 95 %). Precision **100 %**: на
пяти здоровых треках ошибок линтера нет.

**Побочная находка.** Первая версия дефекта «плоский бас» не срабатывала:
**компилятор игнорировал `layer.register`**, то есть `shiftRegister` была
пустой трансформацией — меняла IR, но не меняла звук. Исправлено (D-052),
после чего дефект стал находиться.

**Дата.** 14.11.2026.

### E-004. Канарейки не обгоняют нормальный корпус — ✅

**Гипотеза.** Символьный скор нельзя обойти мусором.

**Метод.** Пять канарейк против корпуса из пяти жанровых треков
(`tests/spike/canary-measure.probe.mjs`).

**Результат.** Корпус: 91.0 · 92.7 · 84.7 · 81.5 · 78.2, медиана **84.69**.
Канарейки: три одинаковые секции — 79.7 · ровный луп — 76.7 · случайные
ноты — 80.7 · плотный шум — 81.3 · тишина с кликом — **14.6**. Все строго
ниже медианы. Проверка в CI.

**Замечание.** Три канарейки из пяти отстают от медианы всего на 3–8 баллов —
это узкий зазор. Если корпус станет беднее (например, из-за новых правил
линтера), канарейка может его перегнать. Зазор — не «доказанная защита», а
порог, который надо держать в поле зрения.

**Дата.** 14.11.2026.

### E-005. Поиск по мутациям улучшает зрелый трек — ❌ нулевой результат

**Гипотеза.** Best-of-16 по мутациям IR поднимет символьный скор.

**Метод.** `searchBest(ir, { n: 16 })` на треке «мрачный трип-хоп» с базовым
скором 90.96.

**Результат.** Лучший из 16 кандидатов — **90.96**, то есть базовый. Ни одна
мутация не подняла скор; все либо снижали его, либо ломали трек.

**Интерпретация.** Символьный скор уже близок к потолку для трека, собранного
правилами, — улучшать нечего, и мутации его портят. Это соответствует
прогнозу брифа: «оставить поиск только как фильтр дефектов». Символьный
поиск полезен как фильтр (он отсеивает мусорные варианты за 53 мс вместо
~2.5 с движком), но **как улучшатель вкуса не доказан**.

**Что нужно.** H2 — человеческие пары. Пока их нет, утверждать «поиск улучшает
трек» нельзя.

**Дата.** 14.11.2026.

### E-006. Критик-цикл не ухудшает трек — ✅ (частично)

**Гипотеза.** Критик-цикл с откатом не может ухудшить трек.

**Метод.** `critique(ir)` на зрелом треке (скор 90.96) и на намеренно
испорченном (одна секция вместо пяти).

**Результат.** На зрелом треке: 0 принятых правок, скор не изменился
(90.96 → 90.96) — правильно, ломать нечего. На испорченном: правки
предлагаются, скор не падает. Ни в одном случае скор не снизился.

**Ограничение.** Цикл не улучшает зрелый трек (см. E-005). Это не дефект
алгоритма, а свойство данных: улучшать нечего.

**Дата.** 14.11.2026.

### E-007. Мелодии в картах жанра играли одну ноту на такт

**Гипотеза.** `<4 ~ 2 ~ 5 ~ 3 ~>` внутри `n(...)` — это восемь шагов внутри такта.

**Метод.** Headless-Strudel, `queryArc` по циклам (без звука):

| паттерн | событий за цикл |
|---|---|
| `n("0 2 4")` | 3 |
| `n("<0 2 4>")` | **1** |
| `n("<0 2 4>").scale("D:minor")` | 1 |

**Результат.** Гипотеза неверна: угловые скобки в mini-нотации Strudel — это
«один элемент за цикл». Мело­дии в картах `genre-trip-hop`, `genre-lofi` и
`composer-workflow` играли по одной ноте на такт, а с `degradeBy(.3)` голос
мог замолчать совсем: при одном событии на цикл остаточность `degrade` давала
пустой результат (воспроизведено: `n("<4 ~ 2 ~ 5 ~ 3 ~>").degradeBy(.3)` → 0
событий за 2 цикла).

**Интерпретация.** Ошибка невидима для слуха в тесте: код исполняется, ошибок
нет, музыка играет. Видна только при сравнении с ожидаемым ритмом — то есть
именно тем гейтом, который мы и написали.

**Что сделано.** Шаги внутри такта переписаны без угловых скобок. Прогрессии
(`chord`, `mask`, `pan`) оставлены: там один элемент за цикл нужен. В линтер
добавлено правило `angle-sequence-in-note` с явным opt-out `one-per-cycle`.

**Долг.** Стоит проверить остальные ноты-ловушки mini-нотации в картах:
`*`, `!`, `@`, `,` — часть из них в примерах не встречается, но ловушка того
же рода.

**Дата.** 14.11.2026.

### E-008. Условная арка жанра не срабатывала никогда

**Гипотеза.** `arc: song-64 (или club-64 для «фестиваля»)` означает: на
запрос про фестиваль берётся club-64.

**Метод.** Сверка кода `parseArc` с текстом карты `genre-synthpop` и запросом
«эйфоричный фестиваль».

**Результат.** Гипотеза неверна по двум причинам сразу:
1. Регулярное выражение требовало `)` сразу после `»`, а в карте стоит `»).` —
   точка после скобки не входила в шаблон;
2. слово-триггер в карте стоит в родительном падеже («фестиваля»), а в
   запросе — именительном («фестиваль»); сравнение шло как подстрока.

На практике: «эйфоричный фестиваль» получал song-64 вместо club-64 — то есть
промисс с эмоцией «эйфория» терял клубную арку.

**Что сделано.** Триггер сравнивается по основе (окончание снимается), точка
перед закрывающей скобкой допускается. Проверка покрыта тестом: строка
матрицы активации «эйфоричный фестиваль» обязана давать club-64.

**Дата.** 14.11.2026.

### E-009. Baseline-0 собран: 60 промтов, символьный скор 85.1

**Что сделано.** Корпус из 60 промтов (4 квадранта × 5 жанров × 3 плотности),
сплит 36/12/12 по sha256 id, для каждого — план, код, IR-хэш, code-хэш,
символьный разбор. Манифест подписан sha256 обоих файлов.

**Результат.** Средний символьный скор корпуса — **85.1**, треков с lint-ошибками
— **0**. Это число ничего не говорит о вкусе: это самосогласование оракула с
планировщиком, а не оценка человеком. Оно полезно как точка отсчёта — «не хуже
Baseline-0» — и как страховка от регрессий при правках компилятора.

**Чего не хватает.** Аудио-части Baseline-0 (WAV + MetricsReport +
renderFingerprint): рендер требует браузера, 60 офлайн-рендеров в CI не
влезли в разумный бюджет. До сборки аудио Baseline-0 — это код и символьный
разбор.

**Гипотеза H3 (символьный скор коррелирует с человеком) не проверялась:**
нужны человеческие пары, их пока ноль. Это остаётся главным блокером.

**Дата.** 14.11.2026.

### E-010. Модель пишет в enum-поле описание — и план не проходит Zod

**Гипотеза.** Структурированный вывод (`json_schema`) гарантирует, что модель
ответит по схеме, поэтому Zod-приёмка будет проходить с первого раза.

**Метод.** Живой вызов на боевом сервере: `POST /api/skills/plan` с промтом
«мрачный трип-хоп про дождь», провайдер OpenAI, бюджет 2 вызова.

**Результат.** Гипотеза неверна. Модель отвечает JSON по схеме, но в поле
`plan` (тип партии) пишет естественный язык:

```
layers.texture.plan: «тихий виниловый шум и тёмная атмосфера»
layers.pad.plan:     «разреженный тёмный педальный слой»
layers.kick.plan:    «плотный ломанный якорь с редкими пропусками»
```

Восемь слоёв из восьми. `strict: false` в json_schema этого не ловит: без
strict режима enum подсказка, а не принуждение. Zod отверг весь план, и
система тихо ушла в правила — то есть вызов модели стоил денег и не дал
результата.

**Дополнительно найдено (баг, а не гипотеза).** Ремонтный ретрай был
implementрован неверно: повтор отправлял модели тот же самый запрос, без
текста ошибки и без её прошлого ответа. То есть модель не могла узнать, что
не так, и второй ответ был идентичным первому — «ретрай» не чинил ничего.

**Что сделано.**
* Детерминированная починка по роли (`server/ir/normalize.js`) — форма
  чинится кодом, а не вызовом.
* Ремонтный ретрай с текстом ошибок и прошлым ответом.
* Контракт: enum-поля описаны словами («ОДНО слово, а НЕ описание»).

**Ограничение.** Починка чинит форму, а не музыку. Качество плана модели на
живых прогонах не измерено — для этого нужны человеческие пары (дорожка H).

**Дата.** 14.11.2026.

### E-012. Из прежних меток обучиться нельзя: в них нет признаков

**Гипотеза.** Раз метки дорожки H уже собираются (пары, победители, хэши),
из них можно обучить Taste Model прямо сейчас, без нового сбора данных.

**Метод.** Разобрать формат `server/data/preferences.jsonl` и посмотреть,
чего в нём не хватает для формулы `P(A лучше B) = σ(w · (x_A − x_B))`.

**Результат.** Гипотеза неверна, и не из-за нехватки данных, а из-за формы
записи. Метка содержала: `pairId`, `winner`, `listenMs`, `prompt`, `seed`,
`hashA`, `hashB`. Не было:

* признаков победителя и проигравшего (нечего сравнивать);
* связи «метка → конкретный трек» (хэш не обратим в план);
* аудио-признаков сторон (L0 вообще не мерялся при прослушивании).

Хэш — это идентификатор, а не признак. По двум хэшам нельзя построить
разность векторов.

**Что сделано.** Пары теперь хранятся вместе с IR обеих сторон
(`server/data/pairs.jsonl`, D-064), а страница «Тиндер» отправляет с
меткой аудио-признаки каждой стороны. Сквозной путь пара → метка →
обучающий пример закрыт тестом.

**Следствие для плана.** Дефицит меток — не единственное узкое место; узкое
место было в их форме. Кодовая часть дороги «выученная цель» теперь
готова: как только появятся пары с признаками, обучение — одна команда
(`npm run taste:train`).

**Дата.** 14.11.2026.

### E-013. Прокси-пары от best-of-N дают обучаемую, но не валидированную модель

**Гипотеза.** Если живых пар пока нет, обучение на прокси-парах
(best-of-N, размеченных символьным скором) даст модель, которую можно
использовать как замену символьному скору.

**Метод.** `npm run taste:train` на корпусе Baseline-0 (60 промтов): для
каждого промта строится план по правилам, гоняется поиск, лучший и худший
кандидат образуют прокси-пару. Вес 0.2 (бриф §7.4), 60 пар.

**Результат.** Модель обучается: 14 из 42 весов ненулевые, точность на
тренировочной выборке 0.92, потери 0.437. Но проверка даёт честный
отказ:

* живых пар в проверке 0 → CV-accuracy не вычисляется;
* вердикт: **не допущена** — «человеческих пар 0 < 60»;
* ни одна базовая линия не может быть посчитана, потому что нет живых
  размеченных пар.

**Что это значит.** Прокси-пары учат модель воспроизводить символьный
скор — они размечены им же. Это не проверка, а тавтология: модель
согласится с символьным скором по построению. Поэтому прокси-пары имеют
вес ≤ 0.2 и **не входят в вердикт о допуске** ни при каких числах.

**Ограничение.** 0.92 на прокси-данных — это не «качество музыки на 92 %».
Это число не имеет смысла как характеристика вкуса и не должно так
читаться.

**Дата.** 14.11.2026.

### E-014. Параллельный оффлайн-рендер двух треков ломает глобальный аудиоконтекст

**Гипотеза.** Пары можно готовить быстрее, если рендерить обе стороны
одновременно (`Promise.all`): 16 тактов звука считаются за ~3.3 с wall-clock,
две стороны уложились бы в те же 3.3 с.

**Метод.** В `src/tinder.js` стороны пары рендерились параллельно. Рендер
идёт в отдельном `OfflineAudioContext`, но движок (Strudel/superdough)
переключает ГЛОБАЛЬНЫЙ аудиоконтекст: `setAudioContext`,
`setSuperdoughAudioController`. Два рендера, идущие одновременно,
перехватывают контекст друг у друга.

**Результат.** Отрицательный, но с очень понятным симптомом:

* одна сторона пары выходила нормальной (пик 1.54, LUFS −16.7), вторая —
  тихой: `lufsI = null`, и страница показывала «цель −70.0 LUFS»;
* громкость при этом НЕ выравнивалась (цель = −70 ⇒ гейн 1 для обеих
  сторон), то есть рецензент сравнивал бы «громче» против «тише» — прямое
  нарушение §7.2 (замечание 10 аудита);
* в консоли 198 однотипных исключений
  `InvalidAccessError: ... cannot connect to an AudioNode belonging to a
  different audio context` — по одному на событие оффлайн-рендера;

### E-019. Рендер не побитово детерминирован — ❌ «бит-в-бит» не подтвердилось

| рендер | исходный адаптер | с дренажом пула (эксперимент) |
|---|---|---|
| 1-й | ok | **падает** |
| 2-й | `InvalidAccessError: different audio context` | падает |
| 3-й | падает | падает |

в пул во время следующего. Быстрые рендеры не дают GC очистить пул;
длинные (опера, полные IR-треки) и человеческий темп суждения — дают.

**Что пробовано и откачено.** Дренаж пула беззвучными `superdough`-триггерами
на старте (сэмпл-источник против ложного «чисто» от worklet из пула),
`offline.close()` + барьер макрозадач. Перекрывает только пул `Ei`, не другие
пути удержания; на модифицированном адаптере падал и первый рендер —
правки ухудшали. Адаптер возвращён к исходному (`git checkout`).

**Что это значит.** Дефект предсуществующий, не регрессия этапа 4. В
реальном использовании (человеческий темп, пауза на прослушивание) не
проявлялся — владелец закрыл 10 пар. Тембровые пары (D-132) эффектов не
несут и рендерятся подряд детерминированно. Зонд этапа 4
(`scripts/probe-timbre-ui.mjs`) меряет при человеческом темпе — 13/13.
Быстрое автоматическое суждение подряд в трековом режиме ненадёжно до
полного фикса. Направление фикса — изоляция рендера в свежем экземпляре
модуля/realm на каждый рендер (D-133); требует репликации регистрации
сэмплов и проверки fingerprint (D-104).

**Дата.** 17.11.2026.

### E-022. IR реверберации superdough случайна и применяется асинхронно — ✅ найдено, измерено, закрыто в realm (D-143)

**Гипотеза.** Realm-изоляция (фикс E-020) сама по себе делает офлайн-рендер
воспроизводимым: тот же движок, тот же код → тот же звук.

**Метод.** Зонд `scripts/probe-render-realm.mjs` + временный бисект-спайк
(удалён после диагностики): два свежих iframe-realm рендерят один код,
сравниваются каналы, checksum IR-буфера конвольвера и состояние PRNG.
Код: `note("c3 e3 g3").s("sawtooth")` с вариантами `.lpf(800)`, `.room(0.3)`.

**Результат (до фикса).**

| Вариант | diff суммы \|канал\| между realm | Вывод |
|---|---|---|
| dry | 0 | детерминирован |
| lpf | 0 | детерминирован |
| room | 72.6 (maxAbsDiff ~0.03) | НЕдетерминирован |
| lpf+room | 3.9–72.6 (плавает) | НЕдетерминирован |

При этом checksum IR-буфера (оба канала, 144000 отсчётов) и состояние
Math.random после рендера — ИДЕНТИЧНЫ между realm. Расхождение только в
хвосте реверберации (первые ~2.9 с dry-сигнала совпадают побайтово).

**Причина (по исходникам superdough 1.3.0, два факта).**
1. `generateReverb` заполняет IR белым шумом `Jn() = Math.random()*2-1`
   (плюс случайный детюн генератора бочки `ko`). В одной странице IR
   кэшируется после первой генерации — поэтому runs=2 повторяемость
   проходила; каждый свежий контекст генерирует СВОЮ случайную IR.
   Прежние замеры D-104/E-019 (1 LSB) делались на коде БЕЗ room —
   обобщение «рендер детерминирован» на код с реверберацией было неверным.
2. IR применяется к конвольверу АСИНХРОННО: `generateReverb` → свип в
   отдельном OfflineAudioContext (`Pn`, оставляет `window.filterNode`) →
   `oncomplete` → `convolver.buffer`. `createReverb` вызывает `generate`
   сам в конце. `startRendering` не ждёт буфера — гонка: часть рендеров
   стартует с пустым конвольвером. Первая версия ожидания (обёртка только
   `node.generate`) НЕ ловила первый generate — измерено: diff оставался
   ~0.02; после отслеживания с момента создания узла — закрыто.

**Фикс (D-143, только в realm, живая страница не тронута).**
(a) `Math.random = mulberry32(RENDER_SEED=0x5eed2026)` до первого рендера;
(б) отслеживание каждого `createReverb`-узла + ожидание `convolver.buffer`
перед `startRendering` (additive-хук `prepare` адаптера, таймаут 5 с →
честная ошибка «рендер недостоверен»).

**Результат (после).** room: diff суммы **3.7e-8**, lpf+room **3.1e-8**,
maxAbsDiff **2.98e-8** ≤ 1e-4 (допуск D-104). Зонд зелёный целиком:
3/3 быстрых рендеров, D-104 adapter-vs-realm maxAbsDiff **0**, живой трек
не затронут, пресет Timbre звучит. Evidence: docs/evidence/render-realm/probe.json.

### E-032. Мьютекс тяжёлых операций на Windows был пустым

19.11.2026, измерено на машине владельца (Windows x64, Python 3.12.16). `heavy_lock` опирался только на `fcntl.flock`; в Windows `fcntl` не существует, модуль импортировался как `None`, и контекст отдавал `locked=False`, то есть **мьютекс не брался вовсе** — воркер на `ThreadingHTTPServer` мог выполнять два `/separate` одновременно. На практике это прикрывала очередь демона (concurrency=1), но механизм D-091 на этой платформе не работал.

Проверено на живом воркере 8010: до правки `locked=False` при доступном файле мьютекса. После правки мьютекс берётся через `msvcrt.locking` (эксклюзивный диапазон байтов, держится ядром, снимается при закрытии дескриптора и при падении процесса). Путь по умолчанию на Windows — временный каталог пользователя; `DD_HEAVY_LOCK` переопределяет его; на POSIX путь `/lock/heavy.lock` сохранён.

Три регрессии на живом коде: мьютекс берётся и пишет владельца в отдельный `<путь>.owner` (на Windows запертый диапазон нельзя прочитать — запись в сам файл делала бы его нечитаемым); второй претендент ждёт и получает ошибку «занят дольше N с» по таймауту; блокировка освобождается после блока. ### E-034. Стенд фактов Strudel 1.3.0: что движок действительно умеет (19.11.2026)

Метод: `scripts/probe-strudel-facts.mjs` (`npm run probe:facts`) — Node без
браузера, UMD-бандл `@strudel/web` 1.3.0, события считаются настоящим
`queryArc`; звучание проверено рендером в headless-Chromium. Артефакты:
`docs/STRUDEL-FACTS.md`, `docs/evidence/strudel/facts.json`.

Ключевые измеренные факты (детали в файле):
- `duckorbit` — метод паттерна, исполняется, 4 события. `duckOrbit` и
  `duckAttack` (другой регистр) — **не существуют**: движок отвечает
  «s(...).duckOrBit is not a function». Опечатка в регистре — тихая поломка.
- `detunepower` в 1.3.0 **отсутствует**. `lfo`, `tremolo`, `tremolosync`,
  `tremolodepth`, `postgain`, `compressor`, `unison`, `detune`, `spread`,
  `seg`, `lpenv` — есть и исполняются.
- Лады: рабочее написание — через двоеточия (`A:harmonic:minor` → 5 событий).
  `A:harmonic_minor`, `A:harmonicminor`, `BOGUS:xxx` — **0 событий**;
  `A harmonic minor` (с пробелом) даёт 2 события и **другие ноты** (Ab3, C4) —
  то есть не «почти тот же лад», а другой.
- Аккорды: `chord(X)` без `.voicing()` даёт 1 событие и **0 нот** — партия
  молчит. `F^7`, `FM7`, `Fm7`, `G7`, `Am` с `.voicing()` → 5 событий и 5 нот;
  `Fmaj7` и `A:min` с `.voicing()` → **0 событий**. `rootNotes()` — 0 событий,
  замена `.voicing()` не работает.
- Темп: `setCpm`/`setcps`/`setbpm` в Node-стенде недоступны (control-функции
  регистрируются `initStrudel` в браузере) — проверка темпа только рендером.
- Звучание: `lead`, `am`, `organ` — **ошибка** («sound not found»); `supersaw`,
  `sawtooth`, `square`, `triangle`, `sine`, `piano`, `pulse`, `fm`, `bd`, `hh`,
  `cp`, `sd` — звучат (LUFS-I от −27 до −14.9).
- `lpf(sine.range(...))` без `.seg()` — 1 событие (значение читается один раз на
  ноту); с `.seg(16)` — 16 событий (непрерывная огибающая).

Гейт: `tests/unit/strudel-facts.test.js` — 34 теста, сверяют реестр правил с
фактами измерения (не с захардкоженным списком).

### E-040. Отрицательный результат: ворота красные из-за константы в тесте (19.11.2026)

### E-041. Диск C: заполнен, и ворота падают на ENOSPC (19.11.2026)

Второй прогон ворот после починки теста RAG — снова **красный**, но уже по
другой причине: три теста в `tests/unit/deep-dive-pipeline.test.js` упали с
`ENOSPC: no space left on device, copyfile ... input.wav -> original.wav`.

Причина — состояние машины, а не код: на диске C: свободно **1 032 192 байта
(≈1 МБ)** при занятых 194 ГБ. Место требуется тестам, которые пишут WAV во
временный каталог (`%TEMP%`).

Что измерено про заполнение:
- `%TEMP%` = **2.74 ГБ**, из них **134 каталога `playwright_chromiumdev_profile-*`**
  (≈18 МБ каждый) — суммарно ≈2.4 ГБ; по датам: 15.11 — 33, 16.11 — 12,
  17.11 — 10, 18.11 — 44, 19.11 — 35.
- Измерено отдельно: **корректно закрытый браузер не оставляет профиля**
  (`chromium.launch()` → `browser.close()` → 0 каталогов). Значит, текут
  процессы, которые умирают, не закрыв браузер: прерванные прогоны,
  убитые воркеры vitest, снятые процессы.
- Один полный прогон тестов (`npx vitest run`, 2147 тестов, 89.1 с) оставляет
  **1 пустой** профиль; `render-wav.test.js` и `gate:a` по отдельности —
  0 профилей. То есть за один прогон утечка мала, но за 5 дней накопилось
  134 каталога.
- Кэши: `~/.cache` — 1.45 ГБ, `pip` — 0.48 ГБ, `npm` — 0.53 ГБ,
  `ms-playwright` — 0.5 ГБ.

Обход для ворот: `TEMP`/`TMP` перенесены на F: (свободно 102.8 ГБ) — после
этого `npm run gate` **зелёный, 15/15 за 143.4 с**. Это не обход гейта: сам
гейт не менялся, менялось только место временных файлов.

Что НЕ сделано (и почему): очистить `%TEMP%` из сессии нельзя — политика
безопасности блокирует удаление вне рабочего каталога. Владельцу: удалить
`%TEMP%\playwright_chromiumdev_profile-*` (≈2.4 ГБ) и перенести `TEMP` на
диск со свободным местом; без этого ворота будут падать на `ENOSPC`.

Найденный проектный дефект (не закрыт): процесс, который умирает, не
закрывает Chromium, и его временный профиль остаётся навсегда. Место для
правки — `server/deepdive/render/render-worker.mjs` (закрытие браузера при
аварийном выходе) и зонды, которые запускают Chromium.
